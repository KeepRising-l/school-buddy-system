# Reference：模块三——交互原型与视觉验证 V1

> **版本：V1.0**
> **模块定位：交互原型与视觉验证**
> **核心问题：用户将看到什么、怎么操作？**

------

# 一、Reference 定位

模块三位于整个软件开发流程的第三阶段。

四个模块分别解决：

```text
模块一：需求规划
    ↓
    做什么？

模块二：技术设计
    ↓
    怎么做？

模块三：交互原型与视觉验证
    ↓
    用户看到什么？
    用户怎么操作？

模块四：开发规划与 MVP 实现
    ↓
    怎么真正做出来？
```

因此，模块三不是重新分析需求，也不是重新设计技术架构，更不是直接开始正式开发。

它的核心任务是：

> **把已经明确的产品需求和已经确定的技术方案，转换成用户能够直观看到、理解、修改和验证的交互原型。**

模块三最终要解决的是：

> **在真正开发之前，用户是否已经明确知道这个产品长什么样、页面怎么组织、用户怎么操作，以及不同操作之间如何流转。**

------

# 二、Skill 与 Reference 的关系

本 Reference 与：

```
Skill_模块三_交互原型与视觉验证_V1.md
```

的关系是：

> **Skill 是行为规则，Reference 是经验知识。**

Skill 负责告诉 AI：

```text
什么时候进入模块三
应该怎么工作
什么时候生成原型
什么时候询问用户
什么时候修改原型
什么时候验证
什么时候允许冻结
什么时候必须回退
```

Reference 负责告诉 AI：

```text
什么是好的 Wireframe
如何表达页面结构
如何表达交互
有哪些常见页面类型
如何处理不同复杂度的产品
哪些原型表达方式已经经过实践验证
```

因此：

> **Skill 决定 AI 怎么工作，Reference 帮助 AI 知道什么样的工作结果更合理。**

------

# 三、模块三的核心目标

模块三的核心不是“画得漂亮”。

而是：

> **让产品在正式开发之前变得可视化、可操作、可验证。**

一个优秀的低保真原型至少应该让用户能够理解：

```text
这个产品有哪些端？
        ↓
每个端有哪些页面？
        ↓
每个页面有什么？
        ↓
这些东西放在哪里？
        ↓
用户可以操作什么？
        ↓
点击之后发生什么？
        ↓
会跳转到哪里？
        ↓
操作成功/失败之后发生什么？
```

因此：

> **原型不是图片，而是产品交互意图的可视化表达。**

# 五、模块三与其他模块的边界

这是整个 Reference 中最重要的部分之一。

## 5.1 模块三不能重新定义产品

例如模块一已经确定：

> 用户可以使用账号密码登录。

模块三可以设计：

```text
账号输入框
密码输入框
登录按钮
```

但不能自行增加：

```text
微信登录
QQ 登录
手机号验证码登录
Apple 登录
```

因为这些属于产品能力。

------

## 5.2 模块三不能重新设计技术架构

例如模块二已经确定：

```text
Vue 3
Spring Boot
REST API
JWT
```

模块三不应该重新讨论：

> “要不要换 React？”

也不应该因为 Wireframe 的表现形式而重新决定后端架构。

------

## 5.3 模块三不能决定开发优先级

例如原型中有：

```text
商品
购物车
订单
优惠券
积分
评论
```

模块三可以完整表达它们的关系。

但：

> 第一阶段到底先开发哪些？

这是模块四的职责。

------

# 六、原型的核心表达方式：Wireframe

模块三 V1 的核心原型表达形式是：

> **文本版线框示意图（Wireframe，线框图）**

它不是高保真视觉设计。

也不是最终 UI。

它主要表达：

```text
页面结构
信息层级
组件位置
页面关系
操作入口
交互关系
状态变化
```

------

# 七、为什么 V1 采用 Wireframe

低保真 Wireframe 有一个非常重要的优势：

> **它不会让用户过早陷入颜色、字体、阴影、圆角等视觉细节，而是先确认产品结构和交互。**

例如：

```text
┌────────────────────────────────────────────┐
│ Logo                         用户头像      │
├──────────────┬─────────────────────────────┤
│              │                             │
│ 首页         │       商品列表              │
│ 商品管理     │                             │
│ 订单管理     │  ┌──────┐  ┌──────┐        │
│ 用户管理     │  │ 商品A │  │ 商品B │        │
│              │  │ ¥99   │  │ ¥59   │        │
│              │  └──────┘  └──────┘        │
│              │                             │
└──────────────┴─────────────────────────────┘
```

这个阶段并不需要决定：

```text
#1677FF
字体 14px
圆角 8px
阴影 0 2px 8px
```

因为这些属于视觉设计和正式 UI 实现。

------

# 八、Wireframe 不是静态截图

这是模块三非常重要的认知。

错误理解：

> Wireframe = 一张页面图片。

正确理解：

> Wireframe = 页面结构 + 页面关系 + 交互意图的表达。

因此，一个页面不仅需要描述：

```text
有什么
```

还需要描述：

```text
在哪里
```

以及：

```text
怎么操作
```

以及：

```text
操作之后发生什么
```

------

# 九、页面原型的五层结构

模块三可以采用以下递进结构：

```text
产品
  ↓
用户端 / 管理端
  ↓
页面
  ↓
页面组件
  ↓
交互
```

这五层并不是固定的页面数量，而是**逐层深入的认知结构**。

------

## 9.1 第一层：产品

首先确定整个产品。

例如：

```text
社区生鲜团购平台
```

------

## 9.2 第二层：用户端 / 管理端

根据产品需求确定不同端。

例如：

```text
社区生鲜团购平台
│
├── 用户端
│
├── 团长端
│
└── 管理端
```

如果产品没有独立的团长端，则不能为了“完整”强行增加。

------

## 9.3 第三层：页面

例如用户端：

```text
用户端
│
├── 首页
├── 商品列表
├── 商品详情
├── 购物车
├── 提交订单
├── 我的订单
├── 订单详情
└── 个人中心
```

------

## 9.4 第四层：页面组件

例如商品详情：

```text
商品详情
│
├── 商品图片
├── 商品名称
├── 商品价格
├── 库存
├── 商品描述
├── 数量选择
├── 加入购物车
└── 立即购买
```

------

## 9.5 第五层：交互

继续向下：

```text
点击「加入购物车」
        ↓
加入购物车
        ↓
购物车数量 +1
        ↓
提示操作成功
```

或者：

```text
点击「立即购买」
        ↓
提交订单页
```

这才形成完整的交互表达。

------

# 十、页面必须回答的五个问题

一个页面的原型是否足够清楚，可以检查：

### ① 这个页面有什么？

例如：

```text
商品名称
商品价格
商品图片
库存
购买按钮
```

### ② 这些东西在哪里？

例如：

```text
顶部：导航
中间：商品信息
底部：操作区域
```

### ③ 用户可以操作什么？

例如：

```text
搜索
筛选
加入购物车
购买
收藏
```

### ④ 点击之后发生什么？

例如：

```text
点击商品卡片
        ↓
商品详情
```

### ⑤ 操作成功/失败后发生什么？

例如：

```text
库存不足
    ↓
提示“库存不足”
    ↓
不能提交订单
```

------

# 十一、交互必须明确表达“点击哪里 → 去哪里”

这是模块三的重要规范。

不能只写：

```text
商品详情页
```

还应该表达：

```text
点击「立即购买」
        ↓
提交订单页
```

例如登录：

```text
登录页
│
├── 点击「登录」
│      ↓
│    首页
│
└── 点击「注册」
       ↓
     注册页
```

再例如：

```text
商品列表
│
├── 点击商品卡片
│      ↓
│    商品详情
│
└── 点击购物车
       ↓
     购物车
```

------

# 十二、交互关系应该独立于页面 Wireframe

一个成熟的原型不能只保存页面。

还应该存在：

```text
页面
组件
组件类型
操作
目标页面
操作结果
```

例如：

```text
Page:
商品列表

Component:
商品卡片

Action:
click

Target:
商品详情
```

因此 AI 在修改 Wireframe 时，也应该同步维护结构化的原型关系。

------

# 十三、Wireframe 与结构化原型模型

可以把模块三理解成：

```text
                原型系统
                   │
          ┌────────┴────────┐
          ↓                 ↓
      Wireframe        结构化原型模型
          │                 │
          ↓                 ↓
      用户看到的          AI理解的
      页面表达            页面/组件/交互关系
```

两者必须保持一致。

例如用户说：

> “把最近聊天放到左边菜单下面。”

那么 AI 不应该只修改文字：

```text
最近聊天
```

还应该同步修改：

```text
左侧导航结构
最近聊天所属区域
组件层级
页面布局关系
```

------

# 十四、自然语言修改是模块三的重要能力

用户不应该必须学习专业原型工具。

可以直接说：

> “左边栏窄一点。”

> “最近聊天放到左边菜单下面。”

> “把输入框放到页面最下面。”

> “商品卡片增加库存。”

> “点击商品卡片进入详情页。”

> “订单状态放到右上角。”

AI 应该理解这些修改对应的原型意图，并同步修改：

```text
Wireframe
+
结构化原型
+
页面关系
+
交互关系
```

```text
    │       │
    │       ├── 点击「加入购物车」
    │       │       ↓
    │       │    加入购物车成功
    │       │
    │       └── 点击「立即购买」
    │               ↓
    │             提交订单
    │
    └── 点击商品 B
            ↓
         商品详情
```

这种表达非常适合验证：

> 用户到底是怎么走完一条业务流程的？

------

# 二十三、典型 Wireframe 案例九：弹窗与二次确认

```text
商品列表
    │
    ↓
点击「删除」
    │
    ↓
┌──────────────────────────────┐
│         确认删除？            │
│                              │
│ 删除后无法恢复。              │
│                              │
│       [取消]    [确认删除]    │
└──────────────────────────────┘
```

交互：

```text
点击取消
    ↓
关闭弹窗

点击确认删除
    ↓
执行删除
    ↓
成功 → 返回列表并刷新
失败 → 显示错误信息
```

------

# 二十四、典型 Wireframe 案例十：多步骤流程

例如商品购买：

```text
① 确认商品
      ↓
② 确认地址
      ↓
③ 确认订单
      ↓
④ 支付
      ↓
⑤ 完成
```

Wireframe 可以表达：

```text
┌──────────────────────────────────────────────────────────┐
│ ① 商品 ───── ② 地址 ───── ③ 订单 ───── ④ 支付 ───── ⑤ 完成 │
├──────────────────────────────────────────────────────────┤
│                                                          │
│                 当前步骤内容                             │
│                                                          │
│                          [上一步] [下一步]                │
└──────────────────────────────────────────────────────────┘
```

重点是验证：

```text
步骤顺序
每一步需要什么
什么时候可以下一步
什么时候不能下一步
完成之后去哪
```

------

# 二十五、页面状态也是原型的一部分

不要只设计“正常状态”。

一个页面至少可能存在：

```text
正常
加载中
空数据
错误
无权限
操作成功
操作失败
```

例如商品列表：

```text
正常：

商品 A
商品 B
商品 C
```

空状态：

```text
┌──────────────────────────┐
│                          │
│      暂无商品             │
│                          │
│      [去添加商品]         │
│                          │
└──────────────────────────┘
```

加载：

```text
正在加载商品……
```

错误：

```text
商品加载失败

[重新加载]
```

------

# 二十六、原型不应该只覆盖 Happy Path

一个成熟原型不能只有：

```text
点击 → 成功
```

还应该考虑重要分支：

```text
点击
 ↓
成功
```

以及：

```text
点击
 ↓
失败
```

或者：

```text
提交
 ↓
库存不足
 ↓
提示
 ↓
不能继续
```

或者：

```text
提交
 ↓
未登录
 ↓
登录页
 ↓
登录成功
 ↓
回到原操作流程
```

------

# 二十七、哪些异常需要进入原型

不是所有异常都必须画出来。

重点考虑：

> **这个异常是否会改变用户操作路径？**

例如：

```text
网络延迟
```

通常只需要 Loading。

但：

```text
库存不足
```

可能直接改变业务流程：

```text
提交订单
 ↓
库存不足
 ↓
无法提交
```

这种就应该进入原型验证。

------

# 二十八、原型复杂度应该与产品复杂度匹配

不要为了“看起来专业”而把所有页面都画得非常复杂。

简单产品：

```text
页面少
流程简单
交互少
```

原型就应该简单。

复杂产品：

```text
多角色
多端
复杂业务流程
大量状态
```

才需要深入：

```text
页面
 ↓
组件
 ↓
交互
 ↓
状态
 ↓
流程
```

因此：

> **原型深度应该由业务复杂度和交互不确定性决定，而不是由固定模板决定。**

------

# 二十九、不是所有页面都需要同样的原型深度

例如：

### 简单页面

```text
关于我们
```

可能只需要：

```text
页面结构
内容区域
返回入口
```

即可。

而：

### 复杂页面

```text
订单详情
```

可能需要：

```text
订单状态
商品信息
价格
地址
操作按钮
取消
退款
确认收货
异常状态
权限
不同状态下可执行操作
```

需要更深入地表达。

------

# 三十、AI 应该自动判断原型范围

模块三不应该要求用户先填写：

```text
我要几个页面
我要画哪些页面
我要设计哪些组件
```

因为模块一和模块二已经包含大量信息。

AI 应该根据：

```text
产品需求
角色
业务流程
技术设计
核心功能
用户操作路径
```

自动推导：

```text
需要哪些端
需要哪些页面
哪些页面重要
哪些页面需要深入
哪些交互需要验证
```

------

# 三十一、原型范围不是固定页面数量

不能简单规定：

> 每个项目必须生成 20 个页面。

因为：

```text
Todo List
```

和：

```text
电商平台
```

的复杂度完全不同。

更合理的标准是：

> **所有会影响用户核心操作理解的页面和交互，都应该得到足够的原型表达。**

------

# 三十二、原型的核心价值是“提前发现问题”

例如模块一认为：

```text
用户 → 下单
```

模块三真正把流程画出来后发现：

```text
商品详情
 ↓
立即购买
 ↓
提交订单
 ↓
地址
 ↓
支付
```

这时候可能发现：

> 用户没有地址怎么办？

或者：

> 用户修改地址之后订单使用哪个地址？

如果这个问题属于业务规则，那么应该：

```text
模块三发现问题
      ↓
判断属于产品问题
      ↓
回到模块一
      ↓
重新确认
      ↓
重新冻结
      ↓
回到模块三
```

而不是偷偷在原型里决定。

------

# 三十三、原型验证与需求验证不是一回事

模块一验证：

> **产品应该做什么？**

模块三验证：

> **已经决定要做的东西，用户看到和操作起来是不是合理？**

例如：

### 模块一

确定：

> 用户可以取消订单。

### 模块三

验证：

```text
订单详情
 ↓
取消订单
 ↓
确认弹窗
 ↓
确认
 ↓
订单状态变为已取消
```

如果用户说：

> “我觉得取消订单不应该放这里。”

这是交互问题。

如果用户说：

> “其实用户根本不能取消这个订单。”

这是产品需求问题。

两者必须区分。

------

# 三十四、原型修改时不能产生隐性需求

用户说：

> “把按钮放到右边。”

AI 只需要修改布局。

不能顺便：

```text
增加一个按钮
增加一个接口
增加一种业务状态
增加一个权限
```

除非用户明确提出，或者该内容已经由前面冻结的需求/技术设计确定。

------

# 三十五、最小交互 Demo

Wireframe 确认之后，可以进入：

> **最小交互 Demo**

它与最终 MVP 不同。

------

## Wireframe

解决：

> “这个页面应该是什么结构？”

------

## 最小交互 Demo

解决：

> “按照这个结构操作起来是什么感觉？”

------

## MVP

解决：

> “真正可以使用的最小产品是什么？”

三者不能混淆：

```text
Wireframe
    ↓
看结构

最小交互 Demo
    ↓
体验交互

MVP
    ↓
真正运行产品
```

------

# 三十六、最小交互 Demo 的目标

Demo 不需要实现完整系统。

重点验证：

```text
页面跳转
核心点击
关键输入
核心流程
交互反馈
```

例如：

```text
登录
 ↓
首页
 ↓
商品列表
 ↓
商品详情
 ↓
立即购买
 ↓
提交订单
```

只要核心流程可以操作，就能够帮助用户发现：

```text
页面不合理
按钮位置不合理
跳转不合理
流程太长
缺少关键步骤
```

------

# 三十七、Demo 不应该变成正式开发

一个常见错误：

```text
原型
 ↓
直接开始写完整后端
 ↓
数据库
 ↓
支付
 ↓
权限
 ↓
部署
```

这是模块四的工作。

模块三只需要：

> **用最低成本验证交互是否正确。**

------

# 三十八、视觉验证应该分层

模块三虽然包含“视觉验证”，但 V1 的重点仍然是：

```text
结构
布局
层级
交互
```

而不是最终视觉品质。

可以理解成：

### V1

```text
低保真 Wireframe
```

### 后续版本

可以逐渐增加：

```text
高保真 UI
视觉规范
设计系统
主题
响应式
动效
```

因此 V1 不应该过早膨胀。

------

# 三十九、V1 暂不强制手绘识别

未来可以支持：

```text
用户手绘
      ↓
AI 识别
      ↓
结构化原型
      ↓
Wireframe
```

但这属于更复杂的能力。

V1 的核心能力先确定为：

```text
AI 自动生成 Wireframe
        ↓
用户自然语言修改
        ↓
AI 自动更新原型
```

也就是说：

> **V1 优先解决“生成与修改”，而不是“识别手绘”。**

------

# 四十、原型必须保持同步

模块三存在三个需要同步的对象：

```text
① Wireframe
② 原型结构
③ 交互关系
```

例如用户说：

> “点击商品卡片进入详情页。”

AI 至少需要同步：

```text
Wireframe：
商品卡片增加可点击意图

原型结构：
商品卡片 → Interactive Component

交互关系：
商品列表 → 商品详情
```

否则最终会出现：

> 图上能点，模型不知道。

或者：

> 模型认为能跳转，Wireframe 却没有表达。

------

# 四十一、原型修改应该具有连续性

例如用户连续提出：

> “左边加个菜单。”

然后：

> “菜单窄一点。”

然后：

> “最近聊天放菜单下面。”

AI 应该基于当前版本继续修改，而不是每次重新生成一个完全不同的页面。

因此：

> **原型应该是一个持续演进的模型，而不是一次性生成的图片。**

------

# 四十二、核心业务流程优先

原型验证时，应该优先验证：

```text
核心用户
    ↓
核心功能
    ↓
核心业务流程
```

例如电商：

```text
浏览商品
 ↓
商品详情
 ↓
购买
 ↓
订单
```

比：

```text
修改头像
```

更应该优先验证。

------

# 四十三、权限相关交互也属于原型

如果系统存在角色：

```text
管理员
普通用户
商户
团长
```

同一个页面可能出现不同操作。

例如：

```text
订单详情

普通用户：
[取消订单]

商户：
[开始制作]
[发货]

管理员：
[关闭订单]
```

因此原型不仅要表达页面，还需要表达：

> **不同角色在页面上看到什么、可以操作什么。**

但权限规则本身仍然来自前面的需求与技术设计。

------

# 四十四、原型应该帮助发现“页面缺失”

例如业务流程：

```text
提交申请
 ↓
审核
 ↓
审核通过
 ↓
开始使用
```

但原型只有：

```text
申请页面
审核页面
```

没有：

```text
审核结果
```

这就可能说明：

> 产品虽然定义了业务流程，但用户实际操作路径没有完整承载。

此时需要判断：

```text
是产品需求缺失？
还是原型表达缺失？
```

不能直接自行决定。

------

# 四十五、原型应该帮助发现“操作入口缺失”

例如产品需求规定：

> 用户可以修改地址。

但 Wireframe 中：

```text
个人中心
订单详情
提交订单
```

都没有入口。

这意味着：

> 功能虽然存在，但用户不知道从哪里使用。

这是原型阶段非常重要的验证结果。

------

# 四十六、原型应该帮助发现“流程断裂”

例如：

```text
购物车
 ↓
提交订单
 ↓
支付
```

但支付成功之后没有任何去向。

那么就应该补充：

```text
支付成功
 ↓
订单详情 / 支付成功页
```

如果这个去向涉及产品行为，就需要回到模块一确认。

------

# 四十七、原型设计中的常见错误

## 错误一：把 Wireframe 当 UI 设计

过早讨论：

```text
颜色
字体
阴影
动画
```

导致核心业务还没确认，视觉已经做得很复杂。

------

## 错误二：只画页面，不画交互

例如：

```text
商品详情页
```

但没有：

```text
点击购买去哪？
点击加入购物车发生什么？
库存不足怎么办？
```

------

## 错误三：只画 Happy Path

忽略：

```text
空数据
失败
无权限
库存不足
状态限制
```

------

## 错误四：原型偷偷增加需求

例如用户只要求：

> 登录。

却自行增加：

```text
微信登录
短信登录
忘记密码
第三方登录
```

------

## 错误五：原型修改后没有同步交互模型

导致：

```text
Wireframe ≠ Prototype Model
```

------

## 错误六：所有页面都做同样深度

简单页面过度设计，复杂页面反而没有深入。

------

## 错误七：Demo 做得太大

原型验证最后变成正式开发。

------

# 四十八、模块三的成熟工作方式

推荐形成：

```text
读取需求
   ↓
读取技术设计
   ↓
理解产品整体
   ↓
判断用户端 / 管理端
   ↓
识别核心业务流程
   ↓
推导页面
   ↓
推导页面组件
   ↓
推导交互关系
   ↓
生成 Wireframe
   ↓
用户查看
   ↓
用户自然语言修改
   ↓
同步更新原型模型
   ↓
再次展示
   ↓
核心流程验证
   ↓
最小交互 Demo
   ↓
用户确认
   ↓
原型冻结
```

------

# 四十九、模块三的完成标准

模块三不是：

> “所有页面都画完了。”

而应该是：

> **所有核心页面、核心交互和核心业务流程都已经得到足够的原型表达，并且不存在会导致后续开发产生明显交互理解差异的重大问题；用户已经确认核心原型和交互方式，并完成必要的最小交互验证。**

也就是说：

```text
页面数量 ≠ 完成度
```

真正重要的是：

```text
核心流程覆盖度
+
交互明确度
+
用户确认度
```

------

# 五十、模块三的最终验收检查

可以使用以下 Checklist：

```text
□ 产品整体结构明确

□ 用户端 / 管理端明确

□ 核心页面明确

□ 页面之间关系明确

□ 页面核心组件明确

□ 重要操作入口明确

□ 点击行为明确

□ 页面跳转明确

□ 输入行为明确

□ 提交行为明确

□ 成功状态明确

□ 重要失败状态明确

□ 重要异常流程明确

□ 角色差异明确

□ 权限相关交互明确

□ 核心业务流程完整

□ Wireframe 与结构化原型同步

□ 用户修改可以被持续同步

□ 没有偷偷增加产品能力

□ 没有偷偷修改技术方案

□ 核心交互已经用户确认

□ 必要的最小交互 Demo 已验证

□ 原型可以冻结
```

------

# 五十一、模块三的经验总结

经过前面的项目探索，可以把模块三的经验浓缩成几个重要原则。

### 原则一

> **原型不是画图，而是表达产品交互。**

### 原则二

> **Wireframe 不是截图，而是页面结构和交互意图。**

### 原则三

> **页面必须表达“有什么、在哪里、怎么操作、操作之后发生什么”。**

### 原则四

> **重要交互必须能够回答“点击哪里 → 去哪里/发生什么”。**

### 原则五

> **原型深度应该由业务复杂度和交互不确定性决定。**

### 原则六

> **AI负责生成和维护原型，用户负责确认和修改产品体验。**

### 原则七

> **Wireframe、结构化原型和交互关系必须保持同步。**

### 原则八

> **原型不能偷偷增加产品能力。**

### 原则九

> **Demo 用来验证交互，不应该提前变成正式开发。**

### 原则十

> **真正的完成不是“画完所有页面”，而是消除核心交互的不确定性。**

------

# 五十二、四个模块的整体关系

模块三必须始终放在整个系统中理解：

```text
┌────────────────────────────────────────────────────────────┐
│ 模块一：需求规划                                          │
│                                                            │
│ 定义产品事实                                               │
│ 做什么？                                                   │
└──────────────────────────┬─────────────────────────────────┘
                           ↓
                     产品需求冻结
                           ↓
┌────────────────────────────────────────────────────────────┐
│ 模块二：技术设计                                          │
│                                                            │
│ 技术落地                                                   │
│ 怎么实现？                                                 │
└──────────────────────────┬─────────────────────────────────┘
                           ↓
                     技术设计冻结
                           ↓
┌────────────────────────────────────────────────────────────┐
│ 模块三：交互原型与视觉验证                                │
│                                                            │
│ 用户看到什么？怎么操作？                                   │
└──────────────────────────┬─────────────────────────────────┘
                           ↓
                     原型设计冻结
                           ↓
┌────────────────────────────────────────────────────────────┐
│ 模块四：开发规划与 MVP 实现                               │
│                                                            │
│ 怎么真正做出来？                                           │
└────────────────────────────────────────────────────────────┘
```

因此：

> **模块一定义产品事实。**
> **模块二把产品事实变成技术方案。**
> **模块三把产品和技术变成可验证的用户交互。**
> **模块四把已经确认的东西变成真正的软件。**

------

# 五十三、模块三 Reference 的核心结论

如果把整个 Reference 最终压缩成一段话：

> **交互原型与视觉验证不是为了提前把页面做漂亮，而是为了在正式开发之前，把已经确定的产品和技术方案转化成用户可以理解、查看、修改和操作的原型。AI 应根据产品复杂度自动判断原型范围，从“产品 → 用户端/管理端 → 页面 → 页面组件 → 交互”逐层展开，通过文本版 Wireframe 表达页面结构，并维护页面、组件和交互之间的一致关系。用户可以通过自然语言持续修改原型，AI 必须同步更新 Wireframe、结构化原型和交互关系。原型阶段不能偷偷增加产品能力，也不能重新设计技术架构。核心页面、核心交互和核心业务流程经过用户确认，并通过必要的最小交互 Demo 验证后，模块三才真正完成，并将冻结后的原型交给模块四进行开发规划与 MVP 实现。**

------

## 五十四、最终原则

> **先理解产品，再表达产品。**

> **先确认结构，再讨论视觉。**

> **Wireframe 表达页面，交互关系表达行为。**

> **页面不是孤立的，页面之间必须形成完整流程。**

> **原型不是静态图片，而是可持续修改的结构化模型。**

> **用户修改的是产品体验，AI负责维护原型一致性。**

> **模块三不重新定义需求，不重新设计技术，不提前承担开发。**

> **真正需要验证的不是“画得好不好看”，而是“用户能不能按照这个原型正确地完成产品核心任务”。**

> **原型确认之后，才能进入真正的开发执行。**
