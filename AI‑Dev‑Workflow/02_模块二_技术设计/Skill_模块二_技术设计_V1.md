# Skill 模块二：技术设计 V1

> **本 Skill 采用分层加载：先阅读本摘要即可开始工作；执行到具体环节时，再深入对应章节。**

## 0. 执行摘要（必读）

### 模块二是什么

把模块一已冻结的产品需求与业务规格，转化为完整、一致、可实现，并经过核心验证的技术方案。

只回答「怎么做」，不重新定义产品，不直接进入大规模开发。

### 工作循环

```text
理解已确定的业务
    ↓
提取技术约束
    ↓
可行性分析
    ↓
技术方案推导（架构 / 数据 / API / 权限 / 状态）
    ↓
业务规则技术落地 + 全场景覆盖检查
    ↓
反向一致性检查
    ↓
核心 Demo 验证
    ↓
用户确认 → 技术设计冻结
```

### 技术决策三级判断

- 🟢 一级：普通实现细节，AI 直接决定，不打扰用户；
- 🟡 二级：重要但可推导的设计，AI 决定并在文档中说明原因；
- 🔴 三级：无法合理推导且影响重大（产品能力 / 成本 / 安全 / 外部依赖），必须确认。

### 十条铁律

1. 模块一已确定的内容直接继承，不得重新询问；
2. 先理解，再推导；先验证，再决策；
3. 技术服务于产品，不得为实现方便偷偷修改业务规则；
4. 技术追求适合，不追求高级，不过度工程化；
5. 每条重要业务规则都要找到技术落点；
6. 必须做全场景覆盖检查，不只验证主流程；
7. 完成方案后必须反向检查需求是否仍全部成立；
8. 有技术风险必须用最小 Demo 验证，Demo ≠ MVP；
9. 没有用户确认不得冻结；
10. 返回模块一修订需求是正常流程，不是失败。

- 技术决策分级：第 8 节
- 架构 / 数据 / 权限 / API 设计：第 11~17 节
- 全场景覆盖与反向检查：第 19~20 节
- Demo 验证：第 22~23 节

## 一、模块定位

你现在执行的是：

> 四模块工作流中的模块二——技术设计。

本模块只负责一件事情：

> **把模块一已经确认的产品需求与业务规格，转化为一套完整、一致、可实现，并经过核心方案验证的技术方案。**

本模块回答：

> **“这个产品怎么做？”**

本模块的上游是：

> **模块一：产品需求与业务规格**

本模块的下游是：

> **模块三：交互原型与视觉验证**

开发规划与执行由模块四承担。

因此，本模块既不能重新定义产品，也不能直接进入大规模开发执行。

------

# 二、核心目标

技术设计的目标不是：

- 堆砌技术名词；
- 罗列所有可能使用的技术；
- 机械生成数据库表；
- 机械生成 API；
- 让文档看起来很专业；
- 在没有验证的情况下假设方案一定可行。

真正目标是：

> **建立一套能够忠实承载产品需求、覆盖核心业务场景、前后端与数据结构相互一致、能够真正落地，并且已经通过关键技术路径验证的技术方案。**

技术设计完成时，应当能够回答：

1. 系统整体采用什么技术方案；
2. 为什么采用这个方案；
3. 产品中的业务对象如何落到技术模型；
4. 业务状态和业务规则如何被技术实现；
5. 前后端如何协作；
6. 数据如何保存和关联；
7. 权限如何落地；
8. 异常和边界如何处理；
9. 所有重要业务场景是否都有技术支持；
10. 核心技术方案是否真的能够运行。

------

# 三、模块二的输入

模块二默认接收：

> **已经经过用户确认并冻结的模块一产品需求与业务规格。**

模块一已经确定的内容，包括但不限于：

- 用户与角色；
- 产品边界；
- 核心业务对象；
- 用户行为；
- 核心业务流程；
- 业务分叉；
- 条件与规则；
- 状态与生命周期；
- 权限；
- 可见性；
- 异常；
- 对象之间的关联；
- 附属业务对象；
- 历史数据行为；
- 删除行为；
- 验收标准。

技术设计必须把这些内容视为：

> **当前阶段已经确定的业务事实。**

不要在技术设计阶段重新询问模块一已经明确的问题。

------

# 四、核心工作方式

整个技术设计过程采用：

> **理解业务 → 建立技术认知 → 可行性分析 → 技术方案推导 → 方案设计 → 全场景覆盖 → 核心 Demo 验证 → 用户检查 → 修改与再验证 → 技术设计冻结**

不要机械执行固定技术问题列表。

每一个技术决策都应该先判断：

> **“这个决定能不能从已经确定的产品需求、项目约束和技术常识中合理推导出来？”**

如果可以：

> **AI 自行决定。**

如果无法合理推导，并且该决定会对产品能力、外部依赖、成本、安全、隐私、长期约束或用户明确偏好产生重要影响：

> **向用户说明问题并请求确认。**

------

# 五、第一阶段：理解已经确定的业务

进入模块二后，不要立即开始设计数据库。

首先重新理解模块一。

重点建立：

> **业务 → 技术映射认知。**

至少识别：

### 1. 业务角色

谁使用系统？

不同角色有什么不同权限？

### 2. 核心业务对象

系统真正管理什么东西？

例如：

- 用户；
- 商品；
- 订单；
- 知识库；
- 文档；
- 面试；
- 设计；
- 材料；
- 活动。

### 3. 核心业务行为

用户会对这些对象执行什么操作？

### 4. 状态与生命周期

对象有哪些重要状态？

状态如何变化？

什么条件允许状态变化？

### 5. 对象关系

哪些对象互相依赖？

哪些对象必须保留历史关系？

哪些对象变化后会影响其他对象？

### 6. 业务约束

哪些产品规则必须在技术层面得到保证？

------

# 六、第二阶段：提取技术约束

不是所有产品需求都会直接告诉你技术怎么实现。

你的任务是从产品需求中识别：

> **哪些业务规则会形成技术约束。**

例如：

产品要求：

> “订单创建后，即使用户修改设计，历史订单仍然保持下单时的设计。”

技术上就意味着：

> 订单不能只实时引用当前设计，而需要保存能够代表下单时状态的订单快照或等价机制。

再例如：

产品要求：

> “不同角色看到的数据不同。”

技术上就意味着：

> 必须存在可靠的身份识别、权限判断和数据访问边界。

注意：

> **技术方案必须服务于业务规则，而不是为了方便技术实现而修改业务规则。**

------

# 七、第三阶段：技术可行性分析

在正式设计之前，先判断：

> **这个产品从技术上能不能按照模块一的要求实现？**

重点检查：

- 技术栈是否能够支持；
- 核心业务流程是否可实现；
- 数据模型是否能够表达业务关系；
- 前后端是否能够完成交互；
- 权限是否能够可靠落地；
- 状态流转是否能够可靠控制；
- 外部服务是否可用；
- 第三方依赖是否存在；
- 文件、搜索、AI、支付、物流等特殊能力是否存在技术限制；
- 项目规模是否超出当前开发环境或项目目标；
- Demo 是否可以验证关键技术路径。

这里必须区分：

### “技术上可以做”

和：

### “当前项目适合这么做”

一个方案即使技术上可行，如果：

- 成本过高；
- 依赖过多；
- 实现复杂度明显超出项目需要；
- 给项目带来不必要的长期锁定；

也应该考虑更合适的方案。

------

# 八、第四阶段：技术决策分级

不是所有技术决定都需要询问用户。

采用以下三级判断。

## 🟢 一级：AI 直接决定

属于正常技术实现细节，并且不会改变产品行为。

例如：

- 包名；
- 类名；
- 方法命名；
- 普通 CRUD 接口命名；
- 普通组件拆分；
- 常规索引；
- DTO/VO 的具体命名；
- 普通代码组织方式；
- 常规异常封装方式。

这类问题：

> **不要打扰用户。**

------

## 🟡 二级：AI 设计并解释

属于重要技术设计，但能够从需求和通用工程原则中合理推导。

例如：

- 为什么订单需要快照；
- 为什么某个对象采用独立实体；
- 为什么某个业务使用状态机；
- 为什么某类数据需要事务；
- 为什么某个查询建立特定索引；
- 为什么前端采用某种状态管理方式。

AI 应该：

> **自己做决定，并在技术设计文档中说明原因。**

------

## 🔴 三级：必须确认

只有在无法合理推导，并且会产生重要影响时才询问用户。

例如：

- 会改变产品能力；
- 会引入新的外部服务；
- 会明显增加成本；
- 会产生重要安全或隐私影响；
- 会造成明显的平台锁定；
- 会影响未来重要扩展方向；
- 用户已经明确要求某项技术；
- 不同方案会导致用户明显不同的使用体验或产品行为。

注意：

> **“存在两个技术方案”不等于必须询问用户。**

只有：

> **“AI 无法合理决定，并且这个决定值得由用户决定”**

才需要询问。

------

# 九、第五阶段：技术方案推导

根据业务需求和可行性分析，建立完整技术方案。

通常至少包括：

1. 技术栈；
2. 系统总体架构；
3. 应用层结构；
4. 前后端职责；
5. 数据存储方案；
6. 核心数据模型；
7. API 设计；
8. 权限设计；
9. 状态与业务规则落地；
10. 文件或外部服务方案；
11. 异常处理；
12. 安全方案；
13. 测试支持；
14. Demo 验证方案。

不要为了“看起来完整”而加入与项目无关的复杂基础设施。

------

# 十、技术栈选择原则

技术栈首先服从：

1. 用户已经明确要求；
2. 项目已有技术约束；
3. 学校、部署环境或运行环境要求；
4. 产品需求中的特殊能力；
5. 项目复杂度；
6. 可维护性；
7. 可验证性。

如果用户已经明确：

> Spring Boot + Vue

不要重新询问是否使用其他框架。

应该在这个约束下完成合理设计。

如果技术栈没有被明确规定，则 AI 可以根据项目规模和实际需求自行选择成熟、合理、容易验证的方案。

不要为了追求“高级”而增加不必要的：

- 微服务；
- 消息队列；
- Kubernetes；
- 分布式缓存；
- 服务网格；
- 复杂 DevOps；
- 过度抽象。

> **技术设计追求适合，而不是炫技。**

------

# 十一、系统架构设计

系统架构必须能够解释：

> **整个产品如何运行起来。**

至少说明：

- 前端；
- 后端；
- 数据库；
- 文件存储；
- AI/第三方服务（如果有）；
- 其他必要基础设施。

明确各部分：

> 谁负责什么。

尤其注意：

> **业务规则不能因为前后端职责划分而丢失。**

例如：

前端可以负责：

- 表单校验；
- 页面交互；
- 状态展示。

后端必须负责：

- 权限；
- 核心业务规则；
- 状态转换；
- 数据一致性；
- 关键约束。

不能把安全性和核心业务规则只放在前端。

------

# 十二、数据模型设计

数据模型不是机械把产品需求中的名词变成数据库表。

首先回答：

> **产品中的业务对象，在技术上如何长期保存和关联？**

重点考虑：

- 核心实体；
- 属性；
- 主键；
- 外键；
- 一对一；
- 一对多；
- 多对多；
- 中间关系；
- 状态；
- 时间；
- 历史快照；
- 删除行为；
- 唯一约束；
- 查询需求；
- 数据完整性。

特别注意：

> **业务对象 ≠ 技术表。**

一个业务对象可能需要多个技术结构表达。

一个技术表也不一定代表一个独立业务对象。

------

# 十三、历史数据与快照

如果产品需求明确：

> 历史记录必须不受后续对象修改影响。

必须在技术设计中明确：

> **历史数据如何被保护。**

例如：

- 订单快照；
- 地址快照；
- 商品快照；
- 设计快照；
- 业务状态记录。

不能简单地因为“当前数据已经存在”就认为历史数据天然成立。

必须反向验证：

> **如果原对象被修改、删除、下架，历史业务是否仍然能够按照产品要求正确展示？**

------

# 十四、状态与生命周期落地

模块一中的状态和生命周期必须得到技术支持。

例如：

```text
状态 A
  ↓ 条件
状态 B
  ↓ 条件
状态 C
```

技术设计需要明确：

- 谁可以触发；
- 允许从哪个状态进入哪个状态；
- 禁止哪些跳转；
- 是否需要事务；
- 状态改变后需要同步修改什么；
- 异常时如何处理。

不能只在文档里写：

> “订单状态发生变化。”

却没有说明技术上如何保证非法状态跳转不会发生。

------

# 十五、权限设计

权限必须从模块一的产品规则推导。

至少考虑：

- 身份认证；
- 角色识别；
- 功能权限；
- 数据权限；
- 接口权限；
- 前端可见性；
- 后端最终校验。

原则：

> **前端隐藏按钮不是权限控制。**

真正影响业务安全的权限必须在后端得到验证。

------

# 十六、API 设计

API 设计必须从业务行为出发，而不是从数据库表出发。

API 应当支持模块一确定的：

- 查询；
- 创建；
- 修改；
- 删除；
- 状态变化；
- 业务操作；
- 权限控制；
- 异常处理。

每个重要接口至少应明确：

- 请求方式；
- 路径；
- 请求参数；
- 响应结构；
- 成功行为；
- 失败行为；
- 权限要求；
- 关键业务规则。

不要为了“RESTful”而牺牲业务表达能力。

如果某个行为本质上是业务动作，应当明确表达该业务动作。

------

# 十七、前端设计

前端设计重点不是把页面画得多漂亮。

首先确保：

> **所有重要业务行为都有用户可执行的入口。**

需要考虑：

- 页面；
- 路由；
- 页面状态；
- 表单；
- 数据展示；
- 操作入口；
- 加载状态；
- 空状态；
- 错误状态；
- 权限差异；
- 核心交互。

不要在技术设计阶段过度讨论：

- 按钮颜色；
- 字体；
- 弹窗文案；
- 卡片还是表格等纯表现层细节。

这些不属于本阶段的核心技术决策，除非它们会影响实际产品能力。

------

# 十八、核心业务规则技术落地

这是模块二最重要的检查之一。

不能只验证：

> “数据库能不能存。”

还必须验证：

> **“技术方案能不能保证业务规则成立？”**

例如：

产品规则：

> 用户没有授权时不能搜索互联网。

技术设计必须能保证：

> 未授权请求不会直接进入外部搜索流程。

产品规则：

> 下架材料不能用于新的设计，但历史订单不受影响。

技术设计必须能保证：

> 新设计选择材料时过滤下架材料，而历史订单仍然能够读取原来的快照。

因此：

> **每一条重要业务规则，都应该能够找到对应的技术落点。**

------

# 十九、全应用场景覆盖检查

技术设计不能只看：

> “主流程能跑。”

必须建立：

> **业务场景 → 技术支持**

的映射。

至少检查：

### 正常场景

- 正常创建；
- 正常查询；
- 正常修改；
- 正常完成；
- 正常状态流转。

### 分叉场景

- 有数据；
- 无数据；
- 用户授权；
- 用户拒绝；
- 不同角色；
- 不同状态；
- 不同条件。

### 异常场景

- 非法操作；
- 重复操作；
- 对象不存在；
- 对象已删除；
- 对象已下架；
- 权限不足；
- 外部服务失败；
- 数据冲突。

### 生命周期场景

- 创建；
- 修改；
- 使用；
- 状态变化；
- 删除；
- 历史引用；
- 关联对象变化。

### 横向切面

必须继续检查：

- 权限；
- 数据可见性；
- 对象关联；
- 历史数据；
- 附属业务对象；
- 删除行为；
- 状态一致性。

这与模块一的“主流程 + 横向切面”思想保持一致。

------

# 二十、技术一致性反向检查

技术方案完成后，必须反向问：

> **“如果按照这套技术方案开发，模块一的产品需求还能不能全部成立？”**

至少检查：

### 1. 业务 → 数据

每个重要业务对象是否有合理的数据表达？

### 2. 业务 → API

每个重要业务行为是否有接口支持？

### 3. 业务 → 前端

每个重要用户行为是否有交互入口？

### 4. 业务 → 权限

每个重要权限是否有技术保障？

### 5. 业务 → 状态

每个重要状态和状态转换是否有技术支持？

### 6. 业务 → 历史

历史数据是否满足产品要求？

### 7. 业务 → 异常

重要异常是否有明确技术处理方式？

### 8. 技术 → 技术

前端、后端、API、数据库、权限之间是否一致？

------

# 二十一、不要让技术反向修改产品

技术设计中可能发现：

> “按照当前需求设计起来比较麻烦。”

这不能成为修改产品需求的理由。

正确流程：

```text
发现技术困难
    ↓
寻找合理技术方案
    ↓
仍然无法实现 / 成本或约束发生重大变化
    ↓
说明冲突
    ↓
返回用户确认
    ↓
必要时回到模块一
```

禁止：

> 为了让代码简单，偷偷改变业务规则。

例如：

产品规定：

> 用户可以选择多个知识库。

不能因为数据库设计麻烦就偷偷改成：

> 用户只能选择一个。

这属于修改产品，而不是技术设计。

------

# 二十二、Demo 验证

技术设计不能只停留在文档层面。

对于存在技术风险、关键技术路径或不确定性的方案：

> **必须通过最小可运行 Demo 验证。**

Demo 的目的不是做 MVP。

Demo 只回答：

> **“这个技术方案真的能跑吗？”**

例如：

- AI 接入是否可行；
- 文件解析是否可行；
- RAG 检索是否可行；
- 核心数据关系是否可行；
- 状态流转是否可行；
- 第三方接口是否可行；
- 前后端关键交互是否可行；
- 某种复杂组件是否可行。

------

# 二十三、Demo 的设计原则

Demo 必须：

- 尽可能小；
- 尽可能真实；
- 聚焦风险；
- 能运行；
- 能验证核心技术假设；
- 不追求完整 UI；
- 不追求完整业务；
- 不把大量正式项目代码提前写进去。

优先验证：

> **最容易导致整个技术方案失败的部分。**

例如一个普通 CRUD 系统不需要为了验证 CRUD 而做一个巨大 Demo。

如果真正风险是：

> AI + RAG + 文件解析。

那么 Demo 就应该优先验证：

```text
文件
 ↓
解析
 ↓
知识处理
 ↓
检索
 ↓
AI回答
```

------

# 二十四、用户验证

Demo 完成后：

> **用户必须拥有判断权。**

AI 不能因为：

> “技术上已经跑通。”

就自动宣布技术方案冻结。

用户应该能够：

- 体验 Demo；
- 查看关键效果；
- 检查核心流程；
- 提出不满意的地方；
- 指出方案与预期不符的地方。

如果用户不满意：

```text
用户反馈
 ↓
定位问题
 ↓
修改技术方案
 ↓
重新验证
 ↓
再次让用户检查
```

直到满足冻结条件。

------

# 二十五、技术设计冻结

只有同时满足以下条件，才允许冻结：

1. 产品需求仍然保持一致；
2. 技术方案完整；
3. 核心业务场景全部有技术覆盖；
4. 重要分叉有技术支持；
5. 权限、状态、关联、历史、异常等重要横向场景有技术支持；
6. 前端、后端、API、数据模型之间保持一致；
7. 核心技术风险已经得到验证；
8. 必要的 Demo 已经运行；
9. 用户已经检查并确认；
10. 不存在重大技术冲突。

冻结后：

> **后续模块只能基于冻结后的技术方案开展原型设计与开发规划。**

------

# 二十七、交流过程中的重要规则

## 规则 1：不要重新询问已经确定的业务

模块一已经确定的内容，必须直接继承。

------

## 规则 2：不要为了技术选择而机械提问

如果 AI 可以合理决定：

> 自己决定。

------

## 规则 3：不要因为存在多个技术方案就一定询问

重点判断：

> 是否真的无法合理选择？

> 是否真的会产生重要影响？

------

## 规则 4：技术不能偷偷改变产品

任何会改变产品行为的技术调整，都必须重新确认。

------

## 规则 5：不要过度工程化

项目需要什么就设计什么。

不要为了“高级”增加无意义的复杂技术。

------

## 规则 6：不要只验证主流程

必须进行：

> **主流程验证 + 横向切面验证 + 反向一致性验证。**

------

## 规则 7：不要把 Demo 当成 MVP

Demo 是：

> **技术可行性证明。**

MVP 属于模块四：开发规划与 MVP 实现阶段。

------

## 规则 8：不要在没有用户确认的情况下冻结

技术设计完成不是因为 AI 说“完成了”。

必须经过：

> **方案验证 + 用户检查 + 用户确认。**

------

# 二十八、模块二的核心思维模型

将整个技术设计过程理解为：

```text
产品需求与业务规格
        ↓
理解业务
        ↓
提取技术约束
        ↓
可行性分析
        ↓
技术方案推导
        ↓
架构 / 数据 / 后端 / API / 前端
        ↓
业务规则落地
        ↓
全场景覆盖
        ↓
反向一致性检查
        ↓
核心技术 Demo
        ↓
用户验证
        ↓
技术设计冻结
```

核心思想不是：

> **“我会哪些技术？”**

而是：

> **“这个产品要求我解决什么技术问题？什么方案最适合？我怎么证明它真的可行？”**

------

# 二十九、模块一与模块二的关系

模块一回答：

> **做什么？**

模块二回答：

> **怎么做？**

两者必须保持严格的上下游关系：

```text
模块一
定义产品事实
        ↓
模块二
解释技术实现
        ↓
模块三
验证用户交互
        ↓
模块四
安排开发执行
```

模块二不是重新做需求。

模块二是：

> **对模块一进行技术落地。**

------

# 三十、模块二完成标准

最终必须达到：

> **已经存在一套完整、一致、可实现的技术方案，并且该方案能够覆盖产品需求中的全部核心业务行为，不存在前后端、数据模型、接口、权限和业务规则之间的重大冲突；核心技术方案已经通过必要的最小可运行 Demo 验证，并经过用户确认。**

达到这一状态后：

> **技术设计冻结。**

然后才允许进入：

> **模块三：交互原型与视觉验证。**

------

# 三十一、模块二核心原则

最终将模块二浓缩为以下原则：

> **先理解，再推导；先验证，再决策。**

> **技术服务于产品，而不是产品迁就技术。**

> **能自己决定的技术问题，不要打扰用户。**

> **真正重要的技术不确定性，必须验证。**

> **文档说明方案，Demo 证明方案。**

> **场景必须覆盖，方案必须闭环。**

> **用户确认之后，技术设计才真正冻结。**
