# 一、Reference 的定位

## 1. Skill 与 Reference 的区别

### Skill

Skill 负责规定：

> **AI 应该怎么工作。**

例如：

- 先理解业务；
- 再进行技术推导；
- 能自己决定的问题不要询问用户；
- 重要技术风险需要验证；
- Demo 验证之后才能冻结；
- 技术不能偷偷修改产品。

------

### Reference

Reference 负责提供：

> **AI 可以参考什么。**

例如：

- 常见架构设计方式；

- API 设计经验；
- 状态机设计经验；

- 权限设计；

- 测试与验收；
- 实际项目案例。

因此：

> **Skill 是行为规则，Reference 是经验知识。**

# 二、技术设计最重要的目标

技术设计最终不是为了：

> “让项目看起来用了很多技术。”

而是为了：

> **让产品需求能够稳定、完整、一致地落地。**

技术设计应该最终形成：

```text
产品需求
    ↓
业务行为
    ↓
技术方案
    ↓
数据
    ↓
API
    ↓
后端
    ↓
前端
    ↓
用户操作
```

整个链路必须闭环。

------

# 三、案例：徽游安徽项目

本 Reference 的第一批经验主要来源于：

> **《徽游安徽_安徽旅游信息管理系统_完整项目规格书》**

该项目的规格已经形成了比较完整的：

```text
产品
+
页面
+
API
+
后端
+
数据库
+
业务流程
+
权限
+
测试
+
验收
```

这样的全栈设计结构。其最终要求明确提出：

> 前端页面、后端接口、数据库实体、业务流程、权限体系必须完全对应。

并明确禁止出现：

- 页面有功能但没有接口；
- 接口有数据但页面没有展示；
- 数据库有字段但前端无法编辑；
- 接口没有权限控制；
- 订单状态与库存状态不一致；
- 前端 Mock 与真实 API 数据结构不一致。

这类经验具有很强的通用性，因此可以沉淀到技术设计 Reference 中。

------

# 四、技术栈选择经验

## 4.1 技术栈不是越多越好

技术栈选择应该服从：

1. 产品需求；
2. 用户指定技术；
3. 项目规模；
4. 开发环境；
5. 部署条件；
6. 学习成本；
7. 可维护性；
8. 可验证性。

------

## 4.2 典型全栈项目技术组合

徽游安徽项目采用了：

```text
前端：
Vue 3
Vite
Vue Router
Pinia
Element Plus
Axios

后端：
Spring Boot
MyBatis-Plus
JWT
Bean Validation

数据库：
H2
```

这种组合的价值不在于“这些技术一定是最好的”。

真正值得学习的是：

> **技术栈应该形成一个完整且容易验证的技术闭环。**

即：

```text
Vue
 ↓
Axios
 ↓
Spring Boot API
 ↓
Service
 ↓
MyBatis-Plus
 ↓
H2
```

而不是单独罗列一堆技术名称。

------

# 五、架构设计经验

## 5.1 前后端职责需要清晰

典型结构：

```text
前端
 ↓
Controller
 ↓
Service
 ↓
Mapper
 ↓
Database
```

其中：

### 前端

负责：

- 页面；
- 用户交互；
- 表单；
- 状态展示；
- API 调用。

### Controller

负责：

- HTTP 请求；
- 参数接收；
- 权限入口；
- 返回 API 响应。

### Service

负责：

- 核心业务逻辑；
- 状态变化；
- 业务规则；
- 事务；
- 多对象协作。

### Mapper / Repository

负责：

- 数据访问；
- 查询；
- 持久化。

### Database

负责：

- 数据持久化；
- 数据完整性；
- 关系和约束。

------

# 六、不要让 Controller 承担所有业务

一个常见问题：

```text
Controller
    ↓
查询数据库
    ↓
计算业务
    ↓
修改状态
    ↓
扣库存
    ↓
创建订单
```

这样会导致业务逻辑越来越混乱。

更合理的思路：

```text
Controller
    ↓
Service
    ↓
业务规则
    ↓
数据访问
```

Controller 主要负责：

> **请求进入系统。**

Service 负责：

> **业务真正发生。**

------

# 七、DTO / VO 经验

不要简单地：

> 数据库 Entity = API 请求 = API 响应。

实际项目中可以进行分离：

```text
Entity
 ↓
数据库模型

DTO
 ↓
请求模型

VO
 ↓
响应模型
```

这样可以避免：

- 数据库结构直接暴露；
- 前端请求直接绑定数据库实体；
- 后续数据库变化影响 API；
- 不应该返回的数据被返回。

------

# 八、数据模型设计经验

## 8.1 不要从“表”开始思考

应该从：

> **业务对象**

开始。

例如旅游项目中存在：

```text
景点
票种
订单
用户
收藏
核销
```

然后再推导：

```text
业务对象
 ↓
关系
 ↓
数据模型
 ↓
数据库表
```

而不是：

```text
我需要几个页面？
 ↓
随便建几个表
```

------

# 九、业务对象关系必须明确

例如：

```text
景点
 ↓
票种
 ↓
订单
 ↓
核销
```

这不是简单的四张表。

真正应该理解为：

> 用户购买的是某个景点下的某种票，形成订单，订单产生核销凭证，最终完成核销。

因此数据库设计必须能够表达：

```text
用户
 ↓
订单
 ↓
票种
 ↓
景点
```

以及：

```text
订单
 ↓
核销码
 ↓
核销记录 / 核销状态
```

------

# 十、历史数据设计

一个非常重要的经验：

> **历史业务不能依赖会随时间变化的当前对象。**

例如订单创建时：

```text
商品名称
商品价格
地址
设计内容
```

这些信息未来可能发生变化。

如果订单只保存：

```text
product_id
address_id
design_id
```

那么以后：

```text
商品修改
地址修改
设计修改
```

可能导致历史订单展示发生变化。

因此需要考虑：

> **快照。**

例如：

```text
订单
 ├── 商品快照
 ├── 价格快照
 ├── 地址快照
 └── 业务对象快照
```

核心原则：

> **历史业务记录应该保留“当时发生了什么”，而不是只保存“现在是什么”。**

------

# 十一、状态机设计经验

很多系统的核心并不是 CRUD，而是：

> **状态变化。**

例如订单：

```text
待支付
 ↓
待使用
 ↓
已使用
 ↓
已完成
```

或者：

```text
待支付
 ↓
已取消
```

技术设计必须考虑：

### 谁可以改变状态？

### 什么条件允许改变？

### 哪些状态不能直接跳转？

### 状态改变后需要同步修改什么？

------

# 十二、状态不能只靠前端控制

错误方式：

```text
前端：
如果订单是待支付
    显示支付按钮
```

然后后端完全不检查。

用户完全可以直接调用 API。

正确方式：

```text
前端控制
+
后端状态验证
```

后端必须最终判断：

```text
当前状态
+
请求动作
+
用户权限
+
业务条件
```

是否允许发生。

------

# 十三、订单设计经验

徽游安徽案例中，订单创建不是简单：

```text
INSERT order
```

而是：

```text
1. 检查用户是否登录
2. 检查景点是否存在
3. 检查票种是否存在
4. 检查票种是否上架
5. 检查库存
6. 检查游玩日期
7. 计算订单金额
8. 创建订单
9. 扣减 / 锁定库存
10. 生成订单编号
11. 生成核销码
```

这体现出一个非常重要的技术设计思想：

> **一个业务动作往往对应多个技术步骤。**

因此：

> 不要把业务行为机械等同于数据库 CRUD。



------

# 十四、事务设计经验

当一个业务动作同时修改多个关键数据时，需要考虑事务。

例如：

```text
创建订单
+
扣减库存
+
生成核销码
```

如果：

```text
订单创建成功
库存扣减失败
```

就可能出现数据不一致。

因此需要根据具体业务判断：

> **哪些操作必须保持原子性。**

核心思想：

```text
业务动作
 ↓
多个数据变化
 ↓
必须保证一致性
```

而不是：

> 只要用了数据库，就自动安全。

------

# 十五、库存设计经验

库存类业务特别容易产生并发问题。

基本逻辑可能是：

```text
购买：
库存 - 购买数量

取消：
库存 + 购买数量

退款：
库存 + 购买数量
```

但真正设计时还必须继续考虑：

- 重复取消；
- 重复退款；
- 并发购买；
- 库存不足；
- 已核销是否允许退款；
- 退款后是否恢复库存；
- 订单状态与库存状态是否一致。

徽游安徽案例明确规定：

> 已经核销的订单不可退款。

因此：

> **库存规则必须和订单状态、退款规则、核销规则一起设计。**

------

# 十六、幂等设计

订单等核心业务必须考虑：

```text
重复点击
重复请求
网络重试
```

例如用户点击：

> “立即购买”

可能因为网络问题连续发送两次请求。

如果后端没有防护：

```text
请求 1 → 创建订单
请求 2 → 再创建一个订单
```

因此需要考虑：

> **幂等机制。**

常见思路：

```text
requestId
```

或者其他后端幂等机制。

徽游安徽项目也明确提出订单创建应考虑这些情况。

------

# 十七、业务操作的“重复执行”检查

所有具有副作用的业务动作都应该考虑：

> **如果用户执行两次会怎么样？**

例如：

- 重复支付；
- 重复取消；
- 重复退款；
- 重复核销；
- 重复收藏；
- 重复提交；
- 重复领取；
- 重复发货。

不能只设计：

> 第一次执行怎么办？

还必须考虑：

> 第二次执行怎么办？

------

# 十八、核销类业务经验

核销码这类业务具有明显的“一次性”特点。

必须考虑：

```text
唯一
不可重复使用
核销后状态改变
已核销不能再次核销
```

同时需要处理：

```text
核销码不存在
核销码已使用
订单已取消
订单已退款
订单日期无效
```

这说明：

> **业务动作设计必须同时包含成功条件与拒绝条件。**



------

# 十九、API 设计经验

API 应当围绕：

> **业务行为**

设计。

而不是：

> **数据库表**

设计。

例如不要机械地认为：

```text
每张表
↓
GET
POST
PUT
DELETE
```

然后结束。

真正需要考虑：

```text
用户想做什么？
 ↓
业务动作是什么？
 ↓
需要哪些数据？
 ↓
业务条件是什么？
 ↓
API 如何表达？
```

------

# 二十、统一响应结构

实际项目中可以使用统一 API 响应结构。

例如：

```json
{
  "code": 200,
  "message": "success",
  "data": {}
}
```

失败：

```json
{
  "code": 400,
  "message": "具体错误信息",
  "data": null
}
```

其价值在于：

> **让前端面对统一的数据协议。**

------

# 二十一、统一异常处理

不要把 Java StackTrace 直接返回给前端。

后端应该：

```text
异常
 ↓
统一异常处理
 ↓
业务错误结构
 ↓
前端
```

例如：

```json
{
  "code": 400,
  "message": "库存不足",
  "data": null
}
```

而不是把：

```text
NullPointerException
at xxx.java:123
```

直接返回给用户。

徽游安徽案例明确提出了统一异常返回机制。

------

# 二十二、前端 API 封装经验

前端不应该每个页面自己处理：

```text
axios
token
401
错误
token过期
```

可以统一封装请求层。

例如：

```text
src/api/request.js
```

统一处理：

```text
JWT
401
错误
Token 过期
响应数据
```

然后业务 API 再按照模块拆分：

```text
api/
├── auth.js
├── spot.js
├── route.js
├── order.js
├── favorite.js
└── ...
```

这种结构可以让：

> **页面 → API → 后端**

保持清晰。

------

# 二十三、前端 Mock 经验

如果项目在开发阶段使用 Mock：

必须保证：

> **Mock API 与真实 API 使用相同的数据结构。**

例如真实 API：

```json
{
  "code": 200,
  "data": {
    "name": "黄山"
  }
}
```

Mock 也应该保持一致。

否则：

```text
Mock 能运行
 ↓
接真实后端
 ↓
页面全部报错
```

因此：

> **Mock 不是随便模拟数据，而应该模拟真实接口协议。**

徽游安徽案例明确要求 Mock 返回结构与真实 API 保持一致。

------

# 二十四、前端页面设计经验

技术设计阶段需要保证：

> **业务功能都有页面入口。**

例如：

```text
首页
 ↓
景点
 ↓
详情
 ↓
购票
 ↓
订单
 ↓
支付
 ↓
核销
```

页面不能只存在视觉设计，而没有后端能力。

------

# 二十五、Loading / Empty / Error

一个完整前端页面至少需要考虑：

```text
正常状态
Loading
Empty
Error
```

例如：

### Loading

数据还没有返回。

### Empty

查询成功，但是没有数据。

### Error

请求失败。

这三种情况不能混为一谈。

徽游安徽最终验收中也明确检查：

- Loading；
- Empty；
- Error；
- 登录状态；
- Token；
- 权限；
- 响应式。

------

# 二十六、权限设计经验

权限至少分成：

```text
身份认证
+
角色权限
+
接口权限
+
数据访问权限
```

例如：

```text
普通用户
    ↓
只能访问自己的订单

管理员
    ↓
可以管理全部订单
```

前端可以：

```text
隐藏管理员按钮
```

但是：

> **真正的权限必须由后端保证。**

------

# 二十七、权限与页面必须一致

不能出现：

```text
页面：
管理员可以核销

API：
任何登录用户都能调用核销接口
```

正确关系应该是：

```text
页面权限
     ↓
API 权限
     ↓
Service 权限
     ↓
数据权限
```

最终由后端保证。

------

# 二十八、业务规则必须有技术落点

一个非常重要的检查方式：

> **每一条重要业务规则，都必须能够找到技术实现。**

例如：

产品要求：

> 已核销订单不能退款。

那么技术设计中必须出现：

```text
退款接口
 ↓
查询订单状态
 ↓
如果已核销
 ↓
拒绝退款
```

不能只在产品需求里写：

> “已核销不可退款。”

而技术设计完全不管。

------

# 二十九、业务规则 → 技术约束

推荐使用以下思考方式：

```text
业务规则
 ↓
会产生什么约束？
 ↓
哪个技术层负责保证？
```

例如：

| 业务规则                 | 技术约束               |
| ------------------------ | ---------------------- |
| 已核销不能退款           | Service 校验状态       |
| 管理员才能核销           | 后端权限               |
| 订单历史不能变化         | 快照                   |
| 库存不能小于 0           | 数据 + 业务约束        |
| 重复提交不能重复创建订单 | 幂等                   |
| 下架票种不能购买         | API / Service 检查状态 |

------

# 三十、全链路一致性

这是徽游安徽项目中非常值得沉淀的一条经验。

最终必须检查：

```text
产品
 ↓
页面
 ↓
API
 ↓
Controller
 ↓
Service
 ↓
Entity
 ↓
Database
```

每一层都必须对应。

不能出现：

```text
页面有功能
但没有 API

API 有数据
但页面没有使用

数据库有字段
但业务无法修改

接口存在
但没有权限

订单状态
和库存状态不一致
```

这种检查比单独检查某一层更重要。



------

# 三十一、不要只做 Happy Path

技术验证不能只测试：

```text
正常登录
 ↓
正常购买
 ↓
正常完成
```

还应该检查：

```text
重复提交
无权限
数据不存在
状态错误
库存不足
对象已删除
对象已下架
网络失败
外部服务失败
```

原则：

> **真正容易出问题的地方，往往不是正常流程，而是分叉和异常。**

------

# 三十二、测试应该覆盖多个层面

完整项目的测试不应该只有：

> “网页点起来没问题。”

可以至少分为：

## 数据层

检查：

- 数据表；
- Entity；
- Mapper；
- Service；
- 关联关系；
- 初始化数据。

## API

检查：

- REST API；
- 参数验证；
- JWT；
- ADMIN 权限；
- 错误处理；
- 分页；
- 搜索。

## 前端

检查：

- API 连接；
- Loading；
- Empty；
- Error；
- 登录；
- Token；
- 权限；
- 响应式。

## 业务

检查完整业务链路：

```text
登录
注册
浏览
搜索
详情
路线
收藏
购票
订单
支付
取消
退款
核销
后台管理
统计
```

徽游安徽项目的验收标准正是按照类似层次组织的。

------

# 三十三、技术验收不是页面验收

错误：

> 页面能打开，所以项目完成。

正确：

```text
页面
+
API
+
数据库
+
权限
+
业务规则
+
状态
+
异常
+
完整流程
```

全部通过。

------

# 三十四、启动与运行能力也是技术设计的一部分

一个项目即使代码正确，如果：

> 很难启动、很难演示、环境很难配置。

对于实际项目而言依然存在问题。

因此技术设计可以考虑：

```text
一键启动
+
手动启动
+
默认端口
+
数据库配置
+
前端代理
+
演示账号
```

例如徽游安徽项目提供：

```text
start.bat
start.sh
start.ps1
```

以及前后端启动方式和默认端口。

这类经验适合沉淀为：

> **项目可运行性也是工程质量的一部分。**

------

# 三十五、Demo 验证经验

Demo 不需要把整个项目做出来。

它应该回答：

> **最重要的技术风险是否成立？**

例如：

```text
风险：
RAG 能不能工作？

Demo：
文件
 ↓
解析
 ↓
向量化
 ↓
检索
 ↓
AI
```

而不是：

```text
先做完整首页
先做登录
先做所有 CRUD
最后才发现核心技术不可行
```

------

# 三十六、优先验证高风险技术

可以按照：

```text
技术风险
×
失败影响
```

决定 Demo 优先级。

例如：

| 技术问题     | 风险 | 是否值得优先 Demo |
| ------------ | ---- | ----------------- |
| 普通 CRUD    | 低   | 通常不需要        |
| 普通分页     | 低   | 通常不需要        |
| JWT 登录     | 中   | 可快速验证        |
| 文件解析     | 中高 | 建议验证          |
| RAG          | 高   | 强烈建议验证      |
| 第三方支付   | 高   | 建议验证          |
| 地图路线 API | 高   | 建议验证          |
| 复杂编辑器   | 高   | 建议验证          |

------

# 三十七、技术方案的风险记录

对于重要技术决策，可以记录：

```text
技术问题
 ↓
候选方案
 ↓
选择方案
 ↓
选择原因
 ↓
风险
 ↓
验证方式
 ↓
验证结果
```

这样以后出现问题时，可以知道：

> 当时为什么这么设计。

------

# 三十八、不要为了“高级”而复杂化

常见过度设计：

```text
单体项目
→ 微服务

普通数据库
→ 分布式数据库

简单查询
→ Elasticsearch

简单异步任务
→ 消息队列

小型项目
→ Kubernetes
```

这些技术本身没有问题。

问题在于：

> **它们是否真的解决了当前项目的问题？**

如果没有：

> 不要加入。

------

# 三十九、技术复杂度应该与项目复杂度匹配

可以使用一个简单判断：

```text
项目复杂度
    ↓
业务复杂度
    ↓
数据复杂度
    ↓
并发复杂度
    ↓
外部依赖复杂度
    ↓
选择技术复杂度
```

不要反过来：

```text
我会某个高级技术
 ↓
项目一定要用
```

------

# 四十、技术设计中的常见错误

## 错误 1：从数据库开始设计

错误：

> 先建表，再想业务。

正确：

> 先理解业务，再设计数据。

------

## 错误 2：把 CRUD 当成业务设计

错误：

> 有订单表，所以有增删改查。

正确：

> 订单有哪些业务动作？每个动作有什么条件？

------

## 错误 3：只设计成功路径

错误：

> 用户正常购买。

正确：

> 正常购买 + 库存不足 + 重复提交 + 状态异常 + 权限不足。

------

## 错误 4：前端承担权限

错误：

> 管理员按钮隐藏了，所以安全。

正确：

> 后端必须验证权限。

------

## 错误 5：历史数据直接引用当前对象

错误：

> 订单直接读取当前商品。

正确：

> 根据业务需求保存历史快照。

------

## 错误 6：忽略幂等

错误：

> 用户点击一次就好了。

正确：

> 如果点击三次呢？

------

## 错误 7：Mock 与真实 API 不一致

错误：

> Mock 随便返回一个对象。

正确：

> Mock 严格模拟真实 API 协议。

------

## 错误 8：Demo 做成半个项目

错误：

> 为了验证一个技术点，先开发几十个页面。

正确：

> Demo 只验证关键技术风险。

------

# 四十一、技术设计检查清单

在技术设计完成后，可以进行以下检查。

## 架构

-  前后端职责清晰
-  后端分层合理
-  技术栈与项目规模匹配
-  没有明显过度设计

## 数据

-  所有核心业务对象有合理技术表达
-  关系正确
-  状态正确
-  历史数据行为正确
-  删除行为正确
-  必要约束存在

## API

-  所有核心业务行为有 API
-  参数完整
-  返回结构明确
-  权限明确
-  异常明确
-  幂等问题已考虑

## 后端

-  核心业务逻辑在 Service
-  权限由后端保证
-  状态转换有约束
-  关键操作考虑事务
-  异常统一处理

## 前端

-  所有重要业务行为都有入口
-  API 对接正确
-  Loading 完整
-  Empty 完整
-  Error 完整
-  权限展示合理

## 一致性

-  产品与技术一致
-  数据与 API 一致
-  API 与前端一致
-  状态与业务规则一致
-  权限与角色一致
-  Mock 与真实 API 一致

## 验证

-  核心技术风险已经识别
-  必要 Demo 已验证
-  正常流程已验证
-  分支流程已验证
-  异常流程已验证
-  用户已经检查

# 四十二、技术设计的经验性思维模型

可以把技术设计理解成：

```text
业务对象
 ↓
业务行为
 ↓
业务规则
 ↓
技术约束
 ↓
数据模型
 ↓
API
 ↓
后端
 ↓
前端
 ↓
测试
 ↓
验证
```

如果某一步断了：

```text
业务
 ↓
技术
 ✕
```

就说明设计还没有闭环。

# 四十三、来自徽游安徽案例的核心经验总结

从《徽游安徽》项目规格中，最值得沉淀的并不是：

> “这个项目用了什么技术。”

而是：

### 经验 1

> **产品、页面、API、数据库、业务流程、权限必须形成对应关系。**

### 经验 2

> **复杂业务不能只设计 CRUD，需要设计业务动作。**

### 经验 3

> **订单、库存、退款、核销等业务必须联合设计。**

### 经验 4

> **存在副作用的业务操作必须考虑重复执行。**

### 经验 5

> **历史业务需要考虑快照和数据稳定性。**

### 经验 6

> **API 需要统一协议和异常结构。**

### 经验 7

> **Mock 必须和真实 API 保持一致。**

### 经验 8

> **测试需要覆盖数据、API、前端和完整业务链路。**

### 经验 9

> **项目是否能够快速启动和演示，也是工程设计的一部分。**

### 经验 10

> **最终验收应该检查整个系统，而不是只检查页面。**

# 四十六、核心原则

最终将本 Reference 的思想浓缩为：

> **技术不是技术名词的堆积，而是业务规则的落地。**

> **不要从数据库开始理解系统，要从业务行为开始理解系统。**

> **一个业务动作往往对应多个技术动作。**

> **状态、权限、历史、异常和幂等，是技术设计的重要组成部分。**

> **前端、API、后端、数据库必须形成完整闭环。**

> **正常流程能跑，不代表技术方案完整。**

> **高风险技术应该优先验证。**

> **Mock 应该模拟真实系统，而不是制造另一套系统。**

> **测试应该验证整个业务链路，而不是只验证页面。**

> **技术复杂度应该与业务复杂度匹配。**

> **真正成熟的技术设计，是能够被开发、能够运行、能够验证，并且能够解释为什么这样设计。**

# 四十八、最终总结

模块二的完整体系现在可以理解为：

```text
模块二 Skill
        │
        │
        ├── 规定 AI 怎么做技术设计
        │
        ↓
模块二 Reference
        │
        │
        ├── 提供技术设计经验
        ├── 提供案例
        ├── 提供检查方法
        ├── 提供常见问题
        └── 提供技术决策参考
        │
        ↓
实际项目
        │
        ↓
项目复盘
        │
        ↓
新的技术经验
        │
        └────────→ 回到 Reference
```

因此：

> **Skill 负责稳定。**

> **Reference 负责成长。**

而模块二真正想建立的能力是：

> **让 AI 不只是“会写代码”，而是能够从已经确定的产品需求出发，理解业务、推导技术方案、识别技术风险、验证关键路径，并最终形成一套真正能够落地的技术设计。**

这一版我特意没有把《徽游安徽》里的**具体旅游业务**硬塞进来，而是把它里面比较成熟的技术设计经验抽出来了。比如订单创建的多步骤校验、库存与退款联动、核销码的一次性约束、幂等、统一异常、Mock/真实 API 一致性，以及最后那套“数据层 → API → 前端 → 业务”的验收思路，都是很适合长期留在 Reference 里的东西。
