# 0. AI 接续与防幻觉规则

## 0.1 接手项目后的基本规则

AI 接手项目后，必须首先阅读本文件，确认项目当前状态，再决定下一步工作。

AI 不得仅依据自身常识、经验、类似项目经验或猜测，将项目中不存在或尚未确认的信息视为项目事实。

如果本文件无法确定某项信息，AI 应继续查找对应项目产物；如果项目产物仍无法确定，则必须将其视为未知或待确认事项，不得自行补充。

---

## 0.2 信息可信等级

项目中的信息分为以下三种状态。

### 🟢 已确认

满足以下任一条件：

- 用户明确确认；
- 已完成并冻结的阶段产物明确规定；
- 项目已经产生明确且可验证的最终实现事实。

已确认内容可以作为后续工作的依据。

---

### 🟡 待确认

表示：

- 已经提出；
- 已经讨论；
- 存在候选方案；
- AI 已经提出建议；
- 但尚未得到最终确认。

待确认内容不得被 AI 自动升级为已确认事实。

---

### 🔴 AI 推测

表示：

- AI 根据上下文进行的推断；
- 尚未得到用户确认；
- 尚未被正式项目产物确认。

AI 推测不得写入“已确认事实”。

---

## 0.3 禁止自行假设

AI 不得自行假设以下内容：

- 用户尚未确认的业务规则；
- 用户尚未确认的产品能力；
- 用户尚未确认的业务分支；
- 会改变产品行为的业务规则；
- 尚未确认的权限规则；
- 尚未确认的数据生命周期；
- 尚未确认的关键技术决策；
- 尚未确认的外部服务依赖；
- 尚未确认的成本相关决策；
- 尚未确认的隐私与安全规则；
- 任何可能导致不同产品行为的重大歧义。

如果某项内容必须确定才能继续工作，应将其记录为“待确认事项”，并根据总控 Skill 判断是否需要返回对应模块。

---

## 0.4 信息来源原则

重要信息应尽可能记录来源。

允许的来源包括：

- 用户明确确认
- 模块一：需求规划
- 模块二：技术设计
- 模块三：交互原型与视觉验证
- 模块四：开发规划与 MVP 实现
- 项目正式产物
- 当前 Git 版本
- 当前对话

如果信息没有明确来源，不得将其自动视为已确认事实。

---

## 0.5 状态冲突处理

如果出现以下情况：

- 项目状态与项目产物冲突；
- 不同阶段项目产物之间冲突；
- 当前代码与技术设计冲突；
- 当前实现与原型行为冲突；
- Git 中的实际实现与项目状态不一致；

AI 不得自行选择其中一个作为正确答案。

必须：

1. 识别冲突；
2. 明确冲突内容；
3. 判断冲突所属阶段；
4. 根据总控 Skill 判断问题归属；
5. 必要时返回对应模块；
6. 重新确认或修改；
7. 重新冻结相关阶段；
8. 更新本文件；
9. 根据实际情况提交 Git。

# 14. 项目状态维护规则

1. 项目状态必须始终反映项目当前有效状态。
2. AI 不得将推测写成已确认事实。
3. AI 不得删除未决事项来掩盖不确定性。
4. AI 不得因为“常见做法”而自动补充项目需求。
5. 阶段完成不等于阶段冻结。
6. 阶段冻结必须有明确依据。
7. 后续阶段不得直接修改前置阶段的冻结事实。
8. 如果确实需要修改前置阶段，必须通过总控 Skill 进入回退与重新确认流程。
9. 重要项目变更必须记录。
10. 重要项目变更应尽可能关联 Git Commit。
11. 项目状态不记录完整聊天历史。
12. 项目状态只保留下一位 AI 继续工作所必须的信息。
13. 详细业务、技术、原型和开发内容应保存在对应项目产物中。
14. 项目状态与项目产物发生冲突时，不得自行猜测解决。
15. Git 用于记录项目历史，项目状态.md 用于记录当前有效状态。
16. 项目状态.md 本身属于项目的一部分，应纳入 Git 管理。
17. 完成具有明确边界的有效工作单元后，应根据项目实际情况更新项目状态。
18. 对具有明确边界且已经验证的有效工作单元，应进行 Git Commit。
19. 不应因为普通聊天、临时思考或未完成的修改频繁创建无意义的 Commit。
20. Git Commit 应尽可能能够表达一个清晰、可回溯的项目变化。
21. AI 换人时，不得依赖完整聊天记录才能理解项目。
22. 项目状态、项目产物和 Git 应共同构成项目的主要可追溯信息来源。
