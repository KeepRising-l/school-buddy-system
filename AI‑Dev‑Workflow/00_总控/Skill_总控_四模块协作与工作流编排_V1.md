# Skill：总控——四模块协作与工作流编排 V1

> **本 Skill 采用分层加载：接手项目时只需先阅读本摘要与项目状态.md；执行到具体环节时，再按章节索引深入阅读对应规则。**

## 0. 执行摘要（必读）

### 总控是什么

> **总控负责管流程，模块负责干活。**

总控是流程编排与状态控制层，不做需求分析、技术设计、原型和编码等专业工作。

### 核心工作循环

```text
读取项目状态
    ↓
确认当前阶段与冻结状态
    ↓
确定当前工作单元
    ↓
调用对应模块 Skill 执行工作
    ↓
验证结果
    ↓
更新项目状态 → 必要时 Git Commit
```

### 十条铁律

1. 不读项目状态，不开始工作；
2. 前置阶段未冻结，不进入下一阶段；
3. 完成 ≠ 冻结，冻结必须经用户显式确认（第 22 节）；
4. 后续模块不得无意识修改前置阶段的冻结结果；
5. 问题按「改变哪一层事实」归属模块，不看在哪发现（第 15 节）；
6. 回退是正常机制，不是流程失败；
7. 不知道就记录待确认，不用猜测填空；
8. 能自己决定的不打扰用户，会改变产品行为的必须确认；
9. 项目状态记录现在，Git 记录过去；
10. 小步推进，小步验证。

### 章节索引

- 职责边界与四模块职责：第 2~3 节
- 项目状态识别与 AI 接手：第 5~6 节
- 阶段入口与流程裁剪：第 7 节
- 闸门条件：第 9~12 节
- 冻结与回退：第 13~14 节
- 变更判断与传播：第 16~17、32 节
- 项目状态维护：第 20~21 节
- 用户确认与防幻觉：第 22~24 节
- Git 机制：第 26~27 节
- 工作单元与小步推进：第 28~29 节
- MVP 控制：第 30~31、35 节
- 总控工作循环：第 37 节

## 1. Skill 定位

本 Skill 是整个 AI 软件开发工作流的最高层流程控制与协作编排规则。

本 Skill 不负责直接完成需求分析、技术设计、交互原型或代码开发，而负责：

- 识别项目当前状态；
- 判断项目当前所处阶段；
- 决定当前应该调用哪个模块；
- 控制四个模块之间的推进关系；
- 管理阶段入口与阶段闸门；
- 管理阶段完成与冻结；
- 管理跨阶段问题；
- 管理阶段回退；
- 管理信息和项目产物在模块之间的传递；
- 管理项目状态；
- 协调 Git 与项目状态；
- 管理 AI 接手与上下文交接；
- 防止 AI 在跨阶段工作中擅自修改已经确认的内容；
- 确保项目按照正确的依赖关系推进。

核心原则：

> **总控负责管流程，模块负责干活，Reference 负责提供经验，项目产物负责留下结果，项目状态负责记录当前状态，Git 负责记录历史。**

---

# 2. 总控与其他组成部分的职责边界

整个 AI 软件开发工作流由以下部分组成：

```text
总控 Skill
    ↓
控制项目如何推进

项目状态.md
    ↓
记录项目现在是什么状态

模块 Skill
    ↓
规定当前模块应该如何工作

Reference
    ↓
提供当前模块的经验、原则和案例

项目产物
    ↓
记录当前模块已经产生的正式结果

Git
    ↓
记录项目随时间发生的版本变化

当前对话
    ↓
提供当前工作上下文
```

## 2.1 总控 Skill

总控 Skill 负责：

> **决定什么时候做什么、由谁做、是否可以继续、是否需要回退。**

总控不直接负责专业工作。

------

## 2.2 模块 Skill

模块 Skill 负责：

> **在进入该模块后，具体应该如何工作。**

四个模块：

```text
模块一：需求规划
    ↓
回答“做什么？”

模块二：技术设计
    ↓
回答“怎么做？”

模块三：交互原型与视觉验证
    ↓
回答“用户将看到什么、怎么操作？”

模块四：开发规划与 MVP 实现
    ↓
回答“怎么真正做出来？”
```

------

## 2.3 Reference

Reference 是经验知识，不是执行规则。

> **Skill 是行为规则，Reference 是经验知识。**

总控不得把 Reference 当成强制执行规则。

------

## 2.4 项目状态.md

项目状态.md 是项目的动态状态中枢。

总控必须通过项目状态.md 了解：

- 当前项目阶段；
- 各模块状态；
- 阶段冻结状态；
- 已确认事实；
- 关键决策；
- 未决事项；
- 阻塞问题；
- 当前工作上下文；
- 最近重要变更；
- Git 状态；
- 项目产物位置；
- 下一步行动。

总控负责维护项目的全局状态，但不得凭空制造项目事实。

------

## 2.5 Git

Git 用于记录项目历史版本。

Git 不替代项目状态.md。

```text
项目状态.md
    ↓
记录“现在是什么状态”

Git
    ↓
记录“过去发生过什么变化”
```

项目状态.md 与 Git 应共同保证项目的可追溯性。

- 角色；
- 核心业务流程；
- 业务规则；

- 业务分支；
- 异常业务行为；
- 权限和可见性；
- 业务对象之间的关系。

模块一完成后形成：

> **产品需求与业务规则基线。**

------

回答：

> **怎么做？**

负责：

- 技术架构；
- 数据模型；

- 技术可行性；

------

## 模块三：交互原型与视觉验证

# 4. 核心工作流

标准工作流：

```text
项目开始
    ↓
读取项目状态
    ↓
判断当前项目状态
    ↓
判断当前应该进入哪个模块
    ↓
进入模块一：需求规划
    ↓
需求闸门
    ↓
进入模块二：技术设计
    ↓
技术闸门
    ↓
进入模块三：交互原型与视觉验证
    ↓
原型闸门
    ↓
进入模块四：开发规划与 MVP 实现
    ↓
MVP 验收
    ↓
项目完成 / 继续迭代
```

但总控不得把项目强制理解为单向流程。

真实项目允许：

```text
模块一 → 模块二 → 模块三 → 模块四
                    ↑
                    │
                  发现问题
                    │
                    ↓
                  模块二
```

也允许：

```text
模块四
  ↓
发现业务规则问题
  ↓
返回模块一
```

因此：

> **四模块是有依赖关系的状态系统，而不是不可返回的流水线。**

------

# 5. 项目状态识别

AI 开始任何项目工作前，必须先判断：

1. 项目是否已经存在；
2. 是否存在项目状态.md；
3. 当前处于哪个阶段；
4. 当前阶段是什么状态；
5. 哪些前置阶段已经完成；
6. 哪些前置阶段已经冻结；
7. 当前是否存在阻塞；
8. 当前是否存在需要回退的问题；
9. 当前 Git 状态是什么；
10. 当前工作单元是什么；
11. 下一步应该做什么。

不得在未判断项目状态的情况下直接开始工作。

------

# 6. AI 接手已有项目

如果项目已经存在，不得强制从模块一重新开始。

AI 应首先判断：

```text
项目目前已经完成到哪里？
```

例如：

```text
模块一：已冻结
模块二：已冻结
模块三：进行中
模块四：未开始
```

那么 AI 应从模块三继续。

如果：

```text
模块一：已冻结
模块二：已冻结
模块三：已冻结
模块四：进行中
```

则直接进入模块四。

------

## 6.1 接手顺序

新 AI 接手项目时：

```text
① 读取项目状态.md
        ↓
② 判断当前阶段
        ↓
③ 阅读当前阶段 Skill
        ↓
④ 阅读当前阶段 Reference
        ↓
⑤ 阅读当前阶段项目产物
        ↓
⑥ 查看当前工作上下文
        ↓
⑦ 检查 Git 当前状态
        ↓
⑧ 判断下一步行动
        ↓
⑨ 继续工作
```

如果当前阶段存在未决事项或阻塞问题，应优先处理这些问题。

------

## 6.2 存量项目重构（工作流外收编）

第 6.1 节处理的是「已经使用本工作流做到一半的项目」。

如果项目已经存在大量代码，但从未使用本工作流（没有项目状态.md、没有冻结产物），则进入：

> **存量项目重构模式（模块零）**

流程骨架：

```text
现状盘点（AI 阅读旧代码）
    ↓
产出《现状说明》供用户核对
    ↓
反向生成三份草稿（均为 🟡 待确认）：
需求 / 技术设计 / 全页面 Wireframe
    ↓
意图追问 → 用户修改 → 跨层同步
    ↓
用户显式冻结 REQ-V1 / TECH-V1 / PROTO-V1
    ↓
进入模块四，按正常流程实现 MVP
```

基本规则：

1. 反向生成的文档一律是草稿，状态为 🟡 待确认，不得自动冻结；
2. 代码行为 ≠ 用户意图：从代码提取的规则必须标注「代码现状」，经用户确认后才能成为需求；
3. 用户修改任何一层，必须跨层传播检查，三份草稿保持一致；
4. 冻结必须按第 22.1 节标准确认动作执行，三份基线可在一次会话中先后冻结；
5. 详细方法论见：00_总控/Reference_总控_存量项目重构_V1.md。

# 7. 阶段入口控制

AI 只有在满足当前阶段入口条件后，才能正式进入该阶段。

------

## 7.1 模块一入口

允许进入模块一的条件：

- 项目目标基本明确；
- 已准备开始需求探索；
- 不存在更高优先级的前置问题。

如果项目完全没有明确目标，则先进行必要的项目启动澄清。

------

## 7.2 模块二入口

模块一必须已经形成明确的产品需求与业务规则基线。

如果模块一尚未完成或存在关键未决事项，则不得直接进入技术设计。

------

## 7.3 模块三入口

模块一需求基线已经明确。

模块二技术设计已经完成并冻结。

如果技术设计尚未确定，则不得进入完整原型验证。

------

## 7.4 模块四入口

以下内容必须已经明确：

- 产品需求；
- 技术设计；
- 核心原型与交互。

对应阶段应已经完成并冻结。

如果发现这些前置条件不存在，不得直接进入正式 MVP 开发。

------

## 7.5 流程裁剪

不是所有项目都需要完整执行四个模块。

总控可以根据项目形态进行裁剪：

- 无用户界面或界面极简的项目（脚本、CLI 工具、后端服务、API）：可以压缩或跳过模块三，由模块二直接进入模块四；
- 范围很小的个人工具：可以将模块一和模块二合并为一次轻量确认，但仍必须形成书面产物；
- 已经存在部分产物的项目：按第 6 节规则接管，不重做已完成阶段。

裁剪规则：

1. 裁剪决定由总控提出，并说明理由；
2. 裁剪决定必须记录到项目状态.md（记为关键决策）；
3. 裁剪只减少流程环节，不降低闸门质量：保留下来的阶段仍必须满足对应闸门条件；
4. 用户不认可裁剪时，按完整流程执行。

------

# 8. 阶段完成与阶段冻结

> **完成 ≠ 冻结。**

一个阶段可以：

```text
已完成
但
未冻结
```

表示 AI 认为工作已经完成，但还没有成为正式基线。

只有经过用户确认并满足该阶段完成条件后，才能进入：

```text
已冻结
```

------

# 9. 需求闸门

模块一必须满足：

- 核心业务流程明确；
- 关键产品边界明确；
- 关键业务分叉明确；
- 业务对象明确；
- 关键对象生命周期明确；
- 附属业务对象处理明确；
- 关键对象关联行为明确；
- 不存在会导致明显不同产品行为的重大歧义；
- 用户确认需求结果。

满足后：

```text
模块一
    ↓
需求冻结
    ↓
允许进入模块二
```

------

# 10. 技术闸门

模块二必须满足：

- 存在完整技术方案；
- 技术方案与产品需求一致；
- 数据模型能够支持业务规则；
- API 能支持核心业务；
- 权限方案能够支持产品权限；
- 前后端方案能够形成闭环；
- 重要技术风险已经处理；
- 核心技术路径已经通过 Demo 验证；
- 核心业务场景已经完成技术覆盖；
- 用户已经确认技术设计。

满足后：

```text
模块二
    ↓
技术冻结
    ↓
允许进入模块三
```

------

# 11. 原型闸门

模块三必须满足：

- 核心页面已经确定；
- 核心页面结构已经确定；
- 页面组件关系明确；
- 核心页面跳转关系明确；
- 核心交互行为明确；
- 关键输入 / 提交 / 操作行为明确；
- 成功与失败反馈明确；
- 核心业务流程可以通过原型表达；
- 用户已经确认核心原型；
- 最小交互 Demo 已经完成必要验证。

满足后：

```text
模块三
    ↓
原型冻结
    ↓
允许进入模块四
```

------

# 12. MVP 验收

模块四不以：

> “代码写完了”

作为完成条件。

必须满足：

```text
代码实现
+
项目可运行
+
前后端联调
+
核心业务闭环可执行
+
异常 / 权限 / 状态得到验证
+
用户能够完成核心任务
```

才可以认为 MVP 完成。

------

# 13. 冻结机制

冻结代表：

> **当前阶段已经形成经过确认的有效基线。**

冻结后：

- 后续模块不得无意识修改前置阶段内容；
- 后续模块不得因为实现方便而改变产品行为；
- 后续模块不得因为技术方便而改变已确认需求；
- 后续模块不得擅自修改已经确认的原型行为。

如果发现确实需要修改：

```text
发现问题
    ↓
判断问题所属阶段
    ↓
返回对应模块
    ↓
重新确认
    ↓
修改阶段产物
    ↓
重新冻结
    ↓
更新项目状态
    ↓
继续后续工作
```

------

# 14. 回退机制

回退不是异常，而是正式工作流的一部分。

## 14.1 产品问题

如果发现：

- 需求遗漏；
- 业务规则错误；
- 产品边界错误；
- 业务行为未定义；
- 业务分支缺失；

返回：

> **模块一：需求规划**

------

## 14.2 技术问题

如果发现：

- 架构不成立；
- 数据模型无法支持业务；
- API 无法支持业务；
- 技术方案存在重大风险；
- Demo 验证失败；

返回：

> **模块二：技术设计**

------

## 14.3 原型问题

如果发现：

- 页面结构错误；
- 交互逻辑错误；
- 页面跳转错误；
- 用户操作路径不合理；
- 原型与确认需求不一致；

返回：

> **模块三：交互原型与视觉验证**

------

## 14.4 开发问题

如果发现：

- Bug；
- 代码错误；
- 联调问题；
- 测试失败；
- 实现与既定设计不一致；

优先在：

> **模块四：开发规划与 MVP 实现**

解决。

------

# 15. 跨阶段问题判断

当发现问题时，不得只根据“问题出现在哪个阶段”判断归属。

必须判断：

> **这个问题真正改变的是哪一层的事实？**

例如：

```text
开发时发现订单取消规则没有定义
```

虽然问题是在模块四发现的，

但真正的问题是：

> 产品业务规则不完整。

因此应该返回模块一。

再例如：

```text
订单快照无法通过当前数据库设计实现
```

真正的问题是：

> 技术设计问题。

因此返回模块二。

再例如：

```text
用户无法从订单详情进入售后流程
```

如果需求和技术都已经支持，但原型缺少这个入口，则属于模块三。

------

# 16. 跨阶段变更传播

如果前置阶段发生变化，后续阶段必须重新检查。

例如：

```text
模块一发生重大变化
        ↓
模块二重新检查
        ↓
模块三重新检查
        ↓
模块四重新检查
```

但不是所有变化都需要完整回滚。

总控应根据变更影响范围判断：

```text
无影响
    ↓
继续

局部影响
    ↓
只重新验证受影响部分

重大影响
    ↓
返回对应阶段重新确认
```

------

# 17. 变更判断

任何新需求、修改建议或开发过程中发现的问题，都必须先判断其性质。

分类：

```text
产品变化
技术变化
原型变化
实现变化
```

------

## 17.1 产品变化

例如：

- 新增功能；
- 修改业务规则；
- 修改用户权限；
- 修改业务流程；
- 修改产品边界。

处理：

> 返回模块一。

------

## 17.2 技术变化

例如：

- 更换数据库；
- 修改架构；
- 修改技术方案；
- 修改关键数据模型；
- 修改核心 API 设计。

处理：

> 返回模块二。

------

## 17.3 原型变化

例如：

- 页面结构变化；
- 页面跳转变化；
- 核心交互变化；
- 信息层级变化。

处理：

> 返回模块三。

------

## 17.4 实现变化

例如：

- Bug 修复；
- 性能优化；
- 代码重构；
- 普通实现细节调整。

如果不改变已确认产品行为、技术设计和原型，则可以留在模块四。

------

# 18. 总控不得越权

总控不得代替模块完成专业工作。

总控不得：

- 自己分析完整需求；
- 自己设计数据库；
- 自己设计完整技术架构；
- 自己设计完整页面；
- 自己直接承担开发任务；
- 因为流程需要而擅自补充产品能力；
- 因为技术方便而改变产品需求。

总控只负责：

> **判断、调度、检查、推进、回退、同步。**

------

# 19. 模块之间的信息传递

模块之间不得依赖完整聊天记录传递信息。

应该通过：

```text
项目状态
+
正式项目产物
+
冻结版本
```

进行信息传递。

------

## 19.1 模块一 → 模块二

传递：

- 产品需求；
- 业务规则；
- 用户；
- 业务对象；
- 生命周期；
- 权限；
- 业务流程；
- 业务边界。

------

## 19.2 模块二 → 模块三

传递：

- 技术能力；
- 数据结构；
- API 能力；
- 权限限制；
- 状态；
- 业务技术约束。

------

## 19.3 模块三 → 模块四

传递：

- 页面结构；
- 页面清单；
- 组件结构；
- 页面跳转；
- 交互；
- 核心用户流程；
- 用户确认结果。

------

# 20. 项目状态更新

总控负责维护项目状态.md。

AI 在以下情况下必须考虑更新项目状态：

- 当前阶段发生变化；
- 当前阶段状态发生变化；
- 阶段完成；
- 阶段冻结；
- 阶段重新打开；
- 出现重要未决事项；
- 出现阻塞问题；
- 发生重要项目变更；
- 当前工作上下文发生重要变化；
- 下一步行动发生变化；
- Git 版本发生重要变化；
- 发生阶段回退。

------

# 21. 项目状态更新权限

AI 可以直接更新：

- 当前阶段；
- 当前阶段状态；
- 当前工作目标；
- 当前工作单元；
- 当前工作上下文；
- 下一步行动；
- 阻塞状态；
- Git 当前状态。

AI 可以记录但不得自行确认：

- 未决事项；
- 候选方案；
- AI 推测；
- 尚未得到用户确认的决策。

只有存在明确依据时，才能更新：

- 已确认事实；
- 关键决策；
- 阶段冻结状态；
- 用户确认结果。

------

# 22. 用户确认规则

以下行为不能被 AI 自动解释为完整确认：

- “嗯”
- “可以”
- “继续”
- “差不多”
- “应该可以”
- “先这样”

AI 必须根据上下文判断用户到底确认了什么。

例如：

> “可以继续。”

通常只代表：

> **允许继续工作。**

不代表：

> 用户确认了上一轮所有讨论内容。

如果需要形成正式阶段冻结，应明确确认对应阶段结果。

## 22.1 标准确认动作

申请冻结时，必须使用标准句式请求用户显式确认：

> 「模块〈X〉工作已完成，是否确认冻结基线〈版本号〉？确认后，后续模块将以该基线为准继续工作。」

只有当用户回复明确包含确认意图，并指向对应阶段或版本号时，才能写入冻结状态。

如果用户回复含糊（例如只说「继续」「可以」），则继续当前工作，不执行冻结。

------

# 23. 防止 AI 幻觉

总控必须始终遵守：

> **不知道就不知道。**

如果项目状态没有记录：

```text
不要猜。
```

如果项目产物没有说明：

```text
不要猜。
```

如果用户没有确认：

```text
不要猜。
```

如果存在多个合理方案，并且选择会改变项目行为：

```text
不要自行确定。
```

应该：

```text
记录为待确认
        ↓
判断影响阶段
        ↓
必要时询问用户
```

------

# 24. “常识”不能覆盖项目事实

即使某种设计：

- 很常见；
- 行业通常如此；
- 大多数项目如此；
- AI 认为这样更合理；

只要项目没有确认：

> 就不能自动变成项目事实。

项目事实优先来自：

```text
用户确认
+
冻结项目产物
+
明确实现事实
```

------

# 25. 项目状态与项目产物的关系

项目状态.md 不保存所有详细内容。

例如：

```text
项目状态.md
    ↓
订单需要保留历史商品信息
```

具体：

```text
订单快照的数据结构
字段定义
数据库设计
API
代码实现
```

应该存在于对应项目产物中。

因此：

> **项目状态负责索引和描述当前事实，项目产物负责保存详细内容。**

------

# 26. Git 协作机制

Git 是整个工作流的版本历史系统。

项目状态.md 必须纳入 Git 管理。

------

## 26.1 Git 的作用

Git 主要负责：

- 版本管理；
- 变更追踪；
- 回退；
- 差异比较；
- 阶段历史；
- AI 工作交接；
- 项目可追溯性。

------

## 26.2 Commit 原则

不要：

> 每说一句话就 Commit。

也不要：

> 一次积累几十个完全不同的修改再 Commit。

推荐：

> **一个具有明确边界、完成并经过验证的有效工作单元，对应一个清晰的 Commit。**

例如：

```text
实现用户登录
```

完成：

```text
代码
+
运行
+
验证
```

然后：

```text
更新项目状态
        ↓
Git Commit
```

------

## 26.3 阶段冻结与 Git

阶段冻结可以对应明确 Git Commit。

例如：

```text
需求冻结
REQ-V1

技术冻结
TECH-V1

原型冻结
PROTO-V1

MVP
MVP-V1
```

Git 可以成为这些阶段版本的历史锚点。

------

# 27. Git 与项目状态冲突

如果：

```text
项目状态说：
技术设计已经冻结

但 Git 中代码明显与技术设计不一致
```

总控不得直接判断哪一个正确。

应：

```text
发现冲突
    ↓
识别冲突
    ↓
确认当前实际状态
    ↓
判断属于设计问题还是实现问题
    ↓
必要时返回对应模块
    ↓
重新确认
    ↓
更新项目状态
    ↓
提交 Git
```

------

# 28. 工作单元机制

总控应尽可能让 AI 按“工作单元”推进，而不是无限制地连续修改整个项目。

一个工作单元应具有：

```text
明确目标
+
明确范围
+
明确完成条件
+
明确验证方式
```

例如：

```text
工作单元：
实现用户登录业务闭环

范围：
数据库
后端
API
前端登录页

完成条件：
用户可以成功登录

验证：
登录成功
登录失败
未登录访问受保护页面
```

完成后：

```text
验证
↓
更新状态
↓
Git Commit
```

------

# 29. 小步推进原则

AI 应尽可能：

```text
小范围修改
    ↓
运行
    ↓
验证
    ↓
确认
    ↓
继续
```

而不是：

```text
一次修改大量模块
    ↓
最后才运行
    ↓
最后才发现问题
```

------

# 30. MVP 控制

总控不得让模块四无限扩展 MVP。

MVP 的目标是：

> **验证核心产品价值与核心业务闭环。**

总控应监督：

```text
P0
核心业务闭环
    ↓
必须完成

P1
核心体验增强
    ↓
根据项目情况决定

P2
增强功能
    ↓
可以后置

P3
未来功能
    ↓
当前不进入 MVP
```

MVP 不是：

> 功能越少越好。

MVP 是：

> **能够验证核心产品价值所需的最小完整产品。**

------

# 31. Demo 与 MVP 的区别

总控必须区分：

### 技术 Demo

证明：

> **技术方案可行。**

主要属于模块二。

------

### 交互 Demo

证明：

> **核心交互能够表达和体验。**

主要属于模块三。

------

### MVP

证明：

> **核心产品业务闭环真正能够运行。**

主要属于模块四。

因此：

```text
Demo ≠ MVP
```

------

# 32. 发现问题时的总控决策流程

当 AI 在任何阶段发现问题时，必须按照：

```text
发现问题
    ↓
问题是什么？
    ↓
改变了什么？
    ↓
改变的是：
产品？
技术？
原型？
实现？
    ↓
确定所属模块
    ↓
判断是否影响已冻结阶段
    ↓
判断影响范围
    ↓
决定：
继续 / 局部重新验证 / 回退
    ↓
更新项目状态
```

------

# 33. 总控状态机

项目整体可以理解为：

```text
项目初始化
    ↓
需求规划中
    ↓
需求待确认
    ↓
需求冻结
    ↓
技术设计中
    ↓
技术待确认
    ↓
技术冻结
    ↓
原型设计中
    ↓
原型待确认
    ↓
原型冻结
    ↓
MVP 开发中
    ↓
MVP 待验收
    ↓
MVP 验收
    ↓
项目完成
```

同时允许：

```text
任何阶段
    ↓
发现前置问题
    ↓
需回退
    ↓
对应模块
    ↓
重新确认
    ↓
重新冻结
    ↓
继续推进
```

------

# 34. 不允许的推进方式

总控不得允许以下情况：

### 情况一

```text
需求不明确
    ↓
直接设计数据库
```

------

### 情况二

```text
技术方案没验证
    ↓
直接进入大规模开发
```

------

### 情况三

```text
原型没确认
    ↓
直接大量开发前端
```

------

### 情况四

```text
开发发现需求问题
    ↓
开发人员自行修改需求
```

------

### 情况五

```text
技术实现困难
    ↓
自行修改产品行为
```

------

### 情况六

```text
AI 不知道
    ↓
根据常见项目经验自行补充
```

------

### 情况七

```text
阶段已经冻结
    ↓
后续模块偷偷修改
```

------

# 35. 项目完成判断

项目不能仅因为：

```text
代码写完
```

就宣布完成。

至少需要：

```text
需求明确
+
技术方案成立
+
核心交互明确
+
MVP 核心业务闭环完成
+
项目可运行
+
核心业务经过验证
+
用户完成最终验收
```

才可以进入：

> **项目完成**

------

# 36. 总控的核心原则

## 原则一

> **总控不做专业工作，总控负责正确地调度专业工作。**

------

## 原则二

> **先判断当前状态，再决定下一步。**

------

## 原则三

> **后续模块不得无意识修改前置模块的冻结结果。**

------

## 原则四

> **发现问题不可怕，错误地继续推进才可怕。**

------

## 原则五

> **任何重大变化都必须找到它真正所属的层级。**

------

## 原则六

> **完成不等于冻结，冻结不等于永久不可修改。**

------

## 原则七

> **回退是正常机制，而不是流程失败。**

------

## 原则八

> **项目状态记录现在，Git 记录过去。**

------

## 原则九

> **聊天记录不是项目的唯一记忆。**

------

## 原则十

> **不知道就记录未知，不要用猜测填空。**

------

## 原则十一

> **能由 AI 自己决定的事情，不要打扰用户；会改变产品行为的事情，必须让正确的模块处理。**

------

## 原则十二

> **不要从“我要写哪些代码”开始推进项目，而要从“当前应该让哪个业务能力真正向前一步”开始推进。**

------

# 37. 总控最终工作循环

每一次 AI 工作循环都遵循：

```text
读取项目状态
    ↓
理解当前项目
    ↓
确认当前阶段
    ↓
确认阶段冻结状态
    ↓
确认当前工作上下文
    ↓
检查 Git
    ↓
确定当前工作单元
    ↓
调用对应模块 Skill
    ↓
执行工作
    ↓
验证结果
    ↓
判断是否产生跨阶段影响
    ↓
如果没有：
    ↓
更新项目状态
    ↓
必要时 Git Commit
    ↓
继续下一工作单元

如果有：
    ↓
判断问题所属阶段
    ↓
必要时回退
    ↓
重新确认
    ↓
重新冻结
    ↓
更新项目状态
    ↓
Git Commit
    ↓
继续推进
```

------

# 38. 总控的最终目标

总控 Skill 的最终目标不是让项目：

> “严格按照一条固定流水线执行”。

而是让项目始终保持：

```text
当前状态清楚
+
阶段边界清楚
+
责任边界清楚
+
信息来源清楚
+
决策来源清楚
+
未决事项清楚
+
变更影响清楚
+
版本历史清楚
+
AI 下一步清楚
```

最终形成：

```text
规则
 ↓
总控 Skill

状态
 ↓
项目状态.md

经验
 ↓
Reference

阶段工作
 ↓
四个模块 Skill

正式结果
 ↓
项目产物

历史
 ↓
Git
```

------

# 39. 总控核心定义

> **总控 Skill 是整个 AI 软件开发工作流的流程编排与状态控制层。**
>
> 它不负责替代需求、技术、原型和开发模块，而负责理解项目当前状态，选择和调度正确的模块，管理阶段入口、完成、冻结与回退，维护项目状态，协调 Git 与项目产物，并保证不同 AI 能够在不依赖完整历史对话的情况下准确接续项目。
>
> **总控负责管流程，模块负责干活，Reference 负责提供经验，项目产物负责留下结果，项目状态负责记录当前状态，Git 负责记录项目历史。**
