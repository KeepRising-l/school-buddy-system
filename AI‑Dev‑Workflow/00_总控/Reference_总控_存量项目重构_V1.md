# Reference：总控——存量项目重构 V1

> 本文档是经验与方法参考，不是强制执行规则（遵守「Skill 是规则，Reference 是经验」的划分）。
>
> 它配套总控 Skill 第 6.2 节「存量项目重构（工作流外收编）」，提供具体操作方法。

------

# 一、定位与适用场景

## 适用

- 项目已经存在大量代码（前端、后端、数据、页面均已实现）；
- 但从未使用本工作流：没有项目状态.md，没有冻结产物，没有阶段文档；
- 用户希望基于旧项目进行重构、重写或升级。

## 不适用

- 已经使用本工作流做到一半的项目（走总控第 6.1 节接手顺序）；
- 只想小修小补、不改变产品形态的项目（按普通开发任务处理即可）。

## 与正常流程的关系

```text
正常流程：  用户想法 ─────────────────→ 模块一 → 模块二 → 模块三 → 模块四
重构流程：  旧代码 → 模块零 ─────────→ 模块一 → 模块二 → 模块三 → 模块四
                                        ↑
                          两者在模块一之后完全共用
```

------

# 二、触发与登记

满足以下任一条件即进入重构模式：

1. 用户明确提出「重构 / 重写 / 翻新」某个已有项目；
2. 项目目录存在成规模的代码，但没有项目状态.md。

进入重构模式后，必须先在项目状态.md 中登记：

- 重构来源（原项目代码位置与简要说明）；
- 现状说明的产物路径（盘点完成后回填）。

------

# 三、模块零：现状盘点

## 3.1 盘点什么

AI 阅读旧项目，从以下维度建立现状认知：

- 项目结构（目录组织、前后端划分、模块边界）；
- 数据模型（实体、表、关系、状态字段）；
- 后端能力（接口清单、业务逻辑、权限控制、事务处理）；
- 前端能力（页面清单、路由、组件、交互行为）；
- 外部依赖（第三方服务、数据库、中间件）；
- 隐含业务规则（从代码逻辑反推的业务行为）。

## 3.2 产出《现状说明》

《现状说明》是描述性事实文档，建议结构：

```text
1. 项目概况（一句话：这是什么，用了什么技术栈）
2. 实际功能清单
   前端页面 / 后端接口 / 数据实体，逐条列出
3. 隐含业务规则
   逐条列出，每条标注来源代码位置
4. 架构与技术栈现状
5. 已知问题清单
   代码质量问题 / 明显 Bug / 安全隐患 / 架构短板
```

关键纪律：

> **不得跳过现状盘点，直接生成需求文档或开始重写。**

《现状说明》是描述性事实，不冻结，但必须交用户核对：

```text
AI 产出《现状说明》
    ↓
用户核对：「功能有没有漏？规则读得对不对？」
    ↓
AI 修正 → 现状认知锁定
```

------

# 四、反向生成三份草稿

现状认知锁定后，AI 一次性反向生成三份文档草稿：

| 草稿 | 内容依据 | 结构依据 |
|---|---|---|
| 《产品需求与业务规格（重构草案）》 | 现状说明中的功能与规则 | 模块一 Skill 第 17 节文档结构 |
| 《技术设计（重构草案）》 | 现有架构、数据模型、API | 模块二 Skill 第 26 节文档结构 |
| 《交互原型（重构草案）》 | 全部页面 | **所有页面都要画出 Wireframe**（含跳转关系与核心交互） |

## 4.1 草稿状态纪律

> **三份草稿一律标记为 🟡 待确认，不得自动冻结。**

## 4.2 来源标注纪律

从代码反推的规则，必须区分三种来源并逐条标注：

```text
【代码现状】  代码里确实是这么做的
【用户确认】  用户明确表态要 / 不要这样
【AI 推测】   AI 根据常识推断，未获确认
```

核心原则：

> **代码行为 ≠ 用户意图。**
>
> 代码里删除是物理删除，不代表用户想要物理删除；
> 可能是当时没做，可能是偷懒，可能是本意。
>
> 必须问，不能默认。

------

# 五、意图追问

反向生成完成后，AI 向用户提问。与新建项目的区别：

| 新建项目问 | 重构项目问 |
|---|---|
| 「你要做什么产品？」 | 不问，代码里已经有了 |
| 「订单取消规则是什么？」 | 「代码里取消是无限制的，这是本意还是当时没做？」 |
| —— | 「你觉得垃圾的是功能、代码质量还是架构？」 |

追问类型：

1. **去留裁决**：这个功能还要不要？
2. **意图核对**：代码里这个行为，是你的本意还是权宜之计？
3. **垃圾定位**：用户不满意的到底是产品形态、代码质量还是架构能力？
4. **新增期望**：重写时想加什么、改什么？
5. **技术栈去留**：框架、数据库换不换？

追问纪律：

- 只问意图层面，不问代码里能读到的事实；
- 按影响排序，不搞问卷式轰炸（参考模块一第 10 节问题优先级）；
- 用户的每一次回答，都更新三份草稿中的对应内容。

------

# 六、修改与跨层传播

用户对任何一份草稿提出修改时，AI 必须做跨层一致性检查：

```text
用户：删除「积分」功能
    ↓
需求草稿：移除积分相关功能需求
    ↓
技术设计草稿：移除积分数据模型、接口、定时任务
    ↓
原型草稿：移除积分页面与相关入口
    ↓
向用户报告影响清单：「此修改影响三份文档的以下位置……」
```

纪律：

> **任何一处修改未完成跨层同步之前，不得申请冻结。**

------

# 七、冻结与进入开发

用户审查三份草稿，直到满意。然后由用户显式触发冻结（可以三份一起）：

```text
确认冻结需求基线 REQ-V1。
确认冻结技术基线 TECH-V1。
确认冻结原型基线 PROTO-V1。
```

冻结后：

1. 更新项目状态.md（阶段、冻结状态、版本号）；
2. Git Commit（freeze 提交）；
3. 《现状说明》转为参考产物归档（它不再具有基线效力）；
4. 进入模块四：先出开发计划，再按业务切片实现 MVP，全部验证规则与正常流程一致。

------

# 八、重写还是渐进重构（模块二职责）

如果旧项目仍可运行，AI 应在技术设计阶段评估两条路线并交给用户决策：

## 整体重写

适合：

- 架构腐化严重，修补成本高于重写；
- 技术栈必须更换；
- 产品形态发生大改。

特点：干净、彻底，但周期长、风险集中。

## 渐进替换

适合：

- 旧系统仍在服务，不能长时间停摆；
- 问题集中在局部模块；
- 技术栈尚可保留。

特点：按业务切片逐块替换，旧系统持续可用，风险分散。

AI 必须给出建议和理由，但决策权在用户。

------

# 九、禁止行为

1. 不得跳过现状盘点直接重写；
2. 不得把代码现状自动当成用户意图；
3. 不得自动冻结反向生成的草稿；
4. 不得因为旧代码「看起来写得还行」而跳过用户裁决；
5. 不得因为走重构入口而省略模块四的切片实现与运行验证；
6. 不得在跨层传播未完成时申请冻结。

------

# 十、完整流程图

```text
旧代码项目
    ↓
登记重构来源（项目状态.md）
    ↓
模块零：现状盘点
    ↓
《现状说明》→ 用户核对
    ↓
反向生成三份草稿（🟡 待确认）
需求 / 技术设计 / 全页面 Wireframe
    ↓
意图追问（去留 / 意图 / 垃圾定位 / 期望 / 技术栈）
    ↓
用户修改 → 跨层传播同步
    ↓
用户显式冻结 REQ-V1 / TECH-V1 / PROTO-V1
    ↓
模块四：开发计划 → 业务切片 → MVP 验收
```
