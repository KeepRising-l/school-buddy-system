可以。现在前三个模块已经把 **“做什么 → 怎么做 → 用户看到什么”** 理顺了，那么第四个模块就应该非常明确地解决最后一个问题：

> **“怎么真正把它做出来，以及现在先做什么？”**

而且这里我建议我们继续保持前面定下来的原则：**Reference 不负责规定 AI 必须怎么工作，而是沉淀经验、方法、原则、案例和常见坑。**

下面这份可以直接作为：

```
Reference_模块四_开发规划与MVP实现_V1.md
```

------

# 二、模块四在整个体系中的位置

整个开发体系目前由四个模块组成：

```text
模块一：需求规划
        ↓
      做什么？
        ↓
模块二：技术设计
        ↓
      怎么做？
        ↓
模块三：交互原型与视觉验证
        ↓
      用户将看到什么？
        ↓
模块四：开发规划与 MVP 实现
        ↓
      怎么真正做出来？
```

四个模块分别解决不同问题。

### 模块一

解决：

> 产品到底要做什么？

输出产品需求、业务规则和产品边界。

------

### 模块二

解决：

> 这些业务应该通过什么技术方案实现？

输出技术架构、数据模型、接口、权限、状态、事务等技术设计。

------

### 模块三

解决：

> 用户实际会看到什么，以及如何操作？

输出页面结构、Wireframe、交互关系和核心流程。

------

### 模块四

解决：

> 已经确定的东西，应该按照什么顺序真正开发出来？

输出：

- 开发规划
- MVP 范围
- 开发任务
- 开发顺序
- 阶段目标
- 实际代码
- 联调
- 测试
- 问题修复
- 迭代计划

因此：

> **模块四不是重新设计产品，而是执行前三个模块已经确认的设计。**

------

# 三、模块四的核心目标

模块四的核心目标不是：

> “把所有功能一次性写完。”

而是：

> **让一个已经经过需求、技术和交互确认的系统，以最小可验证路径逐步变成真正可运行的软件。**

因此，模块四需要同时解决两个问题：

### 1. 怎么开发？

也就是：

```text
任务怎么拆？
先做什么？
后做什么？
每一步做到什么程度？
如何保证前后端能够联调？
```

### 2. 第一版做多少？

也就是：

```text
哪些功能必须进入 MVP？
哪些功能可以延后？
哪些功能暂时不要做？
```

这两个问题必须结合起来考虑。

------

# 四、开发规划不是简单的任务清单

开发规划不能只是：

```text
□ 做登录
□ 做首页
□ 做商品
□ 做订单
□ 做支付
□ 做后台
```

这种列表看起来完整，但实际上无法直接指导开发。

真正有效的开发规划应该回答：

```text
做什么？
为什么现在做？
依赖什么？
做到什么程度算完成？
完成之后如何验证？
下一步依赖它的是什么？
```

因此，一个好的开发任务应该具有：

> **明确目标 + 明确边界 + 明确依赖 + 明确完成标准 + 明确验证方式**

------

# 五、MVP 的真正含义

MVP（Minimum Viable Product）不是：

> “功能越少越好。”

也不是：

> “先随便做一个能运行的页面。”

MVP 真正强调的是：

> **用最小的产品范围验证核心产品价值和核心业务闭环。**

例如一个社区生鲜团购平台。

假设完整产品包括：

```text
用户注册登录
商品浏览
商品搜索
商品分类
商品详情
购物车
订单
支付
配送
优惠券
积分
评价
团购
售后
后台管理
数据统计
```

MVP 并不意味着随机删掉一半功能。

应该先找到：

> **这个产品最核心的业务闭环是什么？**

例如：

```text
用户登录
 ↓
浏览商品
 ↓
查看商品详情
 ↓
加入购物车
 ↓
提交订单
 ↓
支付
 ↓
查看订单
```

那么这条链路可能就是第一阶段最重要的 MVP 主链路。

------

# 六、MVP 应优先保证“闭环”

开发时非常容易出现一种情况：

页面做了很多：

```text
首页 ✓
商品列表 ✓
商品详情 ✓
购物车 ✓
订单页面 ✓
个人中心 ✓
后台首页 ✓
```

但是：

```text
商品 → 购物车 → 订单
```

根本没有真正打通。

这种项目：

> **看起来完成很多，实际上没有完成核心业务。**

因此 MVP 开发应该优先形成：

> **端到端业务闭环。**

例如：

```text
用户
 ↓
进入系统
 ↓
选择商品
 ↓
执行核心操作
 ↓
产生业务对象
 ↓
查看业务结果
```

只有闭环形成之后，继续增加功能才有意义。

------

# 七、开发顺序应该围绕“依赖关系”而不是页面顺序

开发不能简单按照：

```text
首页
商品页
购物车
订单页
个人中心
```

这种视觉顺序推进。

因为页面背后存在技术依赖。

例如：

```text
订单页面
    ↓
订单 API
    ↓
订单 Service
    ↓
订单数据模型
    ↓
商品数据
    ↓
用户数据
```

因此真正合理的开发顺序应该考虑：

- 数据依赖
- API 依赖
- 业务依赖
- 权限依赖
- 状态依赖
- 页面依赖
- 联调依赖

------

# 八、推荐的开发层次

一个完整系统通常可以按照：

```text
基础设施
    ↓
数据模型
    ↓
核心领域逻辑
    ↓
API
    ↓
前端数据层
    ↓
页面
    ↓
交互
    ↓
联调
    ↓
测试
```

但这不是绝对顺序。

不同项目应该根据实际情况调整。

核心思想是：

> **优先完成会被大量后续工作依赖的部分。**

------

# 九、不要把后端和前端完全割裂开发

一种常见开发方式：

```text
第一周：
后端全部写完

第二周：
前端全部写完

第三周：
开始联调
```

这种方式的问题很大。

因为到了联调阶段才会发现：

```text
后端字段和前端理解不一致
接口返回结构不一致
状态定义不一致
权限逻辑不一致
错误处理不一致
分页参数不一致
数据格式不一致
```

最终出现：

> “两边都写完了，但是接不上。”

------

# 十、推荐采用纵向切片开发

相比完全按照技术层分开开发，更推荐：

> **围绕一个完整业务能力进行纵向开发。**

例如“商品购买”：

```text
数据库
 ↓
后端 Entity
 ↓
Service
 ↓
Controller
 ↓
API
 ↓
前端 API
 ↓
商品页面
 ↓
购物车
 ↓
订单
 ↓
联调
 ↓
测试
```

完成之后：

> **这个业务能力真正可运行。**

然后再进入下一条业务链。

------

# 十一、什么是“开发切片”

一个开发切片可以理解为：

> **一个能够独立实现、运行和验证的业务能力。**

例如：

### 切片一：用户登录

```text
用户表
 ↓
登录 API
 ↓
身份验证
 ↓
Token / Session
 ↓
前端登录页面
 ↓
登录状态
 ↓
登录验证
```

完成标准：

> 用户能够真正登录，并且登录状态能够被后续业务使用。

------

### 切片二：商品浏览

```text
商品数据
 ↓
商品 API
 ↓
前端 API
 ↓
商品列表
 ↓
商品详情
```

完成标准：

> 用户可以浏览商品并查看详情。

------

### 切片三：购物车

```text
商品
 ↓
加入购物车
 ↓
购物车数据
 ↓
购物车页面
 ↓
数量修改
 ↓
删除
```

完成标准：

> 用户可以完成基本购物车操作。

------

# 十二、开发任务必须有“完成定义”

开发任务不能只有：

> “完成订单模块。”

因为“完成”到底是什么意思并不明确。

应该定义：

```text
订单模块
├── 创建订单
├── 查询订单
├── 查询订单详情
├── 修改订单状态
├── 取消订单
└── 异常处理
```

然后定义完成标准。

例如：

```text
订单创建成功：
- 商品库存正确扣减
- 订单生成
- 订单金额正确
- 订单状态正确
- 返回订单信息
```

这样才能真正判断：

> **这个任务到底完成没有。**

------

# 十三、开发任务应该避免过大

例如：

> “完成用户系统。”

这个任务太大。

可以拆成：

```text
用户实体
用户注册
用户登录
身份认证
用户信息查询
用户信息修改
权限验证
退出登录
```

进一步还可以拆成：

```text
用户表
注册 API
注册校验
登录 API
Token 生成
Token 校验
用户信息 API
前端登录页面
前端登录状态
```

但是也不能拆得过细。

例如：

```text
创建 User.java
创建 UserService.java
创建 UserController.java
```

这种属于：

> **代码文件级拆分。**

它对于开发管理价值通常较低。

更好的拆分粒度应该是：

> **业务能力级任务。**

------

# 十四、任务拆解应该保持业务语义

推荐：

```text
实现用户登录
实现商品浏览
实现购物车
实现订单创建
实现订单取消
```

而不是：

```text
写 Controller
写 Service
写 Mapper
写 Vue
写 CSS
```

因为前者能够直接对应产品能力。

后者只是技术动作。

------

# 十五、MVP 应该有明确边界

MVP 最危险的问题之一是：

> **开发过程中不断加东西。**

例如：

```text
原本：
商品 + 购物车 + 订单

开发过程中：
“要不要加优惠券？”

又想到：
“是不是应该加积分？”

然后：
“评价也挺合理。”

最后：
“再加个消息通知。”
```

结果：

> MVP 永远做不完。

因此应该存在明确的 MVP Boundary：

```text
MVP
├── 必须完成
├── 可以简化
└── 明确不做
```

------

# 十六、MVP 功能优先级

可以使用类似：

### P0：核心闭环

没有它，核心产品无法成立。

例如：

```text
登录
商品浏览
核心业务操作
核心结果查看
```

------

### P1：核心体验

产品能够正常使用，但不是最核心闭环。

例如：

```text
搜索
筛选
个人资料
历史记录
```

------

### P2：增强功能

提高体验，但可以后置。

例如：

```text
收藏
评价
积分
优惠券
通知
```

------

### P3：远期功能

当前版本完全可以不做。

例如：

```text
复杂推荐算法
高级数据分析
复杂运营系统
第三方生态
```

------

# 十七、MVP 不是把复杂功能砍掉，而是合理简化

例如真正的支付系统可能非常复杂。

MVP 阶段不一定需要真正接入支付平台。

可以：

```text
提交订单
 ↓
选择支付方式
 ↓
模拟支付成功
 ↓
订单变为已支付
```

这样可以验证：

```text
订单创建
 ↓
支付状态变化
 ↓
订单状态变化
```

而不需要立即解决：

```text
真实支付
签名
回调
退款
对账
支付安全
```

这就是：

> **保留业务行为，降低外部依赖。**

------

# 十八、Mock 的正确使用方式

Mock 的目的不是：

> “假装系统已经完成。”

而应该是：

> **降低外部依赖，让核心业务能够提前验证。**

例如：

```text
真实支付 API
       ↓
暂时无法接入
       ↓
Mock Payment Service
       ↓
模拟支付结果
       ↓
继续验证订单流程
```

Mock 应该尽可能模拟真实接口行为：

```text
请求结构
响应结构
成功状态
失败状态
异常状态
```

而不是创造一套完全不同的系统。

------

# 十九、开发阶段不要随意重新设计

进入模块四之后，经常会出现：

> “写着写着发现这里可以换一种设计。”

这个时候必须区分：

### 实现细节优化

例如：

```text
方法名称调整
代码重构
工具类优化
SQL 优化
组件拆分
```

通常可以直接处理。

------

### 技术设计变化

例如：

```text
换数据库
换认证方案
改变数据关系
改变接口协议
改变状态模型
```

需要重新检查模块二。

------

### 产品行为变化

例如：

```text
订单允许修改
用户可以删除历史订单
管理员可以恢复商品
用户可以修改已经提交的订单
```

这已经不是单纯开发问题。

应该回到模块一重新确认。

------

# 二十、开发阶段的“三层变更判断”

可以把开发中的变化理解成：

```text
代码实现变化
      ↓
技术设计变化
      ↓
产品需求变化
```

越往上影响越大。

因此：

> **不能因为已经进入开发阶段，就默认所有东西都可以直接改。**

开发只是执行阶段，不是重新定义阶段。

------

# 二十一、代码开发应该遵循“小步可运行”

不要一次写：

```text
5000 行代码
```

然后再运行。

更好的方式是：

```text
写一点
 ↓
运行
 ↓
验证
 ↓
继续
 ↓
运行
 ↓
验证
```

尤其是：

- 数据库
- API
- 权限
- 状态机
- 事务
- 前后端联调

这些地方越应该小步推进。

------

# 二十二、每个阶段都应该保持“可运行状态”

理想开发状态：

```text
Day 1
系统能启动

Day 2
数据库能运行

Day 3
用户能注册

Day 4
用户能登录

Day 5
商品能查询

Day 6
商品能展示

...
```

而不是：

```text
前两周：
大量代码正在开发中……

第三周：
终于第一次运行

然后发现：
启动不了。
```

后者排错成本极高。

------

# 二十三、开发阶段应该建立“最小运行闭环”

一个最小运行闭环通常包括：

```text
前端
 ↓
API
 ↓
Controller
 ↓
Service
 ↓
数据库
 ↓
Service
 ↓
Controller
 ↓
API
 ↓
前端
```

如果这个闭环能够跑通：

> 后续功能就可以在这个基础上不断扩展。

------

# 二十四、前后端联调应该尽早开始

不要等所有接口写完才联调。

例如：

```text
后端：
GET /products

前端：
商品列表页面
```

接口完成后立即连接。

然后检查：

```text
请求参数
响应结构
字段名称
空数据
异常
分页
加载状态
```

这样问题会非常早地暴露。

------

# 二十五、页面开发不能只验证“有数据显示”

例如商品列表：

```text
正常：
有商品
```

只是一个状态。

至少还应该考虑：

```text
加载中
有数据
无数据
请求失败
权限不足
数据异常
```

因此前端页面实际上存在：

> **状态空间。**

------

# 二十六、核心页面应该考虑完整状态

例如：

```text
商品列表
├── Loading
├── Success
│   ├── 有数据
│   └── 无数据
└── Error
```

订单页面可能：

```text
订单列表
├── 加载中
├── 有订单
├── 无订单
├── 加载失败
└── 权限异常
```

按钮也可能有：

```text
可点击
 ↓
提交中
 ↓
成功
 ↓
失败
```

因此：

> **页面不是静态截图，而是状态变化的界面。**

------

# 二十七、后端开发也应该考虑状态空间

例如订单：

```text
待支付
 ↓
已支付
 ↓
配送中
 ↓
已完成
```

但实际上还可能存在：

```text
待支付
 ↓
已取消

已支付
 ↓
退款中
 ↓
已退款
```

因此开发时不能只实现 Happy Path：

```text
创建 → 支付 → 完成
```

还需要检查：

```text
重复操作
非法状态操作
取消
失败
异常
权限不足
不存在的数据
```

------

# 二十八、状态机是开发阶段非常重要的参考

业务对象如果具有生命周期：

```text
订单
商品
退款
售后
团购
配送
```

都应该明确：

```text
当前状态
 ↓
允许执行的动作
 ↓
目标状态
```

例如：

```text
待支付
├── 支付 → 已支付
└── 取消 → 已取消
```

而：

```text
已完成
```

可能不允许：

```text
支付
取消
```

开发时：

> **不要只判断“这个按钮有没有”，还要判断“当前状态允许不允许执行这个动作”。**

------

# 二十九、权限应该在开发阶段真正落地

前端隐藏按钮：

```text
if (isAdmin) {
    显示删除按钮
}
```

并不代表真正安全。

因为用户仍然可以直接调用 API。

因此：

```text
前端权限
+
后端权限
```

都应该存在。

核心原则：

> **前端负责体验，后端负责真正的权限约束。**

------

# 三十、开发阶段必须重视幂等

一些操作不能因为用户重复点击就执行多次。

例如：

```text
创建订单
支付
提交申请
领取优惠券
确认收货
退款
```

可能出现：

```text
用户点击一次
 ↓
网络卡顿
 ↓
用户再次点击
 ↓
服务器收到两次请求
```

如果没有幂等机制，就可能：

```text
创建两个订单
扣两次库存
执行两次退款
```

因此对于重要业务操作：

> **重复请求应该有明确行为。**

------

# 三十一、异常不是开发结束之后才考虑

开发过程中不要只实现：

```text
成功
```

而应该同时考虑：

```text
成功
失败
不存在
无权限
状态不允许
重复操作
参数错误
系统异常
```

例如：

```text
删除商品
```

可能遇到：

```text
商品不存在
 ↓
商品已被删除
 ↓
商品正在参与订单
 ↓
用户无权限
 ↓
数据库异常
```

这些都属于产品行为的一部分。

------

# 三十二、开发阶段的测试应该分层

测试不应该只靠：

> “我点一下看看。”

可以分为：

### 1. 单元级

验证局部逻辑。

例如：

```text
价格计算
状态转换
权限判断
```

------

### 2. API 级

验证：

```text
请求
响应
参数
权限
异常
```

------

### 3. 业务链路级

验证：

```text
登录
 ↓
浏览
 ↓
购买
 ↓
订单
```

------

### 4. 前端交互级

验证：

```text
点击
输入
提交
跳转
状态
错误提示
```

------

### 5. MVP 验收

最终验证：

> **用户能不能真正完成核心业务。**

------

# 三十三、测试重点应该放在“业务链路”

假设购物流程：

```text
商品详情
 ↓
加入购物车
 ↓
购物车
 ↓
提交订单
 ↓
支付
 ↓
订单
```

不能只测试：

```text
商品页面 ✓
购物车页面 ✓
订单页面 ✓
```

还应该测试：

```text
商品选择是否正确
数量是否正确
价格是否正确
订单是否正确
库存是否正确
状态是否正确
支付后订单是否正确
```

因为：

> **真正的 Bug 经常发生在模块之间，而不是模块内部。**

------

# 三十四、开发完成 ≠ 功能完成

一个功能至少应该经过：

```text
代码完成
 ↓
能够启动
 ↓
接口可用
 ↓
前后端联通
 ↓
正常流程通过
 ↓
异常流程验证
 ↓
业务规则验证
 ↓
MVP 验收
```

因此：

> **“代码写完”只是开发过程中的一个节点。**

------

# 三十五、开发阶段的文档应该服务于开发

开发文档不应该变成：

> “为了写文档而写文档。”

真正有价值的文档应该帮助回答：

```text
这个功能是什么？
怎么调用？
数据是什么？
状态是什么？
依赖什么？
怎么测试？
```

例如 API 文档至少应该能让前端知道：

```text
接口地址
请求方式
参数
返回值
错误情况
权限要求
```

------

# 三十六、开发任务应该形成依赖图

例如：

```text
用户系统
   ↓
商品系统
   ↓
购物车
   ↓
订单
   ↓
支付
   ↓
订单状态
```

如果：

```text
订单依赖商品
```

那么通常应该先确保：

```text
商品数据
商品查询
商品状态
```

已经可用。

开发规划的核心之一就是：

> **消除任务之间的隐性依赖。**

------

# 三十七、不要为了“看起来完整”提前做后台

很多项目会先做：

```text
后台首页
Dashboard
统计图
用户管理
商品管理
订单管理
```

因为这些页面比较容易展示。

但如果用户核心业务：

```text
商品 → 购物车 → 订单
```

都没有打通，那么后台首页的统计图其实没有太大价值。

因此：

> **开发优先级应该由业务价值和依赖关系决定，而不是由页面展示效果决定。**

------

# 三十八、Demo、MVP 和正式产品不是一回事

这三个概念必须区分。

### 技术 Demo

证明：

> **技术方案能不能跑。**

例如：

```text
验证文件上传
验证支付接口
验证 WebSocket
验证 AI API
```

------

### MVP

证明：

> **核心产品业务能不能成立。**

例如：

```text
用户
 ↓
商品
 ↓
购买
 ↓
订单
```

------

### 正式版本

解决：

> **产品能否稳定、完整地服务真实用户。**

包括：

```text
性能
安全
异常
监控
运营
扩展
完整功能
```

因此：

> Demo ≠ MVP ≠ 正式产品。

------

# 三十九、MVP 开发应该允许“临时实现”

例如：

```text
真实支付 → Mock
真实短信 → 固定验证码
真实物流 → 模拟物流
复杂推荐 → 简单排序
```

这不是偷懒。

前提是：

> **临时实现不会破坏核心业务结构，并且未来能够被替换。**

例如：

```text
PaymentService
      ↓
MockPaymentService
```

以后：

```text
PaymentService
      ↓
RealPaymentService
```

这样就比较合理。

------

# 四十、避免为了 MVP 把架构写死

“先做 MVP”不代表：

> “随便写，之后全部重写。”

例如：

```text
所有代码都写在 Controller
所有逻辑都写在 Vue 页面
数据库字段随便设计
状态用各种魔法数字
```

短期可能很快。

后面会变成：

```text
改一个地方
 ↓
五个地方报错
```

因此：

> **MVP 可以简化，但不应该故意制造技术债。**

------

# 四十一、MVP 的“最小”应该是业务最小，不是代码最小

这是一个很重要的区别。

错误：

> “为了快速上线，把所有东西都写成几十行。”

正确：

> “只实现当前真正需要的业务能力，但实现方式保持基本合理。”

也就是说：

```text
功能范围可以小
技术质量不能无限降低
```

------

# 四十二、开发阶段的技术债

技术债不是绝对不能存在。

合理的技术债：

```text
暂时 Mock 支付
暂时不做复杂缓存
暂时使用简单搜索
暂时没有高级推荐
```

因为：

> 这些是有意识的范围控制。

危险的技术债：

```text
没有权限
没有事务
状态随便修改
重复提交没有处理
核心数据没有校验
数据库关系混乱
```

因为：

> 这些可能直接破坏业务正确性。

------

# 四十三、开发过程中发现问题时应该分类

发现问题后，不应该直接：

> “改代码。”

而应该先判断问题属于：

```text
产品问题
技术设计问题
原型问题
实现问题
```

例如：

### “订单可以取消吗？”

如果模块一没有定义：

> 产品问题。

------

### “订单状态怎么存？”

如果模块二没有明确：

> 技术设计问题。

------

### “取消按钮放哪里？”

如果模块三没有明确：

> 原型问题。

------

### “接口写错了。”

> 实现问题。

这种分类非常重要。

------

# 四十四、开发过程应该形成反馈闭环

理想情况：

```text
开发
 ↓
运行
 ↓
发现问题
 ↓
判断问题层级
 ↓
修复
 ↓
重新验证
 ↓
继续开发
```

而不是：

```text
开发两周
 ↓
最后一次运行
 ↓
发现大量问题
 ↓
不知道哪里出了问题
```

------

# 四十五、开发中的“回退机制”

四个模块虽然是递进的，但不是绝对单向。

例如：

```text
模块四开发
    ↓
发现业务规则缺失
    ↓
回模块一
    ↓
重新确认
    ↓
冻结
    ↓
重新进入模块二/三/四
```

或者：

```text
模块四
 ↓
发现技术方案无法实现
 ↓
回模块二
 ↓
重新设计
 ↓
重新验证
 ↓
回模块四
```

因此：

> **冻结不是永远不能修改，而是防止无意识地修改。**

------

# 四十六、开发规划应该有阶段目标

例如：

## 阶段一：项目骨架

```text
项目创建
数据库
基础配置
前后端启动
基础 API
```

目标：

> 项目能够正常启动。

------

## 阶段二：核心业务

```text
用户
商品
核心业务
```

目标：

> 核心业务链路开始形成。

------

## 阶段三：核心闭环

```text
核心操作
 ↓
业务对象生成
 ↓
结果查看
```

目标：

> MVP 主流程跑通。

------

## 阶段四：异常和权限

```text
权限
异常
状态
重复操作
```

目标：

> MVP 不只是 Happy Path。

------

## 阶段五：体验优化

```text
Loading
Empty
Error
交互
视觉
响应
```

目标：

> 从“能跑”变成“好用”。

------

# 四十七、每个阶段应该有验收条件

例如：

### 阶段一完成

```text
✓ 前端可以启动
✓ 后端可以启动
✓ 数据库可以连接
✓ 基础接口可以访问
```

------

### 阶段二完成

```text
✓ 用户可以登录
✓ 商品可以查询
✓ 商品可以展示
```

------

### 阶段三完成

```text
✓ 用户可以完成核心业务
✓ 数据能够正确保存
✓ 页面能够显示业务结果
```

------

### 阶段四完成

```text
✓ 权限正确
✓ 异常正确
✓ 非法状态操作被阻止
✓ 重复操作行为正确
```

------

# 四十八、开发规划应该避免“虚假的完成感”

例如：

```text
✓ 商品模块完成
```

但实际上：

```text
数据库 ✓
后端 ✓
前端 ✓
```

可是：

```text
前后端没联调
库存没处理
异常没处理
权限没处理
```

这不能算真正完成。

因此：

> **完成应该以“可验证的业务能力”为标准，而不是文件数量。**

------

# 四十九、代码生成的核心原则

AI 辅助开发时尤其容易出现：

> 一次生成大量代码。

这会导致：

- 上下文错误
- 文件之间不一致
- API 不一致
- 字段不一致
- 业务规则遗漏
- 用户难以理解
- 调试困难

因此更推荐：

```text
设计
 ↓
生成一个小功能
 ↓
运行
 ↓
检查
 ↓
修正
 ↓
继续
```

而不是：

```text
一次生成整个项目
```

------

# 五十、AI 开发尤其需要保持上下文一致

AI 在长项目中容易出现：

```text
前面叫 userId
后面突然叫 user_id

前面状态是 PAID
后面变成 PAYED

前面接口返回 data
后面返回 result
```

因此开发阶段应该保持：

> **命名、数据结构、接口结构、状态定义的一致性。**

这也是为什么前三个模块的冻结非常重要。

------

# 五十一、开发规划应该成为“唯一执行入口”

进入模块四后：

```text
需求文档
技术设计
原型
开发计划
```

共同构成开发依据。

其中：

> **开发计划负责告诉 AI 当前要做什么。**

例如：

```text
当前阶段：订单 MVP

当前任务：
实现订单创建

依赖：
商品
用户
购物车

完成标准：
订单可以创建并正确保存

下一任务：
订单查询
```

这样 AI 就不会每次重新思考整个项目。

------

# 五十二、当前任务应该有明确上下文

一个好的开发任务最好能够告诉 AI：

```text
项目背景
当前阶段
相关需求
相关技术设计
相关页面
当前任务
任务边界
依赖
完成标准
验证方式
```

这样 AI 才能：

> **局部工作，但保持全局一致。**

------

# 五十三、不要让 AI 每次都重新设计系统

开发阶段最忌讳：

```text
第一次：
这样设计。

第二次：
换一种设计。

第三次：
再换一种。
```

最终：

```text
数据库是一套
API 是第二套
前端是第三套
```

因此开发阶段应该强调：

> **执行已经确认的设计，而不是重复设计。**

------

# 五十四、但是也不能盲目执行错误设计

如果开发过程中发现：

```text
技术方案实际上无法实现
```

或者：

```text
两个模块之间存在冲突
```

不能为了“执行冻结设计”硬写。

应该：

```text
发现冲突
 ↓
停止继续扩大问题
 ↓
定位冲突来源
 ↓
返回对应模块
 ↓
修正
 ↓
重新冻结
 ↓
继续开发
```

------

# 五十五、MVP 的验收应该从用户任务出发

不要只问：

> “代码都写了吗？”

应该问：

> “用户现在能不能完成最重要的事情？”

例如：

```text
用户能否注册？
用户能否登录？
用户能否找到商品？
用户能否购买？
用户能否查看订单？
```

如果答案是：

> 能。

那么 MVP 才真正开始成立。

------

# 五十六、核心业务闭环示例

以一个典型电商系统为例：

```text
用户登录
    ↓
浏览商品
    ↓
查看详情
    ↓
加入购物车
    ↓
确认商品
    ↓
创建订单
    ↓
模拟支付
    ↓
订单状态变化
    ↓
查看订单
```

这条链路如果能够：

```text
真正运行
真正保存数据
真正产生状态变化
```

那么已经形成一个非常有价值的 MVP。

------

# 五十七、MVP 完成之后才进入扩展

例如：

```text
MVP
 ↓
优惠券
 ↓
评价
 ↓
收藏
 ↓
消息
 ↓
积分
 ↓
高级搜索
 ↓
统计分析
```

扩展功能应该建立在：

> **核心系统已经稳定运行**

的基础上。

否则很容易出现：

```text
核心系统还没稳定
 +
新功能不断加入
 =
Bug 指数增长
```

------

# 五十八、开发完成后的“回看”

一个 MVP 完成之后，应该进行一次整体回看：

```text
需求
 ↓
技术
 ↓
原型
 ↓
实现
```

检查四者是否一致。

例如：

```text
需求：用户可以取消订单
技术：存在取消状态
原型：存在取消操作
代码：真正实现取消
```

如果四个地方都对应：

> 说明链路完整。

------

# 五十九、最终一致性检查

可以形成：

```text
产品需求
    ↓
业务规则
    ↓
技术模型
    ↓
API
    ↓
前端
    ↓
交互
    ↓
数据库
    ↓
实际行为
```

任何一个地方出现：

```text
不一致
```

都可能产生 Bug。

因此：

> **软件真正的正确性不是某一个文件正确，而是整条链路一致。**

------

# 六十、开发阶段常见错误

## 错误 1：一次生成整个项目

问题：

> 很快，但很难验证。

------

## 错误 2：先把页面全部做完

问题：

> 页面很多，但业务不闭环。

------

## 错误 3：先做漂亮 UI

问题：

> 视觉完成度高，但核心业务没有验证。

------

## 错误 4：前后端最后才联调

问题：

> 问题集中爆发。

------

## 错误 5：只测试 Happy Path

问题：

> 一旦用户正常操作之外的行为发生，系统就崩。

------

## 错误 6：把 MVP 当残缺产品

问题：

> 为了快而破坏基本架构。

------

## 错误 7：开发过程中无限加需求

问题：

> MVP 永远无法完成。

------

## 错误 8：开发过程中偷偷改变需求

问题：

> 最终实现和产品设计不一致。

------

## 错误 9：代码完成就认为任务完成

问题：

> 没有经过运行、联调和验证。

------

## 错误 10：为了遵守旧设计而拒绝修正明显问题

问题：

> “冻结”变成了僵化。

正确方式：

> **发现问题 → 定位层级 → 回退 → 修正 → 重新冻结。**

------

# 六十一、开发规划 Checklist

开发开始前：

```text
□ 需求已经冻结
□ 技术设计已经冻结
□ 原型已经确认
□ MVP 范围明确
□ 核心业务闭环明确
```

# 六十二、模块四的经验总结

整个模块四可以浓缩成下面这条路径：

```text
已确认的产品
      ↓
已确认的技术
      ↓
已确认的原型
      ↓
确定 MVP
      ↓
拆解业务任务
      ↓
建立依赖关系
      ↓
选择开发顺序
      ↓
纵向切片实现
      ↓
小步运行
      ↓
前后端联调
      ↓
业务验证
      ↓
异常验证
      ↓
MVP 验收
      ↓
继续迭代
```

真正成熟的开发规划不是：

> **“告诉开发者要写哪些代码。”**

而是：

> **“告诉开发者应该以什么顺序，把什么业务能力真正变成可运行的软件。”**

------

# 六十三、模块四最重要的几个原则

### 原则一

> **先确定 MVP，再开始大规模开发。**

------

### 原则二

> **优先完成核心业务闭环，而不是优先完成最多页面。**

------

### 原则三

> **开发任务应该围绕业务能力，而不是围绕代码文件。**

------

### 原则四

> **小步开发，小步运行，小步验证。**

------

### 原则五

> **前后端应该尽早联调，而不是最后才联调。**

------

### 原则六

> **“代码写完”不等于“功能完成”。**

------

### 原则七

> **MVP 可以简化功能，但不能故意破坏基本技术结构。**

------

### 原则八

> **Mock 是为了降低外部依赖，不是为了制造假系统。**

------

### 原则九

> **开发阶段发现问题，要先判断问题属于哪个模块。**

------

### 原则十

> **冻结是为了防止无意识变化，不是为了阻止合理修正。**

------

### 原则十一

> **最终验收应该以用户能否完成核心任务为标准。**

------

### 原则十二

> **开发的最终目标不是生成代码，而是得到一个真正可运行、可验证的产品。**

------

# 六十四、模块四 Reference 的核心思想

如果前三个模块可以分别浓缩成：

> **模块一：把“想法”变成明确的产品。**

> **模块二：把“产品”变成可实现的技术方案。**

> **模块三：把“技术方案”变成用户可以看到和操作的原型。**

那么模块四就是：

> **把已经确认的产品、技术和原型，变成真正运行的软件。**

所以第四个模块最核心的一句话，我建议定成：

> **不要以“写完多少代码”衡量开发进度，而要以“完成了多少可运行、可验证的业务能力”衡量开发进度。**

以及整个四模块体系最后形成：

```text
模块一：定义正确的问题
        ↓
模块二：设计正确的解决方案
        ↓
模块三：验证用户看到的产品
        ↓
模块四：把它真正做出来*
```
