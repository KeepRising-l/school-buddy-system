# Skill：模块四——开发规划与 MVP 实现 V1

> **本 Skill 采用分层加载：先阅读本摘要即可开始工作；执行到具体环节时，再深入对应章节。**

## 0. 执行摘要（必读）

### 模块四是什么

把已确认的需求、技术设计和原型，转化为可执行的开发计划，并实现真正可运行的 MVP。

只回答「怎么真正做出来」，执行已确认的设计，不重新设计产品。

### 工作循环

```text
理解已确认的需求 / 技术 / 原型
    ↓
确定 MVP 范围与核心业务闭环
    ↓
识别依赖 → 拆解任务 → 确定顺序与阶段计划
    ↓
纵向切片：逐个实现业务能力
    ↓
实现 → 运行 → 验证 → 下一个切片
    ↓
前后端联调 → 业务验证
    ↓
MVP 验收
```

### 十条铁律

1. 执行已确认的设计，不重新设计产品；
2. 发现问题先判断层级：产品 / 技术 / 原型 / 实现，按层级回退处理；
3. MVP 以核心业务闭环为准，不以功能多少为准；
4. 禁止开发阶段偷偷扩大需求或修改冻结内容；
5. 采用纵向切片开发：每个切片是一个可运行的业务能力；
6. 任务必须有明确完成标准和验收方式；
7. 小步实现，小步验证，不一次性生成整个系统；
8. 冻结不是拒绝合理修正，修正需按流程重新确认（第 30 节）；
9. 代码写完 ≠ MVP 完成，必须可运行、联调、闭环、验证（第 36~37 节）；
10. MVP 验收必须由用户确认。

# 五、第一步：建立开发认知

开始开发之前，不要立即生成代码。

先建立当前项目的开发认知：

```text
项目是什么？
核心用户是谁？
核心业务是什么？
MVP 是什么？
技术架构是什么？
核心数据对象是什么？
核心页面是什么？
核心业务闭环是什么？
当前已经完成什么？
当前还缺什么？
```

必须能够回答：

> **现在这个项目到底处于什么状态？**

------

# 六、第二步：确定 MVP

不要直接把全部需求转换成开发任务。

先判断：

> **第一版真正需要完成什么？**

将功能划分为：

```text
P0：核心闭环
P1：核心体验
P2：增强功能
P3：后续功能
```

优先实现 P0。

------

# 七、MVP 必须形成核心闭环

找到项目最重要的业务链路。

例如：

```text
用户登录
 ↓
浏览商品
 ↓
查看商品
 ↓
加入购物车
 ↓
提交订单
 ↓
支付
 ↓
查看订单
```

这个链路如果是项目核心，就应该优先实现。

不要因为某些页面容易制作，就优先开发那些页面。

------

# 八、MVP 边界必须明确

输出：

```text
MVP 必须完成：
- xxx
- xxx
- xxx

MVP 可以简化：
- xxx
- xxx

MVP 暂不实现：
- xxx
- xxx
```

如果一个功能不属于 MVP，不要因为：

- 顺手
- 看起来简单
- “以后可能用到”
- AI 觉得应该有

就自动加入 MVP。

------

# 九、禁止开发阶段偷偷扩大需求

如果原需求是：

> 用户可以登录。

不能自行增加：

```text
微信登录
短信登录
第三方登录
找回密码
多因素认证
```

除非这些能力已经在前面的产品设计中确定，或者用户明确要求。

------

# 十、第三步：识别开发依赖

分析：

```text
功能 A
 ↓
依赖功能 B
 ↓
依赖数据 C
```

建立开发依赖关系。

例如：

```text
用户
 ↓
商品
 ↓
购物车
 ↓
订单
 ↓
支付
```

不要在依赖尚未建立的情况下，强行开发依赖它的功能。

------

# 十一、第四步：拆解开发任务

开发任务应以：

> **业务能力**

为主要拆分单位。

推荐：

```text
实现用户登录
实现商品浏览
实现购物车
实现订单创建
实现订单查询
```

不要主要拆成：

```text
写 Controller
写 Service
写 Mapper
写 Vue
```

技术层任务可以作为子任务存在，但不能成为整个开发计划的主要组织方式。

------

# 十二、任务粒度

一个任务应该：

- 足够小，可以独立完成
- 足够完整，可以独立验证
- 有明确输入
- 有明确输出
- 有明确完成标准

例如：

### 不推荐

> 完成订单模块。

### 推荐

> 实现用户提交购物车商品并创建订单。

完成标准：

```text
商品信息正确
数量正确
金额正确
订单生成
订单状态正确
数据正确保存
前端能够显示订单结果
```

------

# 十三、每个开发任务都必须具有完成标准

任务至少应该明确：

```text
任务名称
任务目标
前置依赖
涉及模块
需要修改的内容
完成标准
验证方式
```

例如：

```text
任务：实现订单创建

目标：
用户可以从购物车提交订单。

依赖：
用户
商品
购物车

完成标准：
1. 能创建订单
2. 商品数量正确
3. 金额正确
4. 订单状态正确
5. 数据正确保存
6. 前端可以获得订单结果

验证：
完成一次完整下单流程。
```

------

# 十四、第五步：确定开发阶段

将任务组织为若干阶段。

例如：

```text
阶段一：项目基础设施
阶段二：用户系统
阶段三：核心业务
阶段四：MVP 闭环
阶段五：异常与权限
阶段六：体验优化
阶段七：扩展功能
```

每个阶段都必须有：

> **明确目标 + 明确任务 + 明确验收标准。**

------

# 十五、阶段必须可验证

不要定义：

> “本周完成用户模块。”

应该定义：

> “本阶段完成后，用户能够注册、登录，并保持登录状态。”

也就是说：

> **阶段结束必须能够验证结果。**

------

# 十六、第六步：采用纵向切片开发

尽量围绕完整业务能力开发：

```text
数据库
 ↓
后端业务
 ↓
API
 ↓
前端数据层
 ↓
页面
 ↓
交互
 ↓
联调
 ↓
验证
```

不要长期让某一层完全脱离其他层独立发展。

------

# 十七、开发时保持小步可运行

禁止无必要地一次生成大量代码。

推荐：

```text
实现一个小能力
 ↓
启动
 ↓
检查
 ↓
测试
 ↓
修复
 ↓
继续
```

尤其对于：

- 数据库
- 状态
- 权限
- 事务
- 核心业务逻辑
- 前后端接口

应优先采用小步开发。

------

# 十八、每次开发后都要验证

完成一个重要功能后，至少判断：

```text
代码是否正确？
项目能否启动？
接口是否可用？
数据是否正确？
前端是否能够调用？
正常流程是否通过？
```

不要把问题积累到最后统一处理。

------

# 十九、第七步：尽早前后端联调

一个 API 完成后，应尽早让真实前端接入。

检查：

```text
请求参数
响应结构
字段名称
数据类型
状态码
异常结构
分页
权限
空数据
```

发现不一致时立即修复。

------

# 二十、禁止长期使用与真实系统完全不同的 Mock

Mock 可以使用，但必须尽量模拟真实系统：

```text
真实请求结构
真实响应结构
真实业务状态
真实错误情况
```

不要让 Mock 自己形成一套完全不同的系统。

------

# 二十一、外部依赖可以阶段性 Mock

如果某个外部服务暂时无法接入：

```text
支付
短信
地图
物流
第三方登录
AI 服务
```

可以先 Mock。

但需要明确：

```text
当前：
Mock

未来：
真实服务
```

并尽量保证接口边界一致。

------

# 二十二、第八步：开发业务状态

开发时必须落实业务对象的状态。

例如：

```text
订单：
待支付
已支付
配送中
已完成
已取消
```

实现每个状态允许的操作。

例如：

```text
待支付
├── 支付
└── 取消

已完成
└── 不允许再次支付
```

不能只根据按钮是否显示判断状态。

------

# 二十三、禁止非法状态操作

例如：

```text
已取消订单
```

不能因为有人直接调用 API，就重新执行支付。

后端必须判断：

```text
当前状态
+
当前操作
=
是否合法
```

------

# 二十四、第九步：开发权限

权限必须至少形成：

```text
前端体验控制
+
后端真实权限控制
```

前端可以：

```text
隐藏按钮
禁止普通用户进入页面
```

但真正的权限判断必须在后端完成。

------

# 二十五、第十步：处理重复操作

对于重要业务操作：

```text
创建订单
支付
退款
领取
提交
确认
```

必须考虑重复请求。

判断：

> 用户重复点击、网络重试或重复请求时，系统应该发生什么？

对于需要幂等的操作，应采用合适的幂等策略。

------

# 二十六、第十一步：开发异常流程

不要只实现：

```text
成功
```

还要验证：

```text
参数错误
数据不存在
无权限
状态不允许
重复操作
业务失败
系统异常
```

------

# 二十七、第十二步：开发页面状态

核心页面至少检查：

```text
Loading
Success
Empty
Error
```

如果存在权限控制，还需要：

```text
No Permission
```

按钮操作还应考虑：

```text
可操作
提交中
成功
失败
```

------

# 二十八、第十三步：保持全链路一致

开发过程中持续检查：

```text
需求
 ↓
业务规则
 ↓
技术设计
 ↓
数据库
 ↓
API
 ↓
前端
 ↓
页面交互
 ↓
实际行为
```

任何一层出现冲突，都必须处理。

------

# 二十九、发现前置设计问题时的处理

如果发现问题，不允许直接偷偷修改。

先分类：

```text
产品问题？
技术设计问题？
原型问题？
实现问题？
```

然后：

### 产品问题

返回模块一重新确认。

### 技术问题

返回模块二重新设计。

### 原型问题

返回模块三重新确认。

### 实现问题

直接在模块四修复。

------

# 三十、禁止因为“已经冻结”而拒绝修正

冻结的目的：

> 防止无意识修改。

不是：

> 禁止发现问题之后修正。

如果发现设计确实存在问题：

```text
发现问题
 ↓
定位层级
 ↓
回到对应模块
 ↓
重新确认
 ↓
重新冻结
 ↓
继续开发
```

------

# 三十一、第十四步：测试业务闭环

不能只测试：

```text
页面能打开
接口返回 200
```

必须测试核心业务链路。

例如：

```text
登录
 ↓
浏览商品
 ↓
加入购物车
 ↓
创建订单
 ↓
支付
 ↓
查看订单
```

整个链路应该真正运行。

------

# 三十二、测试 Happy Path

首先保证：

> 用户按照正常预期操作，可以顺利完成核心任务。

------

# 三十三、测试 Branch Path

然后测试：

```text
取消
返回
修改
重新提交
不同状态
不同权限
```

------

# 三十四、测试 Error Path

再测试：

```text
网络错误
参数错误
数据不存在
权限不足
业务冲突
服务器异常
```

------

# 三十五、测试重复操作

重点检查：

```text
重复点击
重复提交
重复请求
刷新
返回
重新进入页面
```

是否会造成错误数据。

------

# 三十六、第十五步：MVP 验收

MVP 验收不能只检查：

```text
□ 代码写完
□ 页面做完
□ API 写完
```

必须检查：

```text
□ 核心业务闭环完成
□ 数据正确
□ 状态正确
□ 权限正确
□ 异常行为合理
□ 前后端真正联通
□ 核心页面交互正确
□ 用户能够完成核心任务
```

------

# 三十七、MVP 验收标准

最终判断：

> **如果把所有非核心功能都拿掉，剩下的产品是否仍然能够完成核心价值？**

如果答案是：

> 能。

则 MVP 基本成立。

如果答案是：

> 不能。

则应该继续完善核心闭环，而不是继续增加外围功能。

------

# 三十八、第十六步：MVP 后再扩展

MVP 验收通过后，再按照优先级开发：

```text
P1
 ↓
P2
 ↓
P3
```

不要在 MVP 尚未稳定之前无限加入新功能。

------

# 三十九、开发阶段的变更控制

遇到新想法时：

```text
这是代码优化？
这是技术优化？
这是技术设计变化？
这是产品需求变化？
```

### 代码优化

通常可以直接执行。

### 技术实现优化

确认不改变技术设计目标后，可以执行。

### 技术设计变化

返回模块二评估。

### 产品需求变化

返回模块一评估。

------

# 四十、当前任务原则

任何时刻都应该明确：

```text
当前阶段：
当前任务：
任务目标：
前置依赖：
完成标准：
验证方式：
```

不要在没有明确当前任务的情况下无限扩展工作范围。

------

# 四十一、开发任务执行原则

执行当前任务时：

1. 先理解任务
2. 检查依赖
3. 检查相关设计
4. 修改必要代码
5. 运行项目
6. 验证功能
7. 修复问题
8. 更新任务状态
9. 再进入下一任务

------

# 四十二、禁止“假完成”

以下情况不能直接标记任务完成：

```text
代码已经写出来
```

或者：

```text
文件已经创建
```

必须至少满足：

```text
实现
+
运行
+
验证
```

对于核心业务，还需要：

```text
联调
+
业务链路验证
```

------

# 四十三、开发状态管理

推荐使用：

```text
待开发
 ↓
开发中
 ↓
待验证
 ↓
验证中
 ↓
已完成
```

如果发现问题：

```text
验证中
 ↓
发现问题
 ↓
开发中
```

不要把有明显问题的任务继续标记为完成。

------

# 四十四、推荐的开发任务结构

每个任务可以采用：

```text
## TASK-001 用户登录

### 目标
实现用户登录能力。

### 前置依赖
- 用户数据模型
- 用户认证方案

### 实现范围
- 登录 API
- 身份验证
- 前端登录页面
- 登录状态保存

### 不包含
- 第三方登录
- 找回密码

### 完成标准
- 用户能够正常登录
- 错误账号能够得到正确提示
- 登录状态能够保持
- 未登录用户不能访问受保护资源

### 验证
- 正常登录
- 错误密码
- 不存在用户
- 未登录访问
```

------

# 四十五、AI 生成代码时的行为

AI 生成代码前应先确认：

```text
要改哪些文件？
为什么改？
依赖哪些已有代码？
是否与现有接口一致？
是否与数据模型一致？
是否与原型交互一致？
```

不要为了实现一个功能：

> 无必要地重构整个项目。

------

# 四十六、优先局部修改

如果一个功能只需要：

```text
3 个文件
```

不要无理由修改：

```text
20 个文件。
```

修改范围越小：

> 越容易验证，越不容易引入回归问题。

------

# 四十七、代码质量原则

MVP 阶段允许：

- 功能简化
- 外部服务 Mock
- 部分高级能力暂缓

但不能故意：

- 破坏数据一致性
- 绕过权限
- 混乱状态
- 删除必要校验
- 把核心逻辑全部堆在一个地方
- 制造无法维护的代码

原则：

> **功能范围可以小，基本结构不能乱。**

------

# 四十八、回归验证

修改一个功能之后，要考虑：

> **它会不会影响之前已经完成的功能？**

尤其检查：

```text
数据库
API
状态
权限
公共组件
公共工具
公共接口
```

如果修改的是公共部分，应进行相应回归验证。

------

# 四十九、模块四的最终输出

模块四最终应形成：

```text
开发规划
MVP 范围
功能优先级
开发阶段
开发任务
任务依赖
任务完成标准
实际代码
运行结果
联调结果
测试结果
问题记录
MVP 验收结果
后续迭代计划
```

------

# 五十、模块四完成条件

当满足以下条件时，认为模块四的 MVP 阶段完成：

```text
□ MVP 范围已经明确
□ 核心业务闭环已经确定
□ 开发任务已经拆解
□ 开发依赖已经明确
□ 核心业务已经实现
□ 前后端已经联调
□ 数据能够正确保存
□ 核心状态正确
□ 权限正确
□ 主要异常流程已经验证
□ 重复操作已经验证
□ 核心页面状态已经验证
□ MVP 核心业务能够完整运行
□ 用户可以完成核心任务
```

------

# 五十一、模块四完成后的进入条件

当 MVP 验收通过后：

```text
模块四 MVP
      ↓
MVP 验收
      ↓
用户确认
      ↓
进入后续迭代
```

后续迭代仍然遵循：

```text
需求变化
 → 模块一

技术变化
 → 模块二

交互变化
 → 模块三

实现变化
 → 模块四
```

------

# 五十二、四模块协作规则

整个系统必须保持：

```text
模块一
定义产品事实
        ↓
模块二
把产品事实变成技术方案
        ↓
模块三
把方案变成用户可见的交互
        ↓
模块四
把确认后的方案真正实现
```

因此：

> **模块四不得成为新的需求分析阶段。**

也不得成为：

> **新的技术设计阶段。**

更不能成为：

> **边开发边随意修改产品的阶段。**

------

# 五十三、核心原则总结

必须始终遵守：

> **先确定 MVP，再开始大规模开发。**

> **优先完成核心业务闭环，而不是最多的页面。**

> **开发任务围绕业务能力，而不是代码文件。**

> **小步开发，小步运行，小步验证。**

> **尽早联调，不要最后联调。**

> **代码完成不等于功能完成。**

> **MVP 可以简化功能，但不能故意破坏基本结构。**

> **Mock 用来降低外部依赖，而不是制造假系统。**

> **发现问题先判断层级，再决定在哪里修改。**

> **冻结是为了控制变化，不是为了阻止合理修正。**

> **最终以用户能否完成核心任务判断 MVP 是否成立。**

------

# 五十四、模块四最终原则

整个 Skill 最终可以浓缩为：

> **不要从“我要写哪些代码”开始开发，而要从“我要让哪个业务能力真正运行起来”开始开发。**

开发的目标不是：

> **生成代码。**

而是：

> **把已经确认的产品、技术和交互，逐步变成一个真实可运行、可验证、可迭代的软件。**

------

这样，四个 Skill 就完整闭环了：

```text
01 Skill：需求规划
        ↓
      做什么？

02 Skill：技术设计
        ↓
      怎么做？

03 Skill：交互原型与视觉验证
        ↓
      用户看到什么、怎么操作？

04 Skill：开发规划与 MVP 实现
        ↓
      怎么真正做出来？
```

而四个 Reference 则负责不断往这四个 Skill 背后补充**经验、案例、原则和踩坑记录**。

**这时候你的整个体系已经不是“一个开发 Prompt”，而是一个完整的分阶段 AI 软件开发工作流了。**
