# AI 软件开发工作流

> 一套面向 AI 协作开发的软件工程工作流，通过「总控 + 四个专业模块 + Reference + 项目状态 + Git」将需求、技术、交互和开发串成一个完整闭环。

---

## 一、这是什么？

这是一个用于指导 AI 参与软件开发的结构化工作流。

如果你是第一次使用，请先阅读 **[使用指南.md](使用指南.md)**——它告诉你如何启动项目、如何配合 AI、如何触发冻结与验收。

它不是单纯的：

> 「告诉 AI 我要做什么 → AI 直接写代码」

而是将软件开发拆分为四个相互衔接的阶段：

```text
需求规划
   ↓
技术设计
   ↓
交互原型与视觉验证
   ↓
开发规划与 MVP 实现
```

并通过一个独立的：

> **00_总控**

负责管理整个项目的阶段推进、冻结、回退、变更和 AI 之间的上下文交接。

整个系统的核心目标是：

> **让 AI 在开发软件时，不依赖漫长的聊天历史，而是依赖明确的规则、已经确认的事实、阶段产物和项目状态持续工作。**

# 三、00_总控是什么？

`00_总控` **不是第五个业务开发模块**。

它是整个工作流的：

> **流程编排与状态控制层**

总控不负责直接完成专业工作。

它不负责：

- 分析具体需求
- 设计数据库
- 设计系统架构
- 绘制具体原型
- 编写具体业务代码

这些事情分别由四个专业模块完成。

总控负责：

- 判断项目当前处于哪个阶段
- 判断是否可以进入下一阶段
- 调度正确的模块
- 管理阶段冻结
- 管理阶段回退
- 处理跨阶段问题
- 管理变更传播
- 管理项目状态
- 管理 AI 之间的上下文交接
- 协调 Git 与项目状态
- 防止 AI 在没有依据的情况下自行修改项目事实

可以简单理解为：

> **总控负责管流程，模块负责干活。**

------

# 四、四个专业模块

## 01_需求规划

### 回答的问题

> **做什么？**

负责确定产品需求和业务规则。

主要解决：

- 产品到底要做什么
- 用户有哪些角色
- 用户可以做什么
- 核心业务流程是什么
- 业务对象有哪些
- 对象之间是什么关系
- 对象生命周期是什么
- 权限如何影响业务行为
- 异常和分支如何处理
- 删除、恢复、历史等行为如何定义
- 哪些事情已经确定
- 哪些事情仍然存在业务歧义

核心原则：

> **需求规划不是把问题问完，而是把会影响产品行为的未知数消灭掉。**

------

## 02_技术设计

### 回答的问题

> **怎么做？**

负责将已经确认的产品需求转化为可实现的技术方案。

主要解决：

- 技术栈
- 系统架构
- 模块划分
- 数据模型
- 对象关系
- API
- 权限
- 状态机
- 事务
- 幂等
- 历史快照
- 前后端协作
- 异常处理
- 技术风险
- 高风险技术验证
- Demo 验证

核心原则：

> **先理解，再推导；先验证，再决策。**

技术设计不是技术名词的堆积，而是：

> **业务规则的技术落地。**

------

## 03_交互原型与视觉验证

### 回答的问题

> **用户将看到什么？怎么操作？**

负责在真正开发之前，将产品需求和技术方案转化为用户可以理解、检查和修改的交互原型。

核心层级：

```text
产品
 ↓
用户端 / 管理端
 ↓
页面
 ↓
页面组件
 ↓
交互
```

主要输出：

- 产品原型结构
- 用户端 / 管理端划分
- 页面清单
- 页面 Wireframe
- 页面组件
- 页面跳转关系
- 点击行为
- 输入行为
- 提交行为
- 成功 / 失败状态
- 核心业务流程

核心要求：

> **必须明确“点击哪里 → 跳转到哪里 / 发生什么”。**

这一阶段重点不是做漂亮的 UI，而是：

> **在开发开始之前消除用户对界面和交互的理解不确定性。**

------

## 04_开发规划与 MVP 实现

### 回答的问题

> **怎么真正做出来？**

负责将前三个阶段已经确认的内容转化为真正可执行的开发计划，并最终实现 MVP。

主要负责：

- MVP 范围确定
- 核心业务闭环识别
- 开发任务拆解
- 任务依赖关系
- 开发顺序
- 阶段计划
- 业务切片实现
- 前后端联调
- 运行验证
- 异常验证
- 权限验证
- 状态验证
- MVP 验收

核心原则：

> **执行已经确认的设计，而不是重新设计产品。**

开发的基本单位不是：

> “我要写哪些文件？”

而是：

> **“我要让哪个业务能力真正运行起来？”**

------

# 五、Skill 与 Reference

每个专业模块都有两个文件：

```text
Skill
Reference
```

两者不是重复内容。

## Skill

Skill 负责：

> **规定 AI 应该怎么工作。**

例如：

- 工作流程
- 判断规则
- 什么时候询问用户
- 什么时候自己决定
- 什么时候必须验证
- 阶段完成条件
- 阶段边界
- 禁止行为

Skill 是：

> **行为规则。**

------

## Reference

Reference 负责：

> **提供 AI 工作时可以参考的经验知识。**

例如：

- 常见设计模式
- 历史案例
- 常见问题
- 风险
- 实践经验
- 设计原则
- 技术经验
- 失败案例

Reference 是：

> **经验知识。**

------

## 两者关系

```text
Skill
 ↓
告诉 AI「应该怎么工作」

Reference
 ↓
告诉 AI「有哪些经验可以参考」
```

因此：

> **Skill 是规则，Reference 是经验。**

Reference 中的经验不应该全部硬编码进 Skill。

只有那些已经被长期实践证明：

- 稳定
- 通用
- 必须遵守

的经验，才适合逐渐进入 Skill。

------

# 六、项目状态

`00_总控` 中还有一个非常重要的文件：

```text
项目状态.md
```

它是：

> **整个项目的当前状态中枢与 AI 交接记录。**

它不是：

- 完整需求文档
- 技术设计文档
- 原型文档
- 开发日志
- 聊天记录

而是记录：

> **“这个项目现在到底进行到哪里了？”**

以及：

> **“如果换一个 AI，它最少需要知道什么才能继续？”**

------

## 项目状态主要记录

```text
当前阶段
四模块状态
阶段冻结状态
已确认事实
关键决策
未决事项
阻塞问题
当前工作上下文
最近重要变更
Git 状态
阶段产物
AI 接手信息
下一步行动
```

其中最重要的是：

### 已确认事实

只有真正确定的项目事实才能进入这里。

例如：

```text
F-001

内容：
订单必须保存商品历史信息。

来源：
模块一需求冻结

状态：
已确认
```

------

### 未决事项

没有确定的事情必须明确标记。

例如：

```text
U-001

问题：
用户取消订单是否存在时间限制？

状态：
待确认

影响：
模块一

处理：
不得自行决定
```

------

### AI 推测

AI 可以提出推测，但：

> **推测不能自动变成项目事实。**

例如：

```text
AI 推测：
可能需要限制订单取消时间。

状态：
AI 推测

注意：
未经用户确认，不得写入已确认事实。
```

------

# 七、为什么需要项目状态？

因为：

> **聊天记录不是可靠的项目状态存储。**

如果整个项目一直由同一个 AI 从头做到尾，AI 可能会：

- 遗忘早期决策
- 混淆已经确认和没有确认的内容
- 错误理解上下文
- 根据常见经验自行补充需求
- 把自己的推测当成事实
- 在后续阶段偷偷改变之前的设计

因此，本工作流不把：

> **“聊天记忆”**

作为项目唯一事实来源。

而是建立：

```text
Skill
  ↓
工作规则

项目状态
  ↓
当前状态

项目产物
  ↓
已经确定的详细内容

Git
  ↓
历史版本

当前对话
  ↓
临时工作上下文
```

形成多层项目记忆。

------

# 八、Git 的作用

本工作流默认所有项目都使用 Git。

Git 不只是代码版本控制工具。

在整个工作流中：

> **项目状态负责记录“现在”，Git 负责记录“过去”。**

因此：

```text
项目状态.md
    ↓
当前项目状态

项目产物
    ↓
当前设计事实

Git
    ↓
历史变化
```

三者共同保证项目能够持续交接。

------

## 阶段冻结可以对应 Git

例如：

```text
freeze(module-1): requirements confirmed

freeze(module-2): technical design confirmed

freeze(module-3): prototype confirmed

mvp: core business flow completed
```

这样可以在 Git 历史中明确看到：

> 哪个阶段什么时候被确认过。

------

## 项目状态也应该进入 Git

`项目状态.md` 不应该被当成临时文件。

它属于项目的一部分。

因此：

> **项目状态.md 应该和代码、需求、技术设计、原型等一起进入 Git。**

------

# 九、阶段冻结机制

整个工作流不是简单的：

```text
A → B → C → D
```

而是：

```text
模块一
 ↓
需求闸门
 ↓
模块二
 ↓
技术闸门
 ↓
模块三
 ↓
原型闸门
 ↓
模块四
 ↓
MVP 验收
```

------

## 为什么需要冻结？

因为后面的 AI 很容易在开发过程中重新解释前面的内容。

例如：

模块一已经确定：

> 商品库存必须参与订单业务。

到了模块四，AI 却突然认为：

> “这个功能其实没必要，可以删掉。”

这就属于未经控制的需求变化。

冻结机制用于建立：

> **当前阶段的有效基线。**

------

## 冻结不是永久锁死

如果后续发现：

- 产品需求本身有问题
- 技术方案无法实现
- 原型与业务冲突
- 开发过程中发现前面存在严重遗漏

不能硬着头皮继续。

应该：

```text
发现问题
 ↓
判断问题属于哪个阶段
 ↓
返回对应模块
 ↓
重新确认
 ↓
重新冻结
 ↓
继续推进
```

因此：

> **冻结不是禁止修改，而是禁止未经控制的修改。**

------

# 十、问题回退机制

发现问题后，不应该直接修改任何东西。

首先判断：

### 产品问题

例如：

- 业务规则错误
- 产品边界错误
- 用户行为定义错误

返回：

```text
01_需求规划
```

------

### 技术问题

例如：

- 数据模型错误
- API 设计错误
- 架构方案无法实现
- 技术验证失败

返回：

```text
02_技术设计
```

------

### 原型问题

例如：

- 页面结构不合理
- 页面跳转错误
- 交互与需求不一致

返回：

```text
03_交互原型与视觉验证
```

------

### 实现问题

例如：

- Bug
- 前后端联调问题
- 代码错误
- 测试失败

留在：

```text
04_开发规划与 MVP 实现
```

------

# 十一、标准工作流

一个全新的项目通常按照下面的方式开始：

```text
用户提出产品想法
        ↓
00_总控识别项目状态
        ↓
01_需求规划
        ↓
需求确认
        ↓
需求冻结
        ↓
02_技术设计
        ↓
技术方案验证
        ↓
技术确认
        ↓
技术冻结
        ↓
03_交互原型与视觉验证
        ↓
Wireframe
        ↓
用户修改
        ↓
核心交互确认
        ↓
原型冻结
        ↓
04_开发规划与 MVP 实现
        ↓
确定 MVP
        ↓
拆解任务
        ↓
逐个实现业务能力
        ↓
前后端联调
        ↓
业务验证
        ↓
MVP 验收
        ↓
继续迭代
```

# 十二、不是所有项目都必须从模块一开始

总控应该能够接管已经存在的项目。

如果项目只有代码、从未使用本工作流，则进入总控第 6.2 节的「存量项目重构模式」：AI 先盘点现状，反向生成需求 / 技术设计 / 全页面 Wireframe 三份草稿，经你确认冻结后再开发（详见使用指南场景 6）。

例如：

```text
已有完整需求
        ↓
直接进入模块二
```

或者：

```text
已有需求 + 技术设计
        ↓
直接进入模块三
```

甚至：

```text
已有完整设计 + 原型
        ↓
直接进入模块四
```

但是在接管已有项目时，AI 必须先：

```text
读取项目状态
 ↓
识别当前阶段
 ↓
检查已有产物
 ↓
检查 Git
 ↓
确认当前基线
 ↓
再继续工作
```

而不是：

> “看起来应该是这样。”

------

# 十三、AI 接手项目

当新的 AI 接管项目时，推荐按照以下顺序读取：

```text
① 读取项目状态.md

② 判断当前项目阶段

③ 阅读当前阶段 Skill

④ 阅读对应 Reference

⑤ 阅读当前阶段项目产物

⑥ 检查 Git 当前状态

⑦ 阅读项目状态中的当前工作上下文

⑧ 继续当前工作
```

如果发现：

```text
项目状态
    ≠
项目产物
```

不能自行选择一个相信。

应该进入：

> **冲突处理流程**

找到冲突所属阶段，重新确认并重新冻结。

# 十六、核心设计思想

这套工作流最核心的不是“四个文件夹”。

真正重要的是：

> **将软件开发中的不同类型的不确定性分层解决。**

------

## 第一层：产品不确定性

解决：

> 到底做什么？

由：

```text
01_需求规划
```

负责。

------

## 第二层：技术不确定性

解决：

> 到底怎么实现？

由：

```text
02_技术设计
```

负责。

------

## 第三层：交互不确定性

解决：

> 用户到底看到什么、怎么操作？

由：

```text
03_交互原型与视觉验证
```

负责。

------

## 第四层：执行不确定性

解决：

> 怎么把已经确认的东西真正做出来？

由：

```text
04_开发规划与 MVP 实现
```

负责。

------

## 第五层：流程不确定性

解决：

> 现在应该做什么？出了问题应该回哪里？

由：

```text
00_总控
```

负责。

------

# 十七、最终工作模型

整个系统可以浓缩成：

```text
                ┌───────────────┐
                │    总控 Skill   │
                │   管理整个流程   │
                └───────┬───────┘
                        │
        ┌───────────────┼───────────────┐
        │               │               │
        ▼               ▼               ▼
      Skill          Reference       项目状态
        │               │               │
      规则             经验             当前状态
        │               │               │
        └───────────────┼───────────────┘
                        │
                        ▼
                 项目专业模块
                        │
                        ▼
                    项目产物
                        │
                        ▼
                       Git
                        │
                        ▼
                   历史版本
```

最终形成：

```text
规则
 ↓
经验
 ↓
当前状态
 ↓
专业工作
 ↓
项目产物
 ↓
Git 历史
```

------

# 十八、这套工作流最重要的原则

### 1. 先理解，再行动

AI 不应该在没有理解项目状态之前直接开始工作。

------

### 2. 先确定，再实现

没有确认的产品规则，不应该直接进入实现。

------

### 3. 能自己决定的，不要打扰用户

普通实现细节由 AI 自主决定。

真正影响产品、成本、安全、隐私、外部依赖或长期架构的决策，再请求用户确认。

------

### 4. 技术服务于产品

不能为了技术方案方便而偷偷改变产品需求。

------

### 5. 用户确认是重要边界

AI 的推测不能自动变成用户的决定。

------

### 6. 阶段之间必须有边界

后续阶段不能无意识地修改前面的设计。

------

### 7. 发现问题就回到正确的阶段

不要在错误的层级上打补丁。

------

### 8. 当前状态与历史状态分离

```text
项目状态 → 现在

Git → 过去
```

------

### 9. 聊天不是唯一记忆

真正重要的信息应该进入：

```text
项目状态
项目产物
Git
```

------

### 10. 小步推进，小步验证

不要一次生成整个系统再发现问题。

应该：

```text
一个业务能力
 ↓
实现
 ↓
运行
 ↓
验证
 ↓
继续下一个
```

------

# 十九、最终目标

这套工作流最终希望实现的不是：

> **让 AI 写更多代码。**

而是：

> **让 AI 能够像一个真正的软件开发团队一样，有规则、有状态、有边界、有验证、有历史地持续完成一个项目。**

最终形成：

```text
用户
 ↓
产品需求
 ↓
业务规则
 ↓
技术方案
 ↓
交互原型
 ↓
开发计划
 ↓
MVP
 ↓
验证
 ↓
迭代
```

同时保证：

```text
总控
    管流程

Skill
    管行为

Reference
    提供经验

项目状态
    管当前状态

项目产物
    保存项目事实

Git
    保存历史

当前对话
    处理临时工作
```

------

# 二十、一句话总结

> **这是一套让 AI 从“聊天式写代码”走向“有状态、有边界、有验证、可交接的软件工程协作”的开发工作流。**

核心链路：

```text
定义 → 落地 → 原型验证 → 执行
```

核心架构：

```text
总控 + 四模块 + Skill + Reference + 项目状态 + Git
```

核心原则：

> **总控负责管流程，模块负责干活，Reference 负责提供经验，项目产物负责留下结果，项目状态负责记录当前状态，Git 负责记录项目历史。**
