# 校园兴趣搭子预约系统 - 项目不足与改进方向

| 文档属性 | 内容 |
|---------|------|
| 项目名称 | 校园兴趣搭子预约系统（School Buddy） |
| 文档版本 | V1.1 |
| 编写日期 | 2026-09-01 |
| 文档目的 | 梳理系统当前存在的不足与可优化方向，作为后续迭代及毕设答辩的参考 |

> **说明**：本文档从**功能完整性、性能、安全、架构、用户体验、工程化**六个维度，客观分析本项目存在的不足与改进方向。
> 这些内容在毕设答辩中可作为"未来工作"或"不足与展望"部分的素材，体现对项目的深入思考。

## 一、功能完整性不足

### 1.1 社交关系链缺失

当前系统没有"好友"或"关注"机制，用户之间无法建立社交关系。主要影响：

- 推荐算法只能基于兴趣标签匹配，缺少社交关系维度（好友发布的、好友报名的）
- 用户无法主动查看感兴趣的人发布了什么组局
- 缺少社交传播路径，组局扩散完全依赖广场曝光

**改进方向**：增加关注/粉丝关系，推荐算法中加入社交权重（好友发布的组局权重更高），个人主页增加"关注"按钮。

### 1.2 即时通讯能力缺失

用户报名后，发布者和参与者之间缺少线上沟通渠道。当前只能看到对方昵称和头像，无法私聊。

- 组局前：参与者之间无法提前沟通细节（比如在哪见面、带什么东西）
- 组局后：缺少联系方式，评价完全依赖系统内文字

**改进方向**：接入 WebSocket 实现简单私聊，或至少提供"群组聊天"功能（一个组局一个群）。考虑到毕设复杂度，也可以用"发布公告"功能替代——发布者可以发公告，所有报名者可见。

### 1.3 地理位置能力较弱

当前"地点"只是文本字段，没有地图能力：

- 用户只能手动输入地点，没有位置选择器
- 无法按距离排序组局（"附近的组局"）
- 无法在地图上查看活动位置

**改进方向**：接入高德/百度地图 SDK，地点选择改为地图选点，增加"附近的组局"排序维度。

### 1.4 消息通知只有站内信，没有推送

当前通知只能在用户打开 App 时在"消息中心"看到，没有主动推送能力：

- 报名通过了，用户不知道，可能错过活动
- 组局被取消了，用户可能到了现场才发现

**改进方向**：接入短信通知（关键节点通知）或微信公众号模板消息。毕设阶段至少可以加个浏览器通知（Notification API）。

### 1.5 ~~评价体系比较单薄~~ ⚠️ 部分已解决（评价回复已实现）

> **现状**：互评其实**已双向打通**（V1.1）——发布者可评价已出勤参与者、参与者也可评价发布者，`ReviewPage.vue` 与 `submitReview` 均支持两端。本文档原写的"只有发布者能评价参与者"已过时。随后补上了唯一缺口「评价回复」。

当前仍可增强：

- **评价回复**：被评价者在"个人主页→收到的评价"中可回复/解释评价（V1.4 已实现，新增 `reply_content / reply_time` 字段 + `POST /api/review/reply` 端点，`ReviewServiceImpl.replyReview`）。
- **评价举报**：恶意差评没有申诉渠道（未实现）
- **评价与信誉分联动不够深**：当前只有出勤/违约影响信誉分，评价本身不影响（未实现）

### 1.6 ~~没有运营后台的核心数据看板~~ ✅ 已实现（V1.2/V1.3）

> **现状**：本节所列能力均已在运营后台落地，可作为答辩中"运营后台"模块的成体系功能亮点：

- **用户留存分析**：按注册日 cohort 计算新增用户，输出次日（D+1）/7 日（D+7）/30 日（D+30）留存率，前端以多折线图展示并附明细表（`StatsServiceImpl.getRetention`）。已避开"距离今天不足 N 天数据不完整"的口径问题。
- **漏斗分析**：浏览 → 报名 → 通过 → 出勤 四阶段转化，横向柱状图呈现每层转化率（`getFunnel`）。
- **系统公告/弹窗发布**：新增 `sys_announcement` 表 + `AnnouncementManage.vue`，支持公告的增删改查、发布/关闭、分页，用户在 App 端可查看公告弹窗。
- **数据导出**：用户 / 帖子 / 统计三类 CSV 导出，含 UTF-8 BOM（保证 Excel 中文不乱码）与逗号/引号/换行转义，留存在线分析可分趋势 / 留存 / 漏斗三种口径导出（`exportUsers / exportPosts / exportStats`）。

**已消除的不足**：运营不再只靠人工翻数据报表，留存健康度、组局转化漏斗、公告触达、数据下载四项主流程闭环。

### 1.7 下一步建议（推荐优先级）

在 1.6 已收官、运营体系基本成型的基础上，从"继续完善**核心业务闭环** + 呼应近期**风控/重信誉**主题"双角度，建议按以下顺序迭代：

| 优先级 | 方向 | 说明 | 理由 | 难度 |
|--------|------|------|------|------|
| ⭐⭐⭐⭐⭐ | **接口限流防刷**（见 3.1） | Redis + 令牌桶/滑动窗口，发帖/举报/报名等写接口按 IP+用户限流 | 独立可演示，安全价值高，与已建的"举报自动风控"主题衔接 | 中 |
| ⭐⭐⭐⭐ | **评价举报申诉**（补全 1.5） | 恶意差评可申诉，管理员复核后撤下 | 补全"评价闭环"，联动内容审核 | 中 |
| ⭐⭐⭐ | **系统公告 → 定向/分人群触达** | 公告按学院/信誉分分组下发，App 端标记已读 | 在 1.6 公告基础上低成本延展，运营精细化 | 低 |
| ⭐⭐⭐ | **浏览器通知推送**（补全 1.4） | 报名通过/组局取消时用 Notification API 主动提醒 | 低难度、演示直观，补上"站内信无推送"短板 | 低 |

**评价闭环说明**：互评（V1.1）+ 评价回复（V1.4）已打通「发布者⇄参与者」双向评价与被评价人解释；推荐下一步做「评价举报申诉」以彻底堵住恶意差评，再接续「接口限流」完善风控与安全。两条线都和已有的「先审后发→信誉分→自动风控」形成可完整演示的价值链路。

## 二、性能与可扩展性问题

### 2.1 推荐算法全量加载 + 内存排序

`RecommendServiceImpl.getRecommendList` 中，推荐排序采用的是：
1. 把所有符合条件的帖子全量查出（`selectList`）
2. 在内存中逐条计算推荐分
3. 内存排序后手动分页

**问题**：
- 帖子数量达到几千条以上时，每次请求都加载全量数据到内存，有 OOM 风险
- 每次请求都重新计算所有帖子的分数，CPU 浪费严重
- 没有利用数据库索引和排序能力

**改进方向**：
- 先按时间/热度粗排取 Top N（如 200 条），再在小数据集上精排
- 引入 Redis 缓存推荐结果（5~10 分钟过期）
- 长期可考虑用 Elasticsearch 做检索和粗排

### 2.2 ~~N+1 查询问题普遍存在~~ ✅ 已优化（V1.4）

> **现状**：已通过共享 `PostConverter`（批量 `IN` 查询 + 内存 Map 组装）与批量查询重构解决，覆盖广场/推荐/管理端帖子、应用、评价、举报列表及帖子详情的报名/可评价用户。广场列表从 `1+N` 次降为 `1+2` 次；三处重复的 `convertToPostVO` 收敛为一份（对应 4.4）。

~~列表类接口中，每条数据都单独查关联信息，是典型的 N+1 问题：~~

| 接口 | N+1 位置 | 影响 |
|------|---------|------|
| 广场列表 | 每条帖子查发布者信息、查标签名 | 10 条帖子 = 1 + 10 + N 次查询 |
| 帖子详情 | 每个报名者查一次用户信息 | 最多 N 次查询 |
| 举报列表 | 每条举报查举报人、处理人、被举报对象 | 3×N 次查询 |

**改进方向**：改用批量查询（`selectBatchIds` 或 `in` 查询），一次查出所有关联数据，再在内存中组装。以广场列表为例，10 条帖子可以从 20+ 次查询降到 3 次。

### 2.3 没有连接池监控和慢查询分析

当前只配置了基础的数据库连接池，缺少：
- 慢 SQL 日志
- 连接池使用率监控
- 接口响应时间统计

**改进方向**：引入 Spring Boot Actuator + Micrometer，或接入简单的 AOP 耗时统计。

### 2.4 Redis 使用较浅

当前只用了 Redis 做浏览量去重，很多场景没有充分利用缓存：

- 广场列表（最热的接口）完全走数据库
- 兴趣标签列表（基本不变）每次都查库
- 用户信息（修改频率低）没有缓存

**改进方向**：增加标签列表缓存、热门帖子缓存、用户信息缓存。注意处理缓存一致性问题。

### 2.5 单体架构，服务未拆分

当前是 Spring Boot 单体应用，所有模块混在一起。对毕设来说够用，但从架构演进角度：

- 推荐服务计算量大，应该独立出来
- 消息通知可以异步化，不阻塞主流程
- 用户服务和内容服务可以独立扩容

**改进方向**：可以在文档中给出微服务拆分方案（用户服务、内容服务、推荐服务、消息服务），答辩时体现架构思维。

## 三、安全风险

### 3.1 缺少接口限流防刷

当前所有接口都没有限流保护：

- 发帖接口可以被恶意调用刷屏
- 短信/注册接口（如果有的话）可以被刷
- 广场列表接口可以被爬虫批量拉取

**改进方向**：引入 Redis + 令牌桶/滑动窗口限流，按用户 ID 或 IP 限流。关键接口（发帖、举报、注册）加限流。

### 3.2 内容安全只有违禁词，检测维度单一

当前违禁词检测是简单的字符串包含匹配：

- **容易绕过**：加空格、谐音、形近字就能躲过
- **没有图片检测**：头像如果有人上传违规图片，系统检测不到
- **没有 AI 内容审核**：语义层面的违规（比如诱导、诈骗话术）发现不了

**改进方向**：
- 违禁词改 DFA 算法（前缀树），性能更好且支持更多词
- 接入第三方内容安全 API（如阿里云内容安全、腾讯云内容安全）
- 图片加审核（文件上传时调用图片检测接口）

### 3.3 XSS 风险较低但未完全杜绝

前端用 Vue 的 `{{ }}` 插值，默认会转义，XSS 风险较低。但：

- 如果后续引入富文本编辑，需要额外注意
- 管理端展示用户输入内容时，同样要注意
- 评论/描述字段在数据库层面没有过滤

**改进方向**：后端增加统一的 XSS 过滤过滤器，对所有用户输入做转义或净化。

### 3.4 没有操作日志审计

管理端的关键操作（封禁用户、下架帖子、删除内容）没有审计日志：

- 出了问题无法追溯是谁操作的
- 多个管理员时无法区分职责

**改进方向**：增加操作日志表（`sys_operation_log`），用 AOP 切面统一记录管理端操作。

### 3.5 JWT 密钥硬编码在配置文件里

`application-local.yml` 里 JWT secret 是明文写死的。虽然本地开发环境没问题，但：

- 生产环境如果也这么配，密钥泄露风险高
- 没有密钥轮换机制

**改进方向**：生产环境用环境变量注入密钥，定期轮换。

## 四、架构与代码质量

### 4.1 业务常量散落在代码中

很多业务参数硬编码在 Service 类里：

| 常量 | 值 | 位置 |
|------|-----|------|
| 最大同时进行帖子数 | 5 | `PostServiceImpl` |
| 浏览量去重窗口 | 10 分钟 | 同上 |
| 推荐缓存过期 | 5 分钟 | `RecommendServiceImpl` |
| 自动风控阈值 | 3 次 | `ReportServiceImpl` |
| 信誉分初始值 | 100 | `CreditConstant`（这个做得好） |
| 违禁词列表 | 硬编码 | `SensitiveWordService` |

**改进方向**：统一放到配置类或 `application.yml` 中，用 `@ConfigurationProperties` 注入。好处是改配置不用重新编译，也方便做动态配置。

### 4.2 领域模型偏贫血

当前实体类（Entity）基本只有 getter/setter，业务逻辑全在 Service 里，是典型的贫血模型：

- `Post` 实体没有任何业务方法，状态变更都在 Service 里操作
- 状态机校验是静态工具类，没有和实体绑定

**改进方向**：可以在答辩中提一下向 DDD（领域驱动设计）演进的思路，把业务逻辑收敛到聚合根中，Service 只做编排。体现理论深度。

### 4.3 缺少单元测试

当前项目应该基本没有单元测试（待确认）：

- 核心业务逻辑（报名流程、状态流转、推荐算法）没有测试覆盖
- 重构风险高，容易改出 bug

**改进方向**：关键业务方法补单元测试，尤其是状态机、信誉分计算、推荐算法这些逻辑复杂的部分。

### 4.4 ~~代码重复：PostVO 转换逻辑多处重复~~ ✅ 已收敛（V1.4）

> **现状**：三份 `convertToPostVO`（`PostServiceImpl` / `RecommendServiceImpl` / `AdminServiceImpl`）已统一收敛到共享 `PostConverter`（`com.buddy.converter`），并同步支持批量 `IN` 查询（见 2.2）。改一个字段只改一处，标签名/发布者信息口径一致。

## 五、用户体验问题

### 5.1 新用户引导缺失

用户注册登录后直接进入广场，没有任何引导：

- 不知道怎么设置兴趣标签（影响推荐质量）
- 不知道怎么发帖、怎么报名
- 信誉分体系是什么、有什么用，用户完全不了解

**改进方向**：增加新手引导流程——首次登录后引导选择兴趣标签、展示功能导览弹窗。

### 5.2 空状态设计单薄

很多列表的空状态只有一句"暂无数据"，没有引导用户下一步做什么：

- 广场空了 → 只显示"暂无组局信息"，虽然有"去发布"按钮，但其他页面不一定有
- 我的报名空了 → 没有"去逛逛"引导
- 消息中心空了 → 没有解释"这里会收到什么通知"

**改进方向**：每个空状态都配上插画 + 清晰的下一步行动引导。

### 5.3 加载状态不一致

有的页面是全局 loading，有的是列表骨架屏/van-list 自带加载，体验不统一。

**改进方向**：统一加载态设计——首屏用骨架屏，翻页用底部 loading，操作类用按钮 loading。

### 5.4 没有深色模式 / 无障碍支持

- 只有浅色模式，夜间使用体验差
- 没有考虑色弱、色盲用户的配色
- 字体大小不能调整

对毕设来说不是必须项，但答辩时提一下可以体现对用户体验的全面思考。

### 5.5 举报反馈链路不完整

用户举报后：

- 不知道处理进度（是待处理还是已处理）
- 处理结果只有系统通知，没有在举报列表里明确展示
- 举报被驳回了，用户不知道原因

## 六、工程化与运维

### 6.1 没有 CI/CD

当前是纯手动部署：
- 本地打包 → 上传服务器 → 重启服务
- 没有自动化测试、自动化部署
- 没有代码质量检查

**改进方向**：可以用 GitHub Actions 或 Jenkins 搭一个简单的 CI 流水线，提交代码后自动构建 + 部署。

### 6.2 没有 Docker 化

项目依赖 MySQL、Redis，环境搭建麻烦：
- 新人拿到代码要自己装 MySQL、建库、导入数据、装 Redis
- 开发环境和生产环境可能不一致

**改进方向**：写一个 `docker-compose.yml`，一条命令启动所有依赖。毕设答辩演示时也方便。

### 6.3 日志策略不完善

- 只有默认的日志配置，没有按级别/模块分文件
- 没有错误日志告警
- 没有访问日志（谁在什么时候调用了什么接口）

**改进方向**：接入 Logback 配置，按天滚动日志，错误日志单独输出。

### 6.4 数据库没有备份策略

当前数据库是单点的：
- 没有定期备份
- 磁盘挂了数据全丢

**改进方向**：写个简单的定时脚本，每天凌晨 mysqldump 备份。

## 七、总结与优先级建议

按"毕设答辩中最值得提及"的角度，整理 Top 10 改进方向：

| 优先级 | 改进方向 | 答辩价值 | 实现难度 |
|--------|---------|---------|---------|
| ⭐⭐⭐⭐⭐ | 推荐算法性能优化（粗排+精排+缓存） | 体现算法+性能思维 | 中 |
| ⭐⭐⭐⭐⭐ | N+1 查询优化 | 体现数据库性能调优能力 | 低 |
| ⭐⭐⭐⭐ | 引入社交关系链（关注/粉丝） | 功能丰富度+推荐维度扩展 | 中 |
| ⭐⭐⭐⭐ | 接口限流与防刷 | 体现高并发/安全意识 | 中 |
| ⭐⭐⭐⭐ | 违禁词检测升级（DFA 算法） | 体现算法+数据结构功底 | 低 |
| ⭐⭐⭐ | 微服务架构拆分方案（只讲不实现） | 体现架构设计思维 | 低（写文档） |
| ⭐⭐⭐ | Docker 容器化部署 | 体现工程化能力 | 低 |
| ⭐⭐⭐ | 操作日志审计 | 体现安全意识 | 低 |
| ⭐⭐ | WebSocket 实时聊天 | 体现实时通信能力 | 高 |
| ⭐⭐ | 地理位置/地图接入 | 功能亮点，可视化效果好 | 中 |

---

> **结语**：作为一个毕设项目，当前 V1.3 版本已经完整覆盖了核心业务流程（发帖→报名→评价→信誉），技术栈选择合理，代码结构清晰。上述不足更多是"生产级产品"和"课程项目"之间的差距，也是毕设答辩中展示思考深度的好素材。
