## 一、研究背景与意义

### 1.1 背景：校园里的"找搭子"是真实且高频的需求

在高校场景中，"想找人一起做某件事，但凑不齐人"是普遍痛点：

- **运动场景**：想打篮球/羽毛球，室友不感兴趣，凑不齐人；
- **电竞场景**：想上分，路人队友不靠谱，希望找段位相近的同学；
- **桌游场景**：剧本杀、狼人杀需要固定人数，缺人就开不了局；
- **跑步/健身/学习场景**：一个人难以坚持，希望找到节奏相近的伙伴。

学生目前的解决方式各有明显缺陷：

| 方式 | 问题 |
|------|------|
| 班级群/社团群发消息 | 覆盖面窄、容易刷屏、信息很快被淹没 |
| 表白墙/论坛发帖 | 信息杂乱、无法按兴趣筛选、没有报名与确认机制 |
| 线下随机约 | 效率低，不了解对方水平，体验差 |

与此同时，"搭子"作为一种轻社交关系在年轻人中快速流行（"同事之上、朋友未满"，因具体需求而结伴、事毕而散）。2023 年以来小红书、抖音等平台陆续推出"找搭子"功能或话题，"搭子文化"成为年轻人社交的高频词。这说明需求真实存在，但现有平台多是**内容社区顺带提供**的能力（发帖+私聊），缺少**结构化的组局与履约工具**。

### 1.2 研究意义

**实践意义**：

1. 把"找搭子"从"发帖+拉群"升级为**结构化流程**：时间/地点/人数/门槛全部结构化，报名走审批，满员有候补，活动后强制互评；
2. 把"靠谱"从主观印象升级为**可量化的信誉分**：临场取消、爽约、被评价都会留下记录并影响后续使用权限；
3. 提供一套**可直接运行、可复现**的完整系统（用户端 H5 + 管理端 + 后端 + 数据库脚本），具备实际落地能力。

**方法/理论意义**：

1. 将**状态机**引入组局与报名两类核心业务对象，把散落的业务分支收敛为显式的合法流转规则，提升可维护性与可测试性；
2. 将**信誉约束**与业务权限打通（低于阈值禁止发帖/报名、推荐沉底），验证"信用机制调节小型社区行为"的可行性；
3. 在推荐排序上采用**可解释的加权公式**（兴趣匹配+时间+信誉+热度），在垂直场景中以可解释性换复杂度，是一条对学生项目更务实的路线。

### 1.3 同类产品调研（简要）

| 类型 | 代表 | 机制 | 对本系统的启示 |
|------|------|------|----------------|
| 活动/内容发现式 | Meetup、小红书、抖音 | 兴趣标签+位置+时间+热度，推荐排序+报名制 | 本系统采用同一路线（增加信誉维度），符合主流 |
| 1v1 滑卡双向选择 | Bumble BFF、探探 | 档案+兴趣+距离，双方同意才匹配 | 适合"找人"；不适合"多人成局"的场景 |
| 问卷/算法撮合 | Timeleft、Soul | 性格问卷→画像→算法直接配对 | 依赖算法与数据积累，且偏 1v1/同桌场景 |

**空白点**：面向校园的"结构化组局 + 履约信誉 + 候补递补"一体化工具缺失，本系统定位于此。

## 二、产品定位与目标

### 2.1 一句话定位

面向高校学生的**兴趣搭子预约平台**：通过"**标签匹配 + 状态化预约 + 信誉分约束**"三位一体机制，解决"找搭子难、约搭子难、搭子不靠谱"三个问题。

### 2.2 产品目标

| 层级 | 目标 | 衡量方式 |
|------|------|---------|
| 核心 | 快速找到兴趣相投、水平相近的搭子 | 发帖到满员时长达标、报名转化可观测 |
| 业务 | 完成"发帖→报名→活动→评价"闭环 | 成功组局数、出勤率（管理端统计可查） |
| 安全 | 靠信誉机制约束违约行为 | 爽约/临场取消有记录与惩罚，违规内容可处置 |
| 体验 | H5 免下载即用 | 移动浏览器直接访问 |

### 2.3 范围与边界

**包含**：H5 用户端（15 个页面）、PC 管理端（8 个页面）、后端接口约 60 个、数据库 13 张表。

**明确不含**（作为已识别的未来方向，不作本期需求）：

- 原生 App；即时聊天/私聊（联系渠道问题见"已知缺口"）；支付；地图定位/附近排序。

## 四、核心设计思路（为什么这样设计）

> 本章回答"为什么这么设计、代价是什么"，是答辩中"设计合理性"的核心素材。

### 4.1 为什么用"组局帖 + 报名审批"，而不是"系统直接撮合"

- **场景匹配**：搭子场景是"事件向"（一起做某事），不是"人设向"（找个人认识）。一场活动往往是 1 对多、多人成局，天然适合"发帖招募 → 报名 → 审批"的市场化流程；
- **降低冷启动**：直接撮合（推荐人）依赖活跃用户密度与算法数据，新平台很难跑通；帖子模式只要有少量帖子即可运转；
- **对标验证**：Meetup、小红书及国内搭子小程序均采用该路线（详见 1.3）。

### 4.2 为什么"发布即见 + 敏感词"，不做人工先审

- **成本现实**：毕业设计没有 7×24 审核人力，先审后发会让"发布体验"与"时效"都不可控；
- **替代防线**：发布与评论做敏感词拦截（第一道）+ 用户举报（第二道）+ 管理员下架/封禁（第三道），形成事后治理闭环；
- **代价与改进**：违规内容存在短暂曝光窗口；后续可接入第三方内容安全 API 加强。

### 4.3 为什么引入信誉分（本系统的核心机制）

- "搭子的最大风险是放鸽子"，需要一个**可积累、可失去、有实际后果**的信号；
- 设计：初始 100 分；评价影响（靠谱 +2/4星 +1/迟到 -3/爽约 -10）+ 台账变动（临场取消 -5/未到场 -10）；限幅 0~100；每日全量重算；
- **后果打通**：低于 60 分 → 禁止发帖、禁止报名、推荐沉底、主页失目标识；恢复即自动解禁；
- 代价：自评属性可被虚报（段位）、惩罚可能误伤（已用"进行中不可标未到场"+结束后 24 小时窗口缓解）。

### 4.4 为什么做候补递补

- 满员后取消产生的空位，若不自动递补，名额利用率低、组织者要反复沟通；
- 设计：满员自动进候补（先到先得）→ 有人取消时队首自动转待审批并双向通知；
- 同类产品少有该机制，是本系统的细节亮点之一。

### 4.5 为什么用状态机管理生命周期

- 帖子 5 态（招募/满员/进行中/结束/取消）、报名 7 态（待审/通过/拒绝/取消/候补/出勤/未到场），组合分支极多；
- 集中定义"哪些流转合法"（如终态不可逆、进行中不可取消），避免非法状态写入，并可用单元测试"逐条边"验证。

### 4.6 推荐排序为什么用可解释的加权公式

- 公式：`0.4×标签匹配 + 0.3×时间重合 + 0.2×发布者信誉 + 0.1×热度`；游客用简化公式；低信誉帖子 ×0.3 沉底；
- 选择理由：可解释（每一分都能讲清）、可演示（不同标签用户排序不同）、无需训练数据；
- 不选协同过滤的原因：冷启动无数据、垂直场景规模小、且黑盒结果难在答辩中解释；
- 改进方向：引入行为反馈闭环（点击/报名数据）、位置维度。

### 4.7 关键取舍一览

| 取舍 | 选择 | 原因 | 代价 | 改进方向 |
|------|------|------|------|---------|
| 审核 | 先发后审 | 无审核人力，保证时效 | 违规内容短暂曝光 | 接入内容安全 API |
| 发布者取消 | 不扣分（只通知报名者） | 惩罚先覆盖参与者侧，避免发布者不敢取消 | 恶意取消无惩罚 | 临场取消可加扣分 |
| 数据完整性 | 不建外键、标签存逗号串 | 简化实现、小数据量、读多写少 | 无法按标签索引查询 | 关联表/检索引擎 |
| 架构 | 单体应用 | 规模匹配、部署简单 | 扩展性受限 | 微服务拆分（只做设计） |
| 会话 | JWT 7 天静态令牌 | 无状态、实现简单 | 无刷新/吊销机制 | 刷新令牌+黑名单 |
| 辅助数据存储 | 默认 MySQL 单表，Redis 可选切换 | 零外部依赖、部署最简，同时保留性能演进路径 | 高频计数会有少量库写入 | 数据量大或响应偏慢时改一行配置切到 Redis |

## 五、核心业务流程

### 5.1 组局主流程（帖子状态机）

```
发布（敏感词校验通过后即可见）
   ↓
RECRUITING（招募中） ──人数满──→ FULL（已满员，后来者进候补）
   ↓ 到达开始时间（定时任务）        ↓
ONGOING（进行中） ──到达结束时间──→ FINISHED（已结束，可评价）
   ↓
任意非终态：发布者取消 / 管理员下架 → CANCELLED
```

### 5.2 报名与审批

报名（资格三重校验：信誉≥60 + 段位 + 性别；不能报自己的局；防重复）→ 待审核 → 发布者通过（占用名额，满则转满员）/ 拒绝 → 通知报名者。

### 5.3 候补与递补

满员后报名 → 候补队列（先到先得）→ 有已通过者取消 → 队首自动递补为待审批 → 双方收到通知。

### 5.4 出勤与信誉

活动进行中/结束后由发布者标记：出勤（无惩罚）/ 未到场（扣 10 分，写台账并通知本人）。进行中不可标"未到场"；结束后 24 小时内必须标记完毕。

### 5.5 评价

活动结束后（7 天窗口内），发布者与出勤参与者之间互评：1-5 星 + 标签 + 文字；被评价人可回复一次。
