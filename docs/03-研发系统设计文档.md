### 1.2 技术选型

| 层级 | 技术 | 版本 | 选型理由 |
|------|------|------|---------|
| 后端框架 | Spring Boot | 2.7.x | 成熟稳定，生态丰富，适合单体项目 |
| ORM 框架 | MyBatis-Plus | 3.5.x | 自动 CRUD + 代码生成器，极大提升开发效率 |
| 数据库 | MySQL | 8.0+ | 关系型数据库，支持复杂查询 |
| 缓存 | Redis | 7.x | 存 Token、推荐结果缓存、防重复提交 |
| 认证 | JWT + Spring Security | - | 无状态认证，前后端分离标准方案 |
| 密码加密 | BCrypt | - | 不可逆加密，安全性高 |
| 用户端 UI | Vue3 + Vant4 | 3.x / 4.x | 移动端 H5 最成熟的组件库 |
| 管理端 UI | Vue3 + Element Plus | 3.x | PC 后台管理最成熟的组件库 |
| 构建工具 | Vite | 4.x | 极速热更新，开发体验好 |
| 状态管理 | Pinia | 2.x | Vue3 官方推荐，轻量简洁 |
| HTTP 客户端 | Axios | 1.x | 请求拦截、统一错误处理 |
| 图表库 | ECharts | 5.x | 管理端数据统计可视化 |

### 3.2 状态机模型

#### 3.2.1 帖子状态机

```mermaid
stateDiagram-v2
    [*] --> RECRUITING : 发布组局（先审后发：审核通过后广场可见）

    RECRUITING --> FULL : current_people = max_people
    FULL --> RECRUITING : 有人取消报名

    RECRUITING --> ONGOING : 到达start_time（定时任务）
    FULL --> ONGOING : 到达start_time（定时任务）

    ONGOING --> FINISHED : 到达end_time（定时任务）
    ONGOING --> CANCELLED : 管理员下架进行中帖子

    RECRUITING --> CANCELLED : 发布者取消/管理员下架
    FULL --> CANCELLED : 发布者取消/管理员下架

    FINISHED --> [*]
    CANCELLED --> [*]
```

#### 3.2.2 帖子审核状态机（V1.1 先审后发）

```mermaid
stateDiagram-v2
    [*] --> PENDING : 发布组局（默认待审核）

    PENDING --> APPROVED : 管理员审核通过 → 广场可见
    PENDING --> REJECTED : 管理员拒绝（带原因）→ 通知发布者

    APPROVED --> PENDING : 管理员重新标记待审（纠错）
    REJECTED --> PENDING : 发布者修改后重新提交审核
```

#### 3.2.3 报名状态机（含候补）

```mermaid
stateDiagram-v2
    [*] --> PENDING : 用户报名
    [*] --> WAITLIST : 满员时候补报名（V1.1）

    PENDING --> APPROVED : 发布者同意
    PENDING --> REJECTED : 发布者拒绝
    PENDING --> CANCELLED : 报名者取消

    WAITLIST --> PENDING : 有空位自动递补（V1.1）
    WAITLIST --> CANCELLED : 候补者主动取消（不扣分）

    APPROVED --> CANCELLED : 报名者取消（活动前）
    APPROVED --> ATTENDED : 活动结束-已到场
    APPROVED --> NOSHOW : 活动结束-未到场

    REJECTED --> [*]
    CANCELLED --> [*]
    ATTENDED --> [*]
    NOSHOW --> [*]
```

### 3.3 信誉分计算模型

```mermaid
graph LR

        R5[爽约 -10分]
    end

    subgraph 额外惩罚
        P1[爽约NOSHOW<br/>额外 -5分]
        P2[临场取消<br/>-5分]

    subgraph 计算
        C1[信誉分 = 100 + Σ评价影响 + Σ额外惩罚]

    end

    subgraph 影响
        E1[≥60 正常使用]
        E2[<60 沉底+禁发帖+禁报名]
    end

    R1 & R2 & R3 & R4 & R5 --> C1
    P1 & P2 --> C1
    C1 --> C2
    C2 --> E1
    C2 --> E2
```

### 4.4 设计模式应用

| 设计模式 | 应用场景 | 说明 |
|---------|---------|------|
| MVC 模式 | 整体架构 | Controller-Service-Mapper 三层分离 |
| 策略模式 | 推荐排序 | 不同排序策略（推荐/最新/热度）可切换 |
| 状态机模式 | 帖子状态流转 | PostStateMachine 封装状态流转校验 |
| 拦截器模式 | JWT 认证 | JwtInterceptor 统一处理登录校验 |
| 统一返回模式 | API 响应 | R<T> 统一封装返回结构 |
| 全局异常处理 | 错误处理 | @ControllerAdvice 统一捕获异常 |
| DTO 模式 | 数据传输 | Request/Response DTO 与 Entity 分离 |
| 建造者模式 | 复杂查询 | MyBatis-Plus QueryWrapper 链式构建 |

```mermaid
flowchart TD
```

```mermaid
    C1 -->|是| C2[点击"候补报名"]

    G -->|是| I{满足段位/性别要求?}

    I -->|否| J[提示"不满足要求"]
    I -->|是| K[点击"报名"]

    P --> R{current_people = max_people?}
    R -->|是| S[post.status=FULL<br/>启动候补队列检查]
    R -->|否| T[保持 RECRUITING]

    S --> S1{有WAITLIST候补?（V1.1）}
    S1 -->|否| S2[结束]
    S1 -->|是| S3[不自动递补<br/>等有人取消才递补]

    R3 -->|否| R5[空位保留，帖子回退 RECRUITING]
```

### 5.5 评价与信誉分更新流程

```mermaid
flowchart TD

    I -->|否| J[等待对方评价]
    I -->|是| K[触发信誉分重新计算]

    K --> L[定时任务每日凌晨执行]

    O -->|否| Q{信誉分 > 100?}

    Q -->|是| R[信誉分 = 100]
    Q -->|否| S[更新 sys_user.credit_score]

    P --> S
    R --> S

    S --> T{信誉分 < 60?}
    T -->|是| U[触发失信惩罚<br/>沉底+禁发帖+禁报名]
    T -->|否| V[正常使用]
```

### 5.6 推荐算法流程

```mermaid
flowchart TD
    A[用户打开广场页] --> B{是否登录?}

    B -->|否| C[按时间+热度排序<br/>不计算标签匹配]
    B -->|是| D[获取用户兴趣标签集合]

    D --> E[查询招募中+已满员的帖子]
    E --> F[遍历每条帖子计算权重]

    F --> G[计算标签匹配度<br/>= 用户标签∩帖子标签 / 帖子标签总数]
    G --> H[计算时间重合度<br/>= 1 - 距活动开始小时数/168]
    H --> I[获取发布者信誉分<br/>= credit_score/100]
    I --> J[计算热度因子<br/>= current_people/max_people]

    J --> K[总权重 = 0.4×标签 + 0.3×时间 + 0.2×信誉 + 0.1×热度]

    K --> L{发布者信誉分 < 60?}
    L -->|是| M[权重 × 0.3 沉底]
    L -->|否| N[保持原权重]

    M --> O[按权重降序排序]
    N --> O

    O --> P[缓存结果 5 分钟]
    P --> Q[返回列表]
```

```mermaid
    S->>DB: UPDATE post_apply SET status='APPROVED'
    S->>DB: UPDATE post SET current_people = current_people + 1
    DB-->>S: 更新成功

    S->>SM: 检查是否满员
    SM->>DB: 查询 current_people vs max_people

    alt 已满员
        SM->>DB: UPDATE post SET status='FULL'
        SM-->>S: 状态变为 FULL
    else 未满员
        SM-->>S: 保持 RECRUITING
    end

    S-->>B: 返回成功
    B-->>F: 返回"已同意"
    F-->>P: 显示"已同意"
```

## 九、安全设计

### 9.1 认证与鉴权

```mermaid
flowchart LR
    A[前端请求] --> B[携带 JWT Token]
    B --> C[JwtInterceptor 拦截]
    C --> D{Token 有效?}
    D -->|否| E[返回 401 未登录]
    D -->|是| F[解析 userId 放入 ThreadLocal]
    F --> G{需要管理员权限?}
    G -->|是| H{is_admin=1?}
    H -->|否| I[返回 403 无权限]
    H -->|是| J[放行到 Controller]
    G -->|否| J
    J --> K[业务处理]
```

### 9.2 越权防护

| 场景 | 防护措施 |
|------|---------|
| 编辑他人帖子 | Controller 层校验 publisher_id = 当前 userId |
| 审核他人帖子的报名 | 校验 postId 对应的 publisher_id = 当前 userId |
| 封禁用户 | 校验 is_admin = 1 |
| 修改个人资料 | JWT 解析的 userId 必须与请求体的 userId 一致 |
| 查看他人通知（V1.1） | 通知查询强制 user_id = 当前 userId，不允许带任意 userId |
| 处理举报（V1.1） | 校验 is_admin = 1 + @RequireAdmin 注解 |
| 查看他人主页（V1.1） | 只读接口，敏感字段脱敏（手机号/学号） |

### 9.3 敏感信息脱敏（V1.1）

| 场景 | 脱敏规则 |
|------|---------|
| 手机号展示 | `138****0001`（保留前 3 后 4 位） |
| 个人主页 | 不返回学号、手机号、密码哈希等字段 |
| 管理端用户列表 | 手机号脱敏展示，完整号码仅详情页管理员可见 |
| 举报人信息 | 举报处理页面举报人脱敏（防打击报复） |

### 9.4 审核与风控（V1.1）

```mermaid
flowchart LR
    A[用户发布帖子] --> B[is_audit_pass=0 待审核<br/>广场不可见]
    B --> C[管理员审核]
    C -->|通过| D[广场可见]
    C -->|拒绝| E[通知发布者+原因]

    F[用户举报帖子/用户] --> G[report 表 status=0]
    G --> H[管理员处理]
    H -->|有效| I[联动下架/封禁+通知双方]
    H -->|无效| J[标记无效]

    I --> K{同一对象累计3次有效举报?}
    K -->|是| L[自动触发处理（半自动风控）]
```

### 9.5 通知与事务一致性（V1.1）

- 通知写入与业务操作**同一事务**：报名/审核/递补等操作失败时不会产生"幽灵通知"；
- 通知发送采用"事务内写库 + 前端轮询未读数"模型，不引入消息队列（单体项目够用）；
- 活动提醒由定时任务批量扫描 `start_time` 在 [now, now+30min] 且状态为 RECRUITING/FULL/ONGOING 的帖子，向发布者 + APPROVED 报名者写入提醒通知（同一任务保证幂等：按 `(post_id, type)` 去重）。
