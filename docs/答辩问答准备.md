## 一、开场自述模板（约 3 分钟，可直接背）

> "我的毕业设计是《校园兴趣搭子预约系统》。它在校园场景里解决三个具体问题：找搭子没渠道、约了容易被放鸽子、不知道对方水平和靠不靠谱。
>
> 系统由三部分组成：用户端 H5、PC 管理端和单体后端。核心机制有三个：第一，结构化组局——把时间、地点、人数、段位和性别门槛全部结构化，报名走审批；第二，状态机管理业务生命周期——帖子有 5 种状态、报名有 7 种状态，非法流转会被拦截；第三，信誉分约束——活动后互评、临场取消和爽约都会影响信誉分，低于 60 分禁止发帖和报名，并且发布的帖子在广场沉底。
>
> 工程上我做了完整的闭环：满员后进入候补，有人退出会自动递补；并发场景用条件更新和原子 SQL 保证不超卖、不重复处理；核心业务有 111 个单元测试，并且接了 CI 流水线。下面我演示一下主要流程。"

## 二、高频问题与建议回答

### （一）选题与需求

**Q1：为什么选这个题目？**
答：校园里"想找人一起做某件事但凑不齐人"是高频真实需求；现有方式是班级群刷屏、表白墙发帖，信息分散且没有任何约束。测试：系统解决"找到 + 约上 + 靠谱"三件事，形成完整闭环。

**Q2：你的系统和微信群/小红书发帖有什么区别？**
答：两点。一是把信息结构化并带门槛校验（时间/地点/人数/段位/性别），不符合门槛的报名会被拦住；二是引入履约约束——报名要审批、爽约和临场取消会影响信誉分、低于阈值直接失去发帖和报名资格。"发帖拉群"没有任何这两层。

**Q3：同类产品是怎么做的，你的差异在哪？**
答：调研了三个路线——活动发现式（Meetup、小红书）、1v1 滑卡式（Bumble BFF）和问卷撮合式（Timeleft、Soul）。我的系统属于第一条路线（活动发现式，适合多人成局），差异点是在其上叠加了"信誉约束 + 候补递补 + 完整状态机"，尤其候补机制在同类产品中不多见。

**Q4：系统的用户是谁，怎么获客？**
答：在校学生，从班级、社团、运动场馆等场景切入；校园内推广成本低，单个院系试点即可自增长。（如实说明：获客不是本文重点，重点是机制设计与实现。）

### （二）架构与技术选型

**Q5：为什么用单体架构？**
答：项目规模与团队规模都匹配单体——模块按业务分包（post/apply/review…），内部边界清晰；部署简单，毕设阶段运维成本低。微服务拆分我做过方案思考（用户服务/内容服务/推荐服务/消息服务），作为架构演进方向写在展望里。

**Q6：为什么选 Spring Boot 3 和 Java 17？**
答：Boot 2.x 已停止维护；17 是当前 LTS，配 Boot 3 是主流组合。迁移时完成了 javax→jakarta、部分 API 变化（如 JJWT 0.11→0.12）的适配。

**Q7：Redis 在你的系统里做什么？**
答：现在默认不需要 Redis。四类辅助能力（登录失败锁定、浏览量去重、上传频率限制、举报去重）被抽象成统一接口，默认用 MySQL 单表实现——部署零外部依赖；如果数据量大或觉得响应偏慢，把配置 `app.aux.store` 改为 `redis` 即可无痛切换，业务代码零改动。这体现的是"先简化部署、保留性能演进路径"的取舍。

**Q8：为什么数据库不建外键？**
答：这是明确的取舍：单机小数据量 + 全链路逻辑删除体系下，外键约束会与"逻辑删除""批量写入"产生额外复杂度；关系完整性由应用层校验保证。代价是无法依赖数据库级约束，改进方向是加外键或引入数据校验层。

**Q9：为什么帖子标签用逗号分隔字符串存？**
答：读多写少、标签数量少（单帖 1-3 个），字符串存储避免联表；代价是无法按标签建索引做精确查询，标签匹配在应用层解析。规模上去后可改关联表或检索引擎。（如被追问：解析时对脏数据做了容错，坏数据不会让广场接口报错。）

### （三）核心机制与算法

**Q10：推荐算法的公式是什么？为什么这样设计？**
答：`0.4×标签匹配 + 0.3×时间重合 + 0.2×发布者信誉 + 0.1×热度`；游客用简化公式。权重是经验值，设计原则是"兴趣优先、时间其次、信誉兜底、热度调节"；维度与 Meetup 的推荐因素（位置/时间/热度/兴趣）基本一致。
深水区：被问"权重凭什么"→答：目前为经验取值+代码集中可配置，科学做法可做 A/B 实验或 AHP 标定，属于改进方向。

**Q11：为什么不用协同过滤/机器学习？**
答：三个原因：冷启动没有行为数据；垂直场景用户量小、数据稀疏；黑盒推荐在答辩与实际运营中都不好解释。当前阶段"可解释 + 可演示"更重要。改进方向：先积累点击与报名数据，再做行为反馈闭环。

**Q12：信誉分怎么计算的？为什么要每日重算？**
答：`信誉分 = 100 + Σ评价影响 + Σ台账变动`，限幅 0~100。评价影响如靠谱 +2、爽约 -10；台账记录临场取消 -5、未到场 -10 等即时惩罚。即时惩罚写台账并当场重算（保证立刻生效），每日凌晨再全量重算兜底——台账的存在就是为了防止"每日重算把惩罚冲掉"。

**Q13：段位为什么是自评？不会虚报吗？**
答：会，这是已知弱点。设计上段位是"报名门槛信号"而非强校验：球类和电竞两类启用，跑步/桌游等无段位概念（存 0）。改进方向：用互评结果校准段位，或让段位只做展示不硬卡门槛。段位名从"青铜~王者"改为"萌新~宗师"，是为了适配全品类活动、去掉游戏专属感。

**Q14：为什么发布就能看见，不先审核？**
答：毕设没有 7×24 的审核人力，先审会让发布时效不可控。替代防线是三层的：敏感词拦截（发布/评论时）、用户举报（含 24 小时去重和 3 次有效举报自动风控）、管理员下架与封禁。代价是违规内容有短暂曝光窗口，改进方向是接入内容安全 API。

**Q15：发布者取消组局为什么不扣分？**
答：取消本身已经付出代价——所有报名者会被自动取消并逐个收到通知，发布者的信誉会自然受损。惩罚机制目前集中在参与者侧（临场取消 -5、爽约 -10）。发布者恶意取消的惩罚是已识别的改进点。

**Q16：候补递补怎么保证公平和不丢名额？**
答：候补按报名时间先到先得；已通过者取消时，队首自动递补为待审批，且"取消、递补、名额回退"在同一事务内完成；每一步都做条件更新，保证并发下不会重复递补或丢名额。

### （四）并发与数据一致性（深水区）

**Q17：两个人同时审批最后一个名额会怎样？**
答：不会超卖。审批通过时人数自增带条件：`current_people < max_people` 才允许 +1，自增失败即判定"名额已满"，整个审批事务回滚；同时"待审核→通过"的状态转换也带旧状态条件，重复审批第二次会直接失败。这条路径有专门的单元测试。

**Q18：重复点击"取消报名"会扣两次分吗？**
答：不会。取消操作是条件更新（只在报名仍处于可取消状态时生效）+ 影响行数校验，第二次点击影响 0 行、直接返回"状态已变化"；扣分逻辑只在转换成功后执行。

**Q19：用户并发发帖绕过"最多 5 局"的限制怎么办？**
答：发帖前先对用户行加锁（SELECT ... FOR UPDATE），把"计数+插入"串行化，同一用户的并发发帖会排队执行。

**Q20：举报去重怎么防并发？**
答：数据库 24 小时查重兜底 + 原子去重门闩（默认 MySQL 唯一键实现，可切换 Redis）双保险：并发双击时只有一个请求能通过；门闩异常时降级为仅数据库查重（此时极端并发下可能重复，属于可接受的降级）。

### （五）安全与隐私

**Q21：系统做了哪些安全措施？**
答：认证方面——BCrypt 存密码、JWT 7 天令牌、连续失败锁定；密钥从环境变量注入且启动自检（缺失或过短直接启动失败，避免弱密钥上线）；鉴权方面——写操作必须登录、管理接口必须管理员，资源归属逐接口校验；输入方面——全参数化查询防注入；上传方面——需登录、按内容识别真实类型、限大小限频率；跨域——白名单配置；防滥用——发布/评论/报名/举报等写接口按"用户 + 动作"限流，超限返回 429。

**Q22：用户隐私怎么保护？**
答：他人主页不展示学号和手机号；隐私开关可隐藏历史组局；通知和报名列表仅本人可见；管理员操作有归属校验；**联系方式（手机号）按业务状态授权**——只有发布者本人和"报名已通过"的参与者之间互相可见，游客/待审核/被拒者在接口层面就拿不到手机号，不是靠前端隐藏。

**Q22-1：移动端适配怎么做的？**
答：H5 用 Vant 4 移动组件库打底，再补一层适配基线：①`viewport-fit=cover` + `env(safe-area-inset-*)` 处理刘海屏与全面屏手势条（顶部由根容器统一让位，底部两个悬浮/固定元素各自处理）；②`100dvh` 替代 `100vh`，地址栏收起时页面不跳；③iOS 专项——关闭数字自动识别为电话链接、禁止聚焦输入框时页面被自动放大、禁止横屏字号放大；④大屏（PC/平板）自动限宽 480px 居中，答辩投影时不会被拉成超宽条；⑤补了图标与"添加到主屏"元信息，从主屏打开是类原生全屏。管理端是电脑端后台，不做移动适配，窄屏给提示。
（顺带讲个坑：只写 `env(safe-area-inset-bottom)` 而不写 `viewport-fit=cover` 的话它恒为 0——原来那段安全区代码就是死代码；而且它还会被组件的 scoped `padding` 简写覆盖，优先级问题。）

### （六）测试与质量

**Q23：测试怎么做的？**
答：135 个单元测试，覆盖状态机逐条流转边、信誉分公式与五档边界、报名资格与并发防护、取消扣分窗口、出勤规则、举报去重与并发处置、上传校验、统计口径（含举报处理率的除零保护）、CSV 防注入、辅助存储双实现、接口限流（超限拦截与存储故障降级）、活动提醒幂等、通知类型筛选与 90 天清理、推荐缓存命中与过期；CI 流水线在每次提交时跑后端测试和双前端构建。
诚实补充：目前没有接口级/集成测试和覆盖率统计，是测试体系的下一步。

**Q24：工作量大概多少？**
答：后端约 60 个接口、13 张表；用户端 15 个页面、管理端 8 个页面；135 例单测 + CI。中间做了一次后端整体重构（技术栈升级 + 按模块分包）和一轮缺陷修复（并发一致性、安全加固、性能优化），全过程有测试与回归保护。

### （七）不足与展望（建议主动讲）

**Q25：这个系统有什么不足？**
答：功能上——身份验证缺失（学号手机号无验证）；修改/找回密码缺失；"你可能感兴趣"推荐位未做；恶意举报惩罚（7 天内多次无效举报）未做。工程上——没有接口级集成测试与覆盖率统计；性能压测与推荐效果评估数据缺失。这些都做过登记，见《产品需求文档》第九节。
（原先登记过的四类缺口——活动提醒任务、推荐缓存与 N+1、接口限流/通知筛选清理/举报处理统计、报名后的联系渠道——本轮已补齐。）

**Q26：如果继续做，下一步做什么？**
答：①实验数据（接口压测 + 推荐效果评估，论文素材最容易补）；②身份验证与密码找回；③推荐升级为"粗排 + 行为反馈"；④消息推送（把站内通知推到微信/短信）。

## 三、口径统一（必须与代码一致，别背错）

| 主题 | 正确口径 |
|------|---------|
| 审核 | 先发后审：发布即见 + 敏感词拦截；管理端保留下架/删除，审核接口仅兜底 |
| 发布者取消 | 不扣任何人的分；自动取消报名并逐个通知 |
| 通知 | 7 类（含"活动提醒"）；活动提醒由定时任务每 5 分钟扫描触发，同一人同一局只提醒一次；通知支持按类型筛选，90 天自动清理 |
| 段位 | 自评；仅球类/电竞启用；档位名：萌新/小白/熟手/高手/宗师 |
| 联系方式 | 仅发布者与"报名已通过（APPROVED/ATTENDED）"者互相可见手机号；站内聊天是有意不做 |
| 限流 | 发布 5 次/时、评论 20 次/时、报名/候补 10 次/时、举报 10 次/时；超限 429；存储故障时降级放行 |
| 删除 | 逻辑删除（可追溯），帖子删除级联评论/报名/评价/收藏 |
| 评价 | 7 天窗口；需出勤；同一局对同一人一次；可回复一次 |

## 四、不要说的话（踩雷清单）

1. 不要说"推荐算法是我的核心创新"——它是主流维度上的可解释实现，被追问深度会尴尬；亮点讲状态机/并发/信誉/闭环；
2. 不要引用已被替换的旧口径（如"先审后发""发布者取消扣 5 分"）；
3. 不要虚构未做过的数据（如"压测支持 100 并发"）——目前无实测，被追问就说"目标是 100 并发，压测是下一步"；
4. 演示失败时的兜底话术："这个分支我在单元测试里覆盖了，现场网络/环境原因我再跑一次"——不要现场改代码。

## 五、现场演示建议流程（10 分钟版）

1. **开场**：H5 广场（游客视角，展示推荐排序/筛选）；
2. **主线**：学生账号登录 → 发布组局（展示拦截：时长超 24h 被拒 / 敏感词被拒）→ 换账号报名 → 发布者审批 → 满员转"已满员" → 第三人候补 → 取消一个名额 → 自动递补；
3. **信誉**：标记未到场 → 信誉分下降 → 低于 60 后发帖被拦（可提前准备一个低分账号）；
4. **管理端**：数据看板 → 处理一条举报（联动下架）→ 封禁用户 → 导出 CSV；
5. **收尾**：展示 CI 与测试报告（111 例全绿）。

**演示前 10 分钟检查清单**：后端已启动（8080）、两个前端已启动（3000/3001）、提前用"未来时间"造好 1-2 条招募中帖子、准备好两个账号（发布者/报名者）、浏览器开好两个窗口（如已切换 Redis 模式，先启动 Redis）。
