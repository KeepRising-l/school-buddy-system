## 一、核心结论：不是"都不做"，而是"分层"

《17》里列了近 20 条不足，但它们**不是同等重要的**。作为毕设，花同样的时间，不同条目换来的答辩加分差距很大。本计划把它们分成三类：

| 分类 | 定 义 | 如何处理 |
|------|-------|---------|
| **A. 必做** | 工程化/质量/安全的**硬化**，工作量可控，但直接体现"专业开发素养"，是评审最看重的 | **全部实现** |
| **B. 可选亮点** | 让项目有"高于平均水平的亮点"，但不做也不影响通过 | 按精力选 1~2 个 |
| **C. 只讲不做** | 大而重的**展示型新功能**，实现成本高、演示风险大、对通过边际价值低 | **不实现**，作为答辩 PPT"未来展望"素材 |

> **澄清**：常说的"别添加新功能"只针对 **C 类**。A 类是"硬化"，不是新功能，务必做。

## 二、A 类 · 必做（按性价比排序）

统计：**6 项**，全做完约 1.5~2.5 周（业余时间）。

### A1. 单元测试（《17》4.3）

- **做什么**：给核心业务逻辑补 JUnit5 + Mockito 测试，重点：信誉分计算（`CreditServiceImpl`）、报名状态机与人数上限、评价提交校验（`ReviewServiceImpl`）、推荐排序（`RecommendServiceImpl`）。
- **工作量**：中
- **验收标准**：核心 Service 方法覆盖 ≥ 60%，`mvn test` 全绿；每个被测方法覆盖"正常/边界/异常"三种情况。

### A2. README / 小白启动文档 ✅ 已在编写

- **做什么**（已开工，`README.md`）：重写根目录 README 为面向小白的启动指南——精确标注 **JDK 1.8 / Maven 3.6+ / Node 18 / MySQL 8.0 / Redis 5.0**，数据库账号密码（root + `application-local.yml`）说明、**Navicat 运行 `init-all.sql` 一站式建库导入**、Redis 启动、后端与前端的启动步骤、测试账号、常见问题。
- **注意**：按项目实际环境（学校用本地 MySQL + Navicat，**无 Docker / 无 Redis 教学**），为降低小白门槛优先保证"只装 MySQL 也能说明清楚"；已提供 Redis 的 Windows 安装方式，并建议后续可把 Redis 做成**可选依赖**（`redis.enabled` 开关 + 优雅降级），让"仅装 MySQL 即可运行"。
- **工作量**：低

### ~~A3. Docker Compose 一键部署~~ ❌ 不采用

> **（根据实际环境取消）** 学校环境使用本地 MySQL + Navicat，无 Docker、无 Redis 教学。容器化反而增加小白理解成本，不适用。

### A4. 接口限流防刷（《17》3.1）

- **做什么**：基于 Redis 的滑动窗口/计数器限流，用拦截器或 AOP 方式限流写接口（发帖、报名、举报、注册）。Redis 项目已在用，无新依赖。
- **工作量**：中
- **验收标准**：同一用户在短时间内高频调用发帖/举报接口返回限流提示，不落库。

### A5. 操作日志审计（《17》3.4）

- **做什么**：新增 `sys_operation_log` 表 + AOP 切面，自动记录管理端关键操作（封禁用户、下架帖子、处理举报、公告发布），含操作人/时间/IP/结果。
- **工作量**：中
- **验收标准**：管理端做一次封禁，审计表有对应记录；后台有简单查询（可并入现有库表/管理页）。

### A6. N+1 查询优化（《17》2.2）

- **做什么**：优化广场列表、帖子详情、举报列表的关联查询，把"逐条查"改为批量 `IN` 查询再组装（`PostConverter` 收敛转换逻辑，见 4.4）。
- **工作量**：中
- **验收标准**：广场列表 20 条帖子的总 SQL 次数明显下降（如 20+ 次 → 3~5 次）。

## 三、B 类 · 可选亮点（选 1~2 个即可）

| 方向 | 对应《17》 | 亮点 / 答辩话术 | 工作量 |
|------|-----------|----------------|--------|
| 推荐算法粗排+精排 & Redis 缓存 | 2.1 | 讲"算法+性能"：先粗排取 TopN 再精排，缓存命中降库压 | 中 |
| 评价举报申诉 | 1.5 | 补全评价闭环：恶评可申诉→管理员复核撤下，串联已有举报/风控 | 中 |
| 浏览器通知推送 | 1.4 | 低难度演示直观：报名通过/取消时 Notification API 提醒 | 低 |
| XSS 过滤 + 违禁词 DFA | 3.2/3.3 | 讲"安全纵深"：输入净化 + DFA 前缀树敏感词 | 低-中 |
| 连接池监控/慢 SQL | 2.3 | 讲"可观测性"：Actuator + AOP 耗时统计 | 低 |

> **建议**：若只选 1 个，选「推荐算法优化 + 缓存」——它同时覆盖算法与性能两个高含金量话题，答辩最能讲。

## 五、可执行排期（四阶段）

> 每个阶段结束都做一次回归 + 提交，保持 `main` 可运行。

### 阶段① 工程基础（约 2~3 天）
- A2 README/小白启动文档（✅ 已完成）、根目录文档索引整理
- 目标：一个只装了 JDK/Maven/Node/MySQL 的小白，按文档能用 Navicat 一键跑起来

### 阶段② 代码质量（约 4~6 天）
- A6 N+1 优化、A1 单元测试（先补核心，再补其余）
- 目标：`mvn test` 全绿，列表接口 SQL 明显减少

### 阶段③ 安全与审计（约 3~5 天）
- A4 接口限流、A5 操作日志审计
- 目标：写接口可限流，管理操作可追溯

### 阶段④ 亮点 + 收尾（约 3~5 天）
- 选做 B 类亮点 1~2 个
- 全量回归、整理答辩素材（架构图、功能清单、性能对比截图、《17》更新）
