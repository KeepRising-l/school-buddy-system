## 一、全景扫描总评：现状体检与历史包袱诊断

### 1.1 项目演进脉络与当前基线
本项目已经历过一次从 `backend-legacy`（Java 8 + Spring Boot 2.7）到 `backend-v2`（Java 17 + Spring Boot 3.3.5，按业务模块 `module/*` 分包）的迁移，并做过一轮安全加固、CAS 并发条件更新、`AuxStore`（MySQL/Redis 双实现）改造、移动端安全区适配以及 137 例单元测试建设。

**已具备的工程亮点（应予保留）**：
1. **核心状态机**：帖子 5 态（`RECRUITING` / `FULL` / `ONGOING` / `FINISHED` / `CANCELLED`）与报名 7 态（`PENDING` / `APPROVED` / `REJECTED` / `CANCELLED` / `WAITLIST` / `ATTENDED` / `NOSHOW`）主干清晰；
2. **并发控制意识**：关键写路径使用了 `UPDATE ... WHERE status = ?` 条件更新与 `current_people < max_people` 原子自增；
3. **零外部依赖启动**：通过 `AuxStore` 将登录锁定、浏览去重、上传限频、举报去重、接口限流默认落地到 MySQL `aux_kv` 表，同时保留 Redis 一键切换能力。

### 1.2 “弱 AI 时代”遗留的四大核心痛点
尽管主干可运行，但深度扫描全量代码后发现，早期生成代码特有的**“表面能跑、细节断链、逻辑自相矛盾、缺乏真智能”**特征依然明显：

1. **前后端契约错位与“假功能/半截工程”**：
   - 后端写了弹窗公告接口、管理端写了发布页面，但 **H5 前端从头到尾没有写任何一行拉取或展示公告的代码**；
   - 管理端标签页写了 `{{ row.status === 1 ? '禁用' : '启用' }}` 切换按钮，但后端列表接口只查 `status = 1`，禁用后标签直接从后台消失，且后端接口把状态硬编码为 `0`（永远无法重新启用）；
   - 管理端帖子列表的“分类筛选”下拉框，把**项目标签名**（如“篮球”“王者荣耀”）当成了**大类名称**（如“球类”“电竞”）传给后端，导致后台按分类筛选帖子 **100% 查不出数据**；
   - 详情页评论时间字段后端叫 `createdTime`，前端读 `createTime`，导致**全站评论时间永远空白**。
2. **数据库约束与 ORM 逻辑删除冲突（隐蔽死锁）**：
   - `favorite`（收藏表）开启了 MyBatis-Plus `@TableLogic`（取消收藏 = `UPDATE favorite SET deleted = 1`），但数据库建了唯一索引 `uk_user_post (user_id, post_id)`（不含 `deleted`）。结果：**用户一旦取消收藏某个帖子，再次收藏该帖时必触发 `DuplicateKeyException` 报错 500**。
3. **局部优化不彻底，仍有 6 处 N+1 查询与 150 次循环 SQL**：
   - 仅广场列表和举报列表消除了 N+1；评论列表、报名管理列表、收到的申请、我的发布、我的预约、个人主页等 **6 个高频接口仍在 for/stream 循环中逐条 `selectById`**；
   - 管理端数据统计（`StatsServiceImpl`）中，发帖趋势、成局趋势、活跃趋势、用户增长、留存分析全部采用 **Java `for` 循环按天发 SQL**，导出一次 30 天趋势 CSV 会瞬间轰炸数据库 **150 条 SQL**。
4. **“伪智能”与高摩擦交互**：
   - 所谓“智能内容审核”只是在 `SensitiveWordService.java` 里硬编码了 28 个词的数组 `contains`；
   - 发布一个搭子组局需要手动点选 10 个表单项（4 个日期/时间滚轮弹窗）；
   - 推荐算法缺乏“推荐理由”透出，前端用户感知不到“为什么推荐给我”。

## 二、代码级缺陷与 Bug 清单（Evidence-First 逐行定位）

以下 **11 个真实缺陷** 均经源码级交叉核对确认，按严重程度分为 P0（功能破损/数据异常）与 P1（功能断链/体验缺陷）：

### 2.1 P0 级缺陷（功能破损 / 逻辑漏洞）

#### [P0-1] 取消收藏后再次收藏必报 500（逻辑删除与唯一键冲突）
- **定位**：
  - 数据库：[`database/schema.sql`](file:///d:/Code/school-buddy-system-gyy/database/schema.sql#L178-L188) 中 `favorite` 表定义了 `UNIQUE KEY uk_user_post (user_id, post_id)` 与 `deleted` 列；
  - 实体：[`Favorite.java`](file:///d:/Code/school-buddy-system-gyy/backend-v2/src/main/java/com/buddy/module/favorite/entity/Favorite.java#L30-L31) 在 `deleted` 字段上标注了 `@TableLogic`；
  - 服务：[`FavoriteServiceImpl.java`](file:///d:/Code/school-buddy-system-gyy/backend-v2/src/main/java/com/buddy/module/favorite/service/impl/FavoriteServiceImpl.java#L40-L69)。
- **根因**：`cancel()` 调用 `favoriteMapper.delete(...)` 时，MyBatis-Plus 将其转为 `UPDATE favorite SET deleted = 1 WHERE user_id = ? AND post_id = ? AND deleted = 0`。当用户再次点击收藏调用 `add()` 时，`selectCount` 只查 `deleted = 0`（返回 0），随后执行 `INSERT INTO favorite`，直接撞上物理唯一索引 `uk_user_post` 抛出 `DuplicateKeyException`！
- **修复方案**：收藏关系无审计追溯价值，移除 `Favorite.deleted` 上的 `@TableLogic`，将取消收藏改为物理删除（或在 `FavoriteMapper` 中使用 `INSERT ... ON DUPLICATE KEY UPDATE deleted = 0, created_time = NOW()`，与 `ApplyServiceImpl` 复用旧行的思路统一）。

#### [P0-2] 收藏夹内存过滤破坏分页，导致后续收藏永久无法加载
- **定位**：[`FavoriteServiceImpl.java`](file:///d:/Code/school-buddy-system-gyy/backend-v2/src/main/java/com/buddy/module/favorite/service/impl/FavoriteServiceImpl.java#L73-L98) 与 [`MyFavorites.vue`](file:///d:/Code/school-buddy-system-gyy/frontend-h5/src/views/mine/MyFavorites.vue#L69-L81)。
- **根因**：后端先对 `favorite` 表分页取 `size=10` 条，再在内存中用 `.filter(p -> p.getIsAuditPass() == 1 && !"CANCELLED".equals(p.getStatus()))` 剔除已下架或已取消的帖子。若第一页 10 条收藏中有 1 条帖子被取消，接口返回的 `records.length` 变为 `9`。而前端 `MyFavorites.vue` 第 74 行写的是 `finished.value = (res.data?.records?.length || 0) < size`（`9 < 10` 为 `true`），直接停止翻页，导致第 2 页以后的收藏永远加载不出来！且被取消的帖子在收藏夹消失后，用户连“取消收藏”清理它的入口都没有。
- **修复方案**：
  1. SQL 层通过 `JOIN post` 关联查询，或者不在收藏夹隐藏 `CANCELLED` 状态的帖子（UI 上已有 `CANCELLED -> 已取消` 的红色标签映射，允许用户看到“已取消”并手动移除收藏）；
  2. 前端分页终止条件统一改为 `page.value >= (res.data?.pages || 1)` 或 `favoriteList.value.length >= res.data?.total`。

#### [P0-3] 满员候补递补后，错误将帖子回退为 `RECRUITING`，导致路人插队
- **定位**：[`ApplyServiceImpl.java`](file:///d:/Code/school-buddy-system-gyy/backend-v2/src/main/java/com/buddy/module/apply/service/impl/ApplyServiceImpl.java#L371-L388)。
- **根因**：
  ```java
  if (PostStatus.FULL.equals(post.getStatus())) {
      promoteWaitlist(post); // 将队首 WAITLIST 改为 PENDING，注意：此时 current_people 仍为 max_people - 1
      post = postMapper.selectById(post.getId());
      if (post.getCurrentPeople() < post.getMaxPeople()) { // 恒为 true！
          postMapper.update(..., .set(Post::getStatus, PostStatus.RECRUITING));
      }
  }
  ```
  因为 `promoteWaitlist` 只是把候补第 1 位变成 `PENDING`（待发布者审核，尚未 `incrementCurrentPeople`），所以第 380 行 `post.getCurrentPeople() < post.getMaxPeople()` **永远成立**，帖子状态被直接改回 `RECRUITING`。如果此时候补队列还有第 2、第 3 位同学在排队（`WAITLIST`），新来的路人看到帖子变成“招募中”，可以直接点击“报名参加”进入 `PENDING`，排在候补队列前面被发布者优先看到！
- **修复方案**：若候补队列中仍有 `WAITLIST` 记录，或刚成功递补了候补者且还有其他候补者，应保持候补顺序或在审批拒绝递补者时继续调用 `promoteWaitlist(post)`（目前 `reject()` 方法第 473-513 行**完全没有触发候补递补**，发布者一旦拒绝递补上来的第 1 位，候补第 2 位永远不会被递补！）。

#### [P0-4] 管理端帖子列表“分类筛选”数据源错误，筛选 100% 失效
- **定位**：[`PostList.vue`](file:///d:/Code/school-buddy-system-gyy/frontend-admin/src/views/post/PostList.vue#L15-L19) 与第 136-144 行。
- **根因**：`PostList.vue` 调用 `getTagList()`（返回的是具体项目标签，如 `name: "篮球"`, `category: "球类"`），然后用 `<el-option v-for="tag in tagOptions" :label="tag.name" :value="tag.name" />` 绑定到 `searchForm.category`。管理员在下拉框选“篮球”，请求参数为 `category=篮球`，而后端 [`AdminPostServiceImpl.java`](file:///d:/Code/school-buddy-system-gyy/backend-v2/src/main/java/com/buddy/module/post/service/impl/AdminPostServiceImpl.java#L74) 查的是 `WHERE category = '篮球'`（库里存的是 `'球类'`），永远返回空列表！
- **修复方案**：`PostList.vue` 改调 `getTagCategories()`（`GET /api/admin/tag/categories`），下拉选项绑定分类名（`球类` / `电竞` / `桌游` / `跑步`）。

#### [P0-5] 管理端标签禁用后直接消失、无法重新启用，且表格合并行错位
- **定位**：
  - 后端：[`AdminTagController.java`](file:///d:/Code/school-buddy-system-gyy/backend-v2/src/main/java/com/buddy/module/tag/controller/admin/AdminTagController.java#L31-L35) 与 [`TagServiceImpl.java`](file:///d:/Code/school-buddy-system-gyy/backend-v2/src/main/java/com/buddy/module/tag/service/impl/TagServiceImpl.java#L36-L54)；
  - 前端：[`TagManage.vue`](file:///d:/Code/school-buddy-system-gyy/frontend-admin/src/views/tag/TagManage.vue#L10) 与第 87-108 行。
- **根因**：
  1. `AdminTagController.getAllTags()` 直接复用了用户端的 `tagService.getAllTags()`（带 `.eq(InterestTag::getStatus, 1)`），导致管理员点击“禁用”后，该标签直接从管理后台表格中消失；
  2. `TagServiceImpl.disableTag()` 硬编码了 `tag.setStatus(0)`，不支持切换回 `1`；
  3. `TagManage.vue` 中 `<el-table :data="tableData" :span-method="categorySpanMethod">`，表格渲染用的是未按分类聚类的 `tableData`，而 `categorySpanMethod` 内部却用 `sortedData.value` 计算合并行数，一旦新增标签属于已有分类但排在末尾，单元格合并就会错位吞行。
- **修复方案**：
  1. `TagService` 新增 `getAdminTagList()`（不过滤 `status=1`，按 `category ASC, sort_order ASC` 排序）与 `toggleTagStatus(Long tagId)`；
  2. `TagManage.vue` 的 `<el-table>` 绑定 `:data="sortedData"`。

### 2.2 P1 级缺陷（功能断链 / 展示失效 / 规则不一致）

#### [P1-1] 帖子详情页评论时间全部空白（字段名拼写不一致）
- **定位**：[`PostDetail.vue`](file:///d:/Code/school-buddy-system-gyy/frontend-h5/src/views/post/PostDetail.vue#L121) vs [`CommentVO.java`](file:///d:/Code/school-buddy-system-gyy/backend-v2/src/main/java/com/buddy/module/post/dto/CommentVO.java#L27)。
- **根因**：后端返回 JSON 字段为 `createdTime`，前端模板写的是 `{{ formatTime(c.createTime) }}`，少了字母 `d`。
- **修复方案**：前端改为 `{{ formatTime(c.createdTime) }}`。

#### [P1-2] 弹窗公告与系统公告在 H5 用户端完全未接入
- **定位**：后端 [`AnnouncementController.java`](file:///d:/Code/school-buddy-system-gyy/backend-v2/src/main/java/com/buddy/module/announcement/controller/AnnouncementController.java#L24) 已实现 `GET /api/announcement/latest-popup`，但 `frontend-h5/src/` 下无任何调用代码。
- **根因**：早期开发只做了后端和管理端，漏掉了 H5 端对接。
- **修复方案**：在 `frontend-h5/src/api/` 新增 `announcement.js`，在 `Square.vue` 挂载时拉取最新弹窗公告（按公告 `id` 记录 `localStorage` 已读状态，同一条弹窗公告对同一设备只弹一次），并增加顶部公告通知栏（`van-notice-bar`）展示普通公告。

#### [P1-3] 提交评价后信誉分不立即重算，且多选评价标签只计算第一个
- **定位**：
  - [`ReviewServiceImpl.java`](file:///d:/Code/school-buddy-system-gyy/backend-v2/src/main/java/com/buddy/module/review/service/impl/ReviewServiceImpl.java#L120)：`reviewMapper.insert(review)` 后未触发 `creditService.recalculateUserCredit(request.getTargetUserId())`；
  - [`CreditServiceImpl.java`](file:///d:/Code/school-buddy-system-gyy/backend-v2/src/main/java/com/buddy/module/credit/service/impl/CreditServiceImpl.java#L156) 与 [`UserServiceImpl.java`](file:///d:/Code/school-buddy-system-gyy/backend-v2/src/main/java/com/buddy/module/user/service/impl/UserServiceImpl.java#L431)：用 `tag.split(",")[0].trim()` 丢弃了用户勾选的第 2、3 个评价标签。
- **修复方案**：
  1. `submitReview` 事务内插入评价后立即调用 `creditService.recalculateUserCredit(request.getTargetUserId())` 并发送收到评价的通知；
  2. 标签云统计展开全部逗号分隔标签（`Arrays.stream(r.getTag().split(","))`）；信誉分影响对单条评价的所有标签求极值或加权限幅（如单次正向最高 `+2`、负向最低 `-10`），避免选顺序不同导致得分不同。

#### [P1-4] H5 详情页报名资格预检逻辑短路，无段位帖子跳过信誉分与性别预检
- **定位**：[`PostDetail.vue`](file:///d:/Code/school-buddy-system-gyy/frontend-h5/src/views/post/PostDetail.vue#L466-L492)。
- **根因**：第 473 行 `if (!p.requireLevel || p.requireLevel === 0) return ''` 写在了信誉分（`<60`）和性别要求（`requireGender`）判断的**前面**！导致所有不设段位的活动（如桌游、夜跑、学习，或球类不限段位），前端预检全部失效，低信誉或性别不符的用户依然能点击报名按钮，直到后端报错。
- **修复方案**：将信誉分和性别预检移到 `if (!p.requireLevel || p.requireLevel === 0)` 之前。

#### [P1-5] 前后端发布时间校验不一致（前端强行限制必须提前 1 小时）
- **定位**：[`PostCreate.vue`](file:///d:/Code/school-buddy-system-gyy/frontend-h5/src/views/post/PostCreate.vue#L488) vs [`PostServiceImpl.java`](file:///d:/Code/school-buddy-system-gyy/backend-v2/src/main/java/com/buddy/module/post/service/impl/PostServiceImpl.java#L117)。
- **根因**：后端只要求 `startTime > now`，但前端写死了 `start <= now.getTime() + 60 * 60 * 1000` 拦截弹窗。校园场景中“半小时后去球场/食堂”非常普遍，且限制 1 小时后导致用户无法在 UI 上直接发帖测试“提前 30 分钟活动提醒”功能。
- **修复方案**：前端放宽为开始时间晚于当前时间（或至少提前 5 分钟），与后端口径对齐。

#### [P1-6] `MyPosts.vue` 与 `MyApplies.vue` 状态与操作残缺
- **定位**：
  - [`MyPosts.vue`](file:///d:/Code/school-buddy-system-gyy/frontend-h5/src/views/mine/MyPosts.vue#L7-L12)：Tab 缺少 `FULL`（已满员）和 `CANCELLED`（已取消），且弹出层只能审批 `PENDING`，不能像详情页那样对 `ONGOING/FINISHED` 帖子标记出勤；
  - [`MyApplies.vue`](file:///d:/Code/school-buddy-system-gyy/frontend-h5/src/views/mine/MyApplies.vue#L65-L68)：“收到的邀请”（实为“收到的申请”）列表中只写了 `PENDING / APPROVED / REJECTED` 三个 `v-if`，当状态为 `WAITLIST / CANCELLED / ATTENDED / NOSHOW` 时状态标签直接消失。
- **修复方案**：统一复用 `applyStatusType` / `applyStatusText` 映射，补全 `MyPosts.vue` 的出勤标记与评价快捷入口。

## 三、性能、数据库与架构深水区优化方案

### 3.1 彻底消灭剩余 6 处 N+1 查询
此前仅优化了 `PostConverter` 和 `ReportServiceImpl`，以下 6 处仍存在循环查库，需统一改为 `selectBatchIds` + 内存 `Map` 组装：

| 序号 | 所在位置 | 当前问题 | 优化方式 |
|-----|---------|---------|---------|
| 1 | [`CommentServiceImpl.getComments`](file:///d:/Code/school-buddy-system-gyy/backend-v2/src/main/java/com/buddy/module/post/service/impl/CommentServiceImpl.java#L88-L103) | 每页 100 条评论触发 100 次 `userMapper.selectById` | 收集 `userId` 集合，1 次 `selectBatchIds` 查出评论者昵称与头像 |
| 2 | [`ApplyServiceImpl.getApplyList`](file:///d:/Code/school-buddy-system-gyy/backend-v2/src/main/java/com/buddy/module/apply/service/impl/ApplyServiceImpl.java#L531-L542) | 每条报名触发 1 次 `userMapper.selectById` | 批量查询申请人 `Map<Long, User>` |
| 3 | [`ApplyServiceImpl.getReceivedApplies`](file:///d:/Code/school-buddy-system-gyy/backend-v2/src/main/java/com/buddy/module/apply/service/impl/ApplyServiceImpl.java#L567-L585) | 每条记录查 1 次 `userMapper` + 1 次 `postMapper` | 复用上方已查出的 `myPosts` 转为 `Map`，批量查询申请人 |
| 4 | [`UserServiceImpl.getMyPosts`](file:///d:/Code/school-buddy-system-gyy/backend-v2/src/main/java/com/buddy/module/user/service/impl/UserServiceImpl.java#L359-L361) | 内部私有 `convertToPostVO` 逐条查 `userMapper` | 直接注入并调用 `postConverter.toVOList(postPage.getRecords())`，删除重复的私有转换方法 |
| 5 | [`UserServiceImpl.getMyApplies`](file:///d:/Code/school-buddy-system-gyy/backend-v2/src/main/java/com/buddy/module/user/service/impl/UserServiceImpl.java#L379-L396) & [`getUserProfile`](file:///d:/Code/school-buddy-system-gyy/backend-v2/src/main/java/com/buddy/module/user/service/impl/UserServiceImpl.java#L461-L485) | 参加过的组局逐条 `postMapper.selectById`；收到的评价逐条查评价人与帖子 | 批量 `selectBatchIds` 一次加载 |
| 6 | [`PostServiceImpl.getPostDetail`](file:///d:/Code/school-buddy-system-gyy/backend-v2/src/main/java/com/buddy/module/post/service/impl/PostServiceImpl.java#L295-L305) | 发布者兴趣标签逐个 `interestTagMapper.selectById` | 改为 `interestTagMapper.selectBatchIds` |

### 3.2 重构 `StatsServiceImpl`：从 150 次循环 SQL 降为单次聚合
- **现状**：[`StatsServiceImpl.java`](file:///d:/Code/school-buddy-system-gyy/backend-v2/src/main/java/com/buddy/module/admin/service/impl/StatsServiceImpl.java#L129-L344) 中，`getPostTrend(30)`、`getSuccessMatchTrend(30)`、`getActiveUserTrend(30)`、`getUserGrowthTrend(30)`、`getRetention(30)` 均在 `for` 循环中按天执行 `selectCount`。打开一次管理端“数据统计”页签会瞬間发出 **120+ 条 SQL**。
- **优化方案**：
  - 在 `PostMapper`、`PostApplyMapper`、`UserMapper` 中仿照 `ReportMapper.countDailySince`，编写 `GROUP BY DATE(created_time)` 聚合 SQL；
  - Java 层用 `LocalDate` 循环构造近 $N$ 天的日期骨架，从聚合 `Map<String, Long>` 中 `getOrDefault(dateStr, 0L)` 补零；
  - 优化后，每个趋势接口从 **30~60 条 SQL 降至 1~2 条 SQL**，响应时间从百毫秒级降至 `<5ms`。

### 3.3 缓存一致性与浏览量原子化
1. **推荐缓存失效补齐**：
   - 在 [`PostStatusTask.java`](file:///d:/Code/school-buddy-system-gyy/backend-v2/src/main/java/com/buddy/module/post/task/PostStatusTask.java#L38) 推进帖子到 `ONGOING` / `FINISHED` 且 `count > 0` 时，调用 `cacheEpoch.bump()`，防止已开始/已结束的组局继续留在广场推荐缓存中；
   - 在 `ApplyServiceImpl.approve` / `cancelApply` 触发人数变化或 `RECRUITING <-> FULL` 状态切换时调用 `cacheEpoch.bump()`，保证广场卡片人数进度条实时准确。
2. **浏览量原子更新与游客去重**：
   - `PostMapper` 新增 `@Update("UPDATE post SET view_count = view_count + 1 WHERE id = #{postId}") int incrementViewCount(@Param("postId") Long postId)`，替代先查后改；
   - 游客访问详情页时，若 `userId == null`，取客户端 IP（`request.getRemoteAddr()`）作为去重后缀 `post:view:{postId}:ip:{ip}`，解决全站游客共用 `:null` 的问题。

### 3.4 仓库清理与代码规范化
1. **清理仓库垃圾文件**：删除根目录残留的 `dump.rdb`、`backend-v2/app.log`、`backend-v2/app-err.log`，并在 `.gitignore` 中忽略 `*.rdb`、`*.log`；
2. **归档或移除 `backend-legacy`**：将 `backend-legacy` 移至独立历史分支或彻底移除，消除双后端维护心智负担；

## 四、产品功能与用户体验（UX）重塑规划

围绕“找搭子 → 约搭子 → 履约核销 → 信用沉淀”全链路，补齐以下关键产品设计：

### 4.1 广场首页体验升级：公告触达 + “猜你喜欢”横向推荐位
1. **顶部滚动公告栏 + 强提醒弹窗**：对接 `/api/announcement/latest-popup` 与新增的 `/api/announcement/active-list`，让管理端发布的校园防诈骗提醒、场馆开放通知真正触达学生；
2. **“你可能感兴趣”横向精选位（闭合 PRD 5.3.2 缺口）**：
   - 在广场搜索栏下方、主列表上方，为已登录且设置了兴趣标签的学生展示 **Top 5 个性化精选卡片**（横向滑动）；
   - 每张卡片展示**推荐理由胶囊**（例如：`🏀 匹配你的篮球·熟手`、`⚡ 距开始仅剩 2 小时`、`🌟 100分靠谱局主`），让推荐算法从“黑盒排序”变成用户直观可感的亮点。

### 4.2 组局履约闭环升级：活动签到码核销（防扯皮机制）
- **痛点**：现有机制完全依赖发布者事后手动点击“已出勤 / 未到场（-10分）”，容易出现发布者忘记标记（导致大家都无法互评）或恶意误标未到场引发纠纷。
- **新规划**：
  1. 帖子进入 `ONGOING`（或开始前 30 分钟）时，系统自动为该局生成 **4 位数字活动签到码**（仅发布者可见）；
  2. 线下见面时，参与者输入 4 位签到码即可**自助完成“已出勤”核销**；
  3. 同时保留发布者手动标记与“一键全员出勤”按钮；若活动结束 24 小时后发布者仍未操作，系统定时任务自动将未标记的 `APPROVED` 参与者默认置为 `ATTENDED`（默认守约原则），彻底解决“局主不点出勤导致参与者无法评价”的死胡同。

### 4.3 个人中心与全局通知体验补齐
1. **底部导航栏（Tabbar）全局未读消息角标**：在 `TabbarLayout.vue` 中拉取未读通知数，在底部“我的”图标右上角显示红点/数字，并在广场页顶部提供快捷消息铃铛入口；
2. **账号安全设置页**：新增修改密码（校验旧密码 + 设置新密码）、补充绑定学号/手机号、微信号选填（同组成员成行后与手机号一同解锁，适应大学生更习惯加微信而非打电话的真实习惯）。

## 五、AI 原生（AI-Native）能力升级规划

针对项目早期“AI 能力弱、全靠手写死规则”的局限，结合现代大模型（支持接入 DeepSeek / 通义千问 Qwen / Gemini 等 OpenAI 兼容接口，**并提供无 API Key 时的本地规则引擎优雅降级**，确保任何环境 100% 可运行、可测试），规划四大高价值 AI 场景：

```
+-----------------------------------------------------------------------------------+
|                        校园搭子系统 · AI Native 智能层架构                        |
+-----------------------------------------------------------------------------------+
|  [H5 用户端]                                              [PC 管理后台]           |
|   ├── 1. AI 一键组局 (一句话自动填表 + 文案润色)            ├── 3. AI 内容风控    |
|   ├── 2. AI 语义找搭子 & 个性化推荐理由徽章                 └── 4. 举报智能研判   |
|   └── 5. 成局破冰小秘书 (共同兴趣话题 & 行前贴士)                                 |
+-----------------------------------------+-----------------------------------------+
                                          |
                                          v
+-----------------------------------------------------------------------------------+
|  com.buddy.module.ai.client.LlmClient (统一 AI 网关接口)                          |
|   ├── OpenAiCompatibleClient (配置了 API Key 时：调用 DeepSeek / Qwen / Gemini)   |
|   └── FallbackRuleAiClient   (未配置或超时降级：正则意图解析 + 模板生成，零依赖)  |
+-----------------------------------------------------------------------------------+
```

### 5.1 场景一：AI 一键成局助手（Smart Post Composer）
- **痛点**：目前发布组局需要依次填写标题、分类、具体项目、开始日期、开始时间、结束日期、结束时间、地点、人数、段位、性别、描述共 **12 个交互步骤**，移动端操作繁琐。
- **AI 升级方案**：
  - 在 `/post/create` 页面顶部增加 **「✨ AI 一键填表」** 智能输入框；
  - 学生输入一句自然语言，如：*“明天晚上7点到9点在南区体育馆约3个人打羽毛球，要求熟手以上，AA场地费”*；
  - 后端 `POST /api/ai/parse-post` 结合当前系统时间与可用标签库（`interest_tag`），自动提取并返回结构化 JSON：
    ```json
    {
      "title": "南区体育馆羽毛球3缺1，熟手局来！",
      "category": "球类",
      "tagId": 2,
      " tagName": "羽毛球",
      "startTime": "2026-11-19 19:00:00",
      "endTime": "2026-11-19 21:00:00",
      "location": "南区体育馆",
      "maxPeople": 4,
      "requireLevel": 3,
      "requireGender": 0,
      "description": "明晚 19:00-21:00 南区体育馆羽毛球双打局，要求熟手及以上水平，场地已看，费用 AA，鸽子勿扰！"
    }
    ```
  - 前端自动填充全部表单项并高亮提示，用户确认后一键发布！同时提供 **「✨ AI 润色描述」** 按钮，帮社恐学生把干巴巴的几个字扩写成热情清晰的招募帖。

### 5.2 场景二：可解释推荐理由生成与语义搜索（Explainable Recommendation）
- **痛点**：目前推荐算法只算出一个 `double score`，前端列表看不出推荐与普通排序的区别。
- **AI 升级方案**：
  - `PostVO` 新增 `recommendReasons`（`List<String>`）与 `matchPercent`（匹配度百分比，如 `92% 契合`）；
  - 在推荐打分时，同步生成 1~3 个可解释的动态标签：
    - 命中用户高段位标签 → `🎯 契合你的「羽毛球·熟手」`
    - 发布者信誉 ≥ 95 → `🛡️ 100分全勤局主`
    - 同学院发布 → `🎓 计算机学院校友`
    - 即将开始且缺 1 人 → `🔥 差1人即刻成局`
  - 广场卡片直观展示匹配度与理由标签，答辩演示时切换不同账号登录，不仅排序不同，每张卡片上的推荐理由也千人千面！

### 5.3 场景三：双层智能内容安全防线（DFA 树 + AI 语义风控）
- **痛点**：目前 [`SensitiveWordService.java`](file:///d:/Code/school-buddy-system-gyy/backend-v2/src/main/java/com/buddy/module/post/service/SensitiveWordService.java) 仅用 `List.stream().filter(lower::contains)` 遍历 28 个词，既无法防谐音/夹杂符号绕过（如 `代*考`、`兼职日结加V`），也缺乏分类词库。
- **AI 升级方案**：
  1. **第一层（同步毫秒级拦截）**：升级为 **DFA（确定有限状态自动机 / Trie 树）+ 噪音字符跳过（忽略空格、`*`、`-` 等穿插符）**，词库扩充为校园高频风险词（涉诈兼职、刷单、代考代写、软色情、人身攻击）；
  2. **第二层（管理端举报 AI 研判 Copilot）**：在管理端举报详情弹窗中，提供「AI 风险研判建议」（综合被举报对象的历史有效举报次数、信誉分台账、文本风险特征，给出风险等级与处置建议文案）。

### 5.4 场景四：成局破冰小秘书（Icebreaker Copilot）
- **痛点**：大学生经常都是“社恐”，组局满员后不知道怎么开口联系。
- **AI 升级方案**：
  - 在帖子详情页的「联系方式」卡片（仅已通过成员可见）下方，根据本局所有已加入成员的**共同兴趣标签、学院分布、活动类型**，自动生成一段 **「💡 破冰小贴士」**（例如：*“本局 4 位伙伴中有 3 位来自计算机学院，且有 2 位同时喜欢『王者荣耀』！建议提前 10 分钟在南区体育馆正门集合，记得带球拍和水哦~”*），并提供一键复制打招呼话术。
