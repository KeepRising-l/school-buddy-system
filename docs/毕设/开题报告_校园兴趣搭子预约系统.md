## 一、立题依据（课题研究的目的与意义及国内外研究现状）

### （一）课题研究的目的与意义

在高校校园中，"想找人一起做某件事，但凑不齐人"是一种真实且高频的困扰。运动场景中，想打篮球、羽毛球，室友不感兴趣；电竞场景中，想找人组队上分，路人队友配合难以保障；桌游场景中，剧本杀、狼人杀需要凑齐固定人数才能开局；跑步、健身、自习等场景中，一个人难以长期坚持，希望找到节奏相近的伙伴。这些需求的共同特征是**事件向**的：因一件具体的事而结伴，事毕而散——这正是"搭子"这种轻社交关系的典型形态。

然而，学生现有的解决方式普遍低效且缺乏约束。班级群、社团群发消息覆盖面窄，信息很快被日常消息刷屏淹没；表白墙、论坛发帖信息杂乱，无法按兴趣筛选，也没有报名与确认机制；线下随机相约则效率低、不了解对方水平，体验难以保障。究其根本，问题在于**需求与工具之间的错位**：学生的诉求是"围绕一件具体的事，快速凑齐合适的人并确保履约"，而现有手段提供的是"发一条信息，然后听天由命"——活动要素没有结构化，报名没有审批，爽约没有任何后果。

本课题拟设计并实现一个面向高校学生的校园兴趣搭子预约系统，其研究意义体现在以下三个层面。

**其一，在应用层面**，系统把"找搭子"从"发帖拉群"升级为结构化流程：时间、地点、人数、段位与性别门槛全部结构化填写，报名经过发布者审批，满员后自动进入候补队列并在有人退出时自动递补，活动结束后参与者之间互评。同时，系统把"靠谱"这一主观印象转化为可量化的信誉分：临场取消、爽约、被评价均留下记录并影响后续使用权限，使小型社区中的履约行为有了可积累、可失去、有实际后果的信号。

**其二，在技术层面**，本课题并非简单堆砌功能，而是针对组局类业务的两个典型难点做了系统性工程处理。其一是**业务生命周期复杂**：组局帖有招募、满员、进行中、结束、取消五种状态，报名有七种状态，组合分支极多，系统以显式状态机收敛全部合法流转，并以逐条边覆盖的单元测试守护；其二是**并发竞争真实存在**：最后名额的审批争抢、重复取消、重复处置等并发场景，系统统一采用"带预期旧状态的条件更新 + 影响行数校验 + 原子 SQL"的模式解决，保证不超卖、不重复处理、重复操作幂等。这些处理使系统的工程完成度显著区别于常见的功能堆砌型毕设。

**其三，在方法层面**，本课题在若干机制设计上做了面向校园场景的取舍：推荐排序采用可解释的加权公式（兴趣匹配、时间重合、发布者信誉、热度）而非深度模型，以可解释性换取对冷启动与"黑盒结果难以说明"的规避；信誉约束与业务权限直接打通（低于阈值禁止发帖报名、推荐沉底），验证"信用机制调节小型社区行为"的可行性；候补递补机制在同类产品中较少见，对"名额利用率"这一具体问题给出了事务内闭环的解法。这些设计对面向垂直小场景的社交预约类系统具有一定的参考价值。

### （二）国内外研究现状

#### 1. 国外研究现状

国外对"线上群体活动与线下事件结合"的研究起步较早，围绕事件型社交网络、推荐算法、信任机制与数据一致性等方向形成了较为丰富的成果。

**在事件型社交网络与群体活动推荐方面**，国外学者提出了事件型社交网络（Event-Based Social Network，EBSN）的概念，用于描述将线上社交关系与线下真实活动相结合的平台形态，Meetup、Plancast 等是其典型代表。EBSN 场景中用户通常以"群组"而非个体的形式参与活动，因此群体事件推荐成为该领域的重要任务。Liao 等（2022）针对群体事件推荐中显式信息与隐式信息相互割裂、数据稀疏的问题，提出了图多头注意力网络（GMAN）模型，将用户显式属性图与隐式社交图统一建模；Deng 等（2023）进一步引入异构属性图，同时考虑用户的长短期偏好，在真实数据集上取得了优于基线的推荐效果。这些研究说明，**围绕"事件 + 群体 + 兴趣"的推荐已具备成熟的方法论**，但其关注点集中在推荐算法本身，对活动的组织流程（名额管理、报名审批、退出递补、履约约束）少有涉及。

**在推荐系统与冷启动方面**，Li 等（2024）在综述中系统总结了推荐系统的最新进展，覆盖个性化推荐与群体推荐的主要分类，并讨论了鲁棒性、数据偏差与公平性等议题；LeBlanc 等（2024）从统计学视角回顾了推荐系统的建模范式与评估方法。针对新平台普遍面临的冷启动问题，Yuan 与 Hernandez（2023）对用户冷启动问题进行了系统综述，将解决思路归纳为数据驱动与方法驱动两类；Dadgar 与 Hamzeh（2022）则利用社交信任信息缓解协同过滤的冷启动与数据稀疏问题，证明**社交关系可以作为独立的推荐信号**。这些成果为"以兴趣标签与社交属性为输入的轻量推荐"提供了理论支持。

**在信任与信誉机制方面**，共享经济领域的研究具有直接借鉴价值。Jiang 等（2024）对共享经济中的信任机制进行了元分析，区分了"对平台的信任"与"对交易对手的信任"两个维度，并检验了评价反馈、提供者声誉等前因变量；Alamoudi 等（2023）研究了平台制度机制（反馈机制、资金托管、提供者认证、应急救助）对用户信任的影响，证实**平台级信誉信号能够显著增强用户对交易对象的信任**。这些研究支持了本课题将"信誉分"作为核心机制的设计路线。

**在并发控制与数据一致性方面**，Huang 等（2022）在《The VLDB Journal》上对竞争负载下的乐观并发控制（OCC）进行了重新评估，指出在合理的实现选择下 OCC 在高竞争场景中依然具备竞争力，并给出了若干优化技术。这类研究为业务系统中广泛使用的"乐观并发 + 条件更新"模式提供了理论基础。

综合来看，国外在推荐算法、信任机制、并发控制等单项技术上积累深厚，但成果多面向大规模通用平台；面向校园小规模社区的"结构化组局工具"的整合性研究相对缺乏，小型垂直场景下的机制设计缺少可复现的工程实践案例。

#### 2. 国内研究现状

国内在校园互助平台类系统的设计与实现方面已有较多实践性成果。张银霞等（2023）基于响应式动态网站模式设计并实现了校园互助系统，讨论了跨平台适配与数据库访问的实现范式；胡成文等（2023）基于微信小程序实现了校园跑腿互助平台，验证了轻量级载体在校园场景中的传播优势；周明月等（2023）基于 SSM 框架实现了大学生互助平台，覆盖寻物启事、二手交易、互助信息发布等功能。这些工作表明，**校园互助类系统的功能形态与技术路线已经比较成熟**，从传统 Web 到小程序均有覆盖，为本课题的系统设计提供了工程参考。

在"搭子"社交现象的研究方面，国内社会学与传播学领域积累了大量一手观察。王昕迪与胡鹏辉（2023）在《中国青年研究》上系统分析了搭子社交的形成逻辑，指出其本质是"领域精准陪伴"——围绕特定场景建立的、边界清晰的轻社交关系；刘航（2023）以"找搭子"为对象研究了当代青年的碎片化社交行动，发现这类需求已从个体尝试演变为群体性的社交趋势。这些研究**直接证实了本课题研究背景的真实性与紧迫性**，同时也提示：需求侧的流行速度快于工具侧的供给，"找搭子"仍缺少与之匹配的结构化工具。

在信用机制与在线社交的经济学研究方面，王勇等（2023）基于大型二手交易平台数据实证发现，数字信用与社交关系均能显著促进交易达成，且二者存在相互强化的作用。这一结论为"在校园小社区中引入可量化信誉分以约束履约行为"的设计提供了实证依据。

在推荐算法方面，国内研究与国外基本同步推进。廖国琼等（2021）在《软件学报》上对事件型社交网络推荐系统进行了系统综述，梳理了矩阵分解、图模型、概率模型与深度学习等推荐技术路线在"事件 + 群体"场景中的应用与演进，说明该问题已引起国内学界的系统关注；吴相帅等（2023）提出了基于图注意力的异构图社交推荐网络，将用户显式社交关系、潜在关联与协作关系统一建模；张杰与陈可佳（2023）提出了关联项目增强的多兴趣序列推荐方法，通过项目关联矩阵与多头自注意力提升推荐效果。这些研究代表了推荐算法的主流演进方向，但也意味着较高的数据与算力门槛——对缺少历史行为数据的新建校园平台而言，**轻量、可解释的排序策略仍然具有现实价值**。

在状态机与软件测试方面，聂钰格等（2022）在《计算机研究与发展》上提出了面向智能服务终端的探索性自适应 FSM 测试方法，利用有限状态机建模系统的状态迁移并自动生成测试用例。该工作与本课题"以显式状态机建模业务生命周期、以状态迁移路径设计测试用例"的工程实践相互呼应，印证了状态机方法在复杂业务系统中的价值。

**现有研究的主要不足可归纳为三个方面：**

其一，**校园互助平台类研究多停留在功能实现层面**。现有文献普遍聚焦于"提供了哪些功能"（信息发布、二手交易、代取代办），对履约约束机制（爽约与临场取消的后果设计）与名额竞争的正确性（并发审批、防超卖）缺乏讨论，系统在真实使用中的行为保障不足。

其二，**社交匹配类研究的撮合对象偏重"人与人的连接"，对"事件向组局"的流程治理关注不足**。搭子场景的核心诉求是"围绕一件事凑齐人"，需要名额管理、报名审批、候补递补等结构化流程支撑，而这些流程设计在现有文献中鲜有系统化呈现。

其三，**单项技术研究与整合式机制设计之间存在断层**。推荐、信誉、状态机、并发控制等技术各自成熟，但面向校园小型社区的"多机制整合设计"缺少可复现、可解释的完整实践：如何在无历史数据的新平台上做可解释推荐、如何让信誉分真正影响业务权限、如何在单体架构内达成可靠的并发一致性，仍缺少细节层面可供参考的案例。

#### 3. 本课题的切入点

针对上述不足，本课题面向校园兴趣组局场景做了以下针对性设计：

（1）**结构化组局与全流程治理**：将组局活动的时间、地点、人数、门槛全部结构化，覆盖"发布 → 报名 → 审批 → 满员 → 候补 → 递补 → 出勤 → 评价"的完整生命周期，补齐现有校园互助类系统在流程治理上的空白。

（2）**信誉分与业务权限的深度联动**：设计"评价影响 + 惩罚台账"双通道的信誉分体系（临场取消扣分、爽约扣分、每日重算兜底），并让信誉分直接决定发帖与报名资格、推荐曝光权重，把"信用约束"落到真实后果上。

（3）**状态机 + 并发一致性的工程模式**：以显式状态机定义帖子与报名的全部合法流转，以"带预期旧状态的条件更新 + 影响行数校验 + 原子 SQL + 行级锁"统一处理并发场景，并以逐条边覆盖的单元测试保证正确性，为同类系统提供可复制的工程范式。

（4）**可解释的轻量推荐**：采用"兴趣标签匹配 + 时间重合 + 发布者信誉 + 热度"的加权公式进行个性化排序，无需训练数据、每一分的来源均可解释，适配新平台的冷启动现实。

（5）**完整可运行的工程交付**：系统包含 H5 用户端与 PC 管理端两个前端、结构化的后端模块、数据库脚本与部署文档，配有 137 例单元测试与持续集成流水线，具备"可运行、可演示、可复现"的完整形态。

## 二、课题研究内容

### 1. 系统分析

本课题旨在设计并实现一个面向高校学生的兴趣搭子预约平台。系统的核心定位是把"找搭子"这一松散、无约束的社交行为，转化为"标签匹配 + 状态化预约 + 信誉分约束"三位一体的结构化服务，解决"找搭子难、约搭子难、搭子不靠谱"三个具体问题。

系统面向三类角色：**游客**可浏览广场、组局详情与他人主页；**学生用户**可注册登录、维护兴趣标签与自评段位、发布组局、报名与候补、参与评价、收发通知；**管理员**负责平台运营监督，包括用户管理、帖子管理、举报处置、标签与公告管理以及数据统计。

从功能需求看，系统覆盖账户与资料、组局发布、广场推荐、报名审批、候补递补、出勤与评价、信誉分、通知、收藏举报、管理端运营共十个功能域，形成"发布 → 报名 → 活动 → 评价 → 信誉"的完整业务闭环。

### 2. 系统总体设计

系统采用前后端分离架构。后端基于 Java 17 与 Spring Boot 3.3.5 实现，按照业务模块分包组织代码（认证、用户、帖子、报名、评价、通知、举报、管理端等），数据存储采用 MySQL 8，共设计 13 张表。

系统主要功能模块设计如下：

**（1）用户端功能（H5，Vue 3 + Vant）**

- **注册与登录**：支持学号/手机号注册与登录，登录失败连续 5 次锁定 30 分钟；令牌采用 JWT 机制，有效期 7 天。
- **个人资料与兴趣标签**：资料编辑（昵称、头像、签名、学院、性别）；兴趣标签设置与自评段位（仅球类、电竞两类启用，档位为萌新至宗师五档）；主页隐私开关；他人主页展示评价标签云与历史组局。
- **组局发布**：填写标题、分类、兴趣标签、开始/结束时间、地点、人数上限、段位与性别门槛、描述；发布前依次进行信誉校验、敏感词校验、时间合法性（开始时间须晚于当前、时长不超过 24 小时）与数量限制校验（同时进行中的组局不超过 5 个）。
- **广场与推荐**：推荐、最新、最热三种排序；推荐按兴趣匹配度、时间重合度、发布者信誉与热度加权计算；支持分类、关键词、时间范围筛选；游客可浏览。
- **报名与候补**：报名提交前进行资格三重校验（信誉分不低于 60、满足段位门槛、满足性别门槛）；发布者对待审核报名进行通过或拒绝；满员后自动转入已满员状态，后来者进入候补队列；已有通过者取消时，候补队首自动递补为待审核并双向通知。
- **出勤与评价**：活动进行中或结束后，发布者标记出勤或未到场（未到场扣除信誉分并通知本人）；活动结束后 7 天窗口内参与者互评（星级、标签、文字），被评价方可回复一次。
- **通知中心**：覆盖新报名、报名结果、候补递补、组局取消、组局下架、活动提醒、系统消息等类型；未读角标、单条与全部已读、按类型筛选；活动开始前 30 分钟自动提醒。
- **其他**：收藏、举报（帖子与用户两类对象、24 小时去重、有效举报联动处置）、公告弹窗。

**（2）管理端功能（PC，Vue 3 + Element Plus + ECharts）**

- **用户管理**：用户列表与检索、详情查看、封禁/解封、重置信誉分。
- **帖子管理**：列表筛选、下架（支持填写下架原因并通知发布者）、逻辑删除。
- **标签管理**：兴趣标签的增、改、禁用。
- **举报处置**：举报列表与详情、判定有效或无效；有效举报联动下架帖子/封禁用户并通知相关方；同一对象累计 3 次有效举报触发自动风控。
- **公告管理**：站内公告与弹窗公告的创建、发布、关闭。
- **数据统计**：总览指标（总用户、总帖子、今日发帖、成功组局、活跃用户、分类 Top5）、发帖/成局/活跃/用户增长趋势、次日与 7 日/30 日留存、浏览至出勤的转化漏斗、举报处理统计，以及用户/帖子/统计数据三类 CSV 导出。

### 3. 关键技术实现

**（1）业务状态机。** 组局帖定义招募中、已满员、进行中、已结束、已取消五种状态，报名定义待审核、已通过、已拒绝、已取消、候补中、已出勤、未到场七种状态。全部合法流转在状态机中集中定义（如终态不可逆、进行中不可取消报名），非法流转在服务层直接拦截，并以逐条状态迁移边覆盖的单元测试保证行为正确。

**（2）并发一致性控制。** 所有状态转换操作统一采用"带预期旧状态的条件更新 + 影响行数校验 + 副作用后置"模式：更新语句在 WHERE 条件中携带预期旧状态，影响行数为零即判定并发冲突并放弃副作用，从而保证重复点击、重复处置只生效一次。名额控制采用原子条件自增（人数小于上限才允许加一），自增失败即判定名额已满并回滚审批事务；发布上限采用用户行级锁（SELECT FOR UPDATE）串行化同一用户的并发发帖。

**（3）信誉分体系。** 信誉分初始为 100，由"评价影响"（靠谱 +2、四星 +1、迟到 -3、爽约 -10 等）与"惩罚台账"（临场取消 -5、未到场 -10）构成，限幅 0 至 100。即时惩罚写入台账并当场重算（保证立即生效），每日凌晨再全量重算兜底（防止历史数据漂移）。信誉分低于 60 的用户禁止发帖与报名、其帖子在推荐中沉底并展示失信标识，分数恢复后自动解禁。

**（4）可解释推荐排序。** 推荐分数按"0.4×兴趣标签匹配度 + 0.3×时间重合度 + 0.2×发布者信誉 + 0.1×热度"加权计算，游客访问时使用简化公式，低信誉发布者的帖子乘以沉底系数。打分阶段采用批量查询一次性加载发布者信息，结果按用户与查询条件进行短时缓存，避免重复计算与 N+1 查询。

**（5）安全与工程质量。** 认证采用 BCrypt 加密存储与 JWT 令牌，密钥外部注入且启动自检；接口按"登录必需/管理员必需/限流"三个层次统一治理；上传按文件内容识别真实类型并限制大小与频率；关键写接口按用户与动作限流。核心业务配有 137 例单元测试，并通过 GitHub Actions 在每次提交时执行后端测试与双前端构建。

### 4. 论文撰写与答辩准备

论文拟按绪论、相关技术、需求分析、系统设计、系统实现、系统测试、总结与展望的结构组织，重点呈现状态机设计、并发一致性方案、信誉分体系与推荐排序的设计取舍；同时整理演示脚本与答辩材料，完成系统演示与答辩。
