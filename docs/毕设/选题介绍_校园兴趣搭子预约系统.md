## 一、选题背景

在高校校园中，"想找人一起做某件事，但凑不齐人"是一种真实且高频的困扰：想打篮球、羽毛球，室友不感兴趣；想找水平相近的队友打游戏上分；剧本杀、狼人杀等桌游需要凑齐固定人数才能开局；一个人跑步、健身、自习难以坚持，希望找到节奏相近的伙伴。这些需求的共同特征是**事件向**的——因一件具体的事而结伴，事毕而散——正是近年来在青年群体中快速流行的"搭子"社交的典型形态。有研究指出，"搭子社交"已成为当代青年新型社交趋势的代表形式，以精准的领域陪伴、较低的情感负担和弹性的关系边界为特征，折射出青年群体碎片化、场景化的社交诉求。

然而，学生目前解决这类需求的方式普遍低效：在班级群、社团群发消息，覆盖面窄且很容易被日常消息刷屏淹没；在表白墙、论坛发帖，信息杂乱、无法按兴趣筛选，也缺乏报名与确认机制；线下随机相约则效率低、不了解对方水平，体验难以保障。与此同时，现有社交平台（小红书、抖音、各类兴趣社区）虽已陆续推出"找搭子"相关功能，但其本质是**内容社区顺带提供的能力**（发帖加私聊），缺少面向"组局"这一事件场景的**结构化工具与履约约束**：活动信息没有结构化（时间、地点、人数、门槛混在自由文本里），报名没有审批流程，爽约没有任何后果。

## 二、选题意义

**实践层面**，本课题把"找搭子"从"发帖拉群"升级为结构化流程：时间、地点、人数、段位与性别门槛全部结构化填写，报名经过发布者审批，满员后自动进入候补队列，有人退出时自动递补，活动结束后参与者之间强制互评。同时，系统把"靠谱"这一主观印象转化为可量化的信誉分：临场取消、爽约、被评价均留下记录并影响后续使用权限（低于阈值禁止发帖与报名、发布的组局在推荐中沉底），使小型社区中的履约行为第一次有了可积累、可失去、有实际后果的信号。

**方法层面**，本课题将状态机引入组局与报名两类核心业务对象的管理，把散落的业务分支收敛为显式的合法流转规则，并用逐条边覆盖的单元测试加以守护；将信誉约束与业务权限打通，验证"信用机制调节小型社区行为"的可行性；在推荐排序上采用可解释的加权公式（兴趣匹配 + 时间重合 + 发布者信誉 + 热度），在垂直场景中以可解释性替代模型复杂度，避免冷启动与"黑盒推荐难以解释"的问题。

**交付层面**，课题将产出一套可直接运行、可复现的完整系统：H5 用户端、PC 管理端、单体后端、数据库脚本与部署文档齐备，具备实际落地形态。

## 三、主要研究内容

系统面向高校学生，采用"**标签匹配 + 状态化预约 + 信誉分约束**"三位一体的机制设计，解决"找搭子难、约搭子难、搭子不靠谱"三个具体问题。主要研究内容包括：

**（1）组局与报名全流程**：用户发布组局（填写时间、地点、人数上限、段位与性别门槛、描述），报名者经过资格校验（信誉分阈值、段位、性别）后提交申请，发布者审批；满员自动进入"已满员"状态，后来者进入候补队列。

**（2）候补与自动递补**：候补按报名时间先到先得；已有通过者取消报名时，队首候补自动递补为待审批状态，取消、递补与名额回退在同一个事务内完成，并发下不重复递补、不丢名额。

**（3）信誉分体系**：初始 100 分，由"评价影响 + 台账变动"构成并限幅 0~100；临场取消、未到场等惩罚即刻生效，每日全量重算兜底；低信誉用户禁止发帖、禁止报名、推荐沉底，恢复后自动解禁。

**（4）推荐与广场**：按可解释加权公式对组局进行个性化排序，支持最新、最热排序与分类、关键词、时间范围筛选，游客可用。

**（5）活动闭环**：活动开始前定时提醒；活动结束后发布者标记出勤，参与者互评（星级 + 标签 + 文字），评价结果回流信誉分。

**（6）管理端**：用户管理（封禁/解封/重置信誉）、帖子管理（下架/删除）、举报处置（含自动风控）、标签管理、公告管理与数据统计（趋势、留存、漏斗、举报处理统计、CSV 导出）。

系统规模：后端接口约 60 个、数据库 13 张表、两个前端共 23 个页面，核心业务单元测试 137 例并配置持续集成流水线。

## 四、技术方案概要

| 层 | 技术选型 |
| --- | --- |
| 后端 | Java 17 + Spring Boot 3.3.5 + MyBatis-Plus，按业务模块分包 |
| 数据库 | MySQL 8（13 张表，逻辑删除，关键唯一约束） |
| 认证与安全 | JWT（JJWT）+ 拦截器统一鉴权；BCrypt 密码；密钥启动自检；CORS 白名单；上传内容识别；关键写接口限流 |
| 辅助数据存储 | 统一接口抽象，默认 MySQL 单表实现（零外部依赖），可一行配置切换 Redis |
| H5 用户端 | Vue 3 + Vant 4 + Pinia + Vite |
| 管理端 | Vue 3 + Element Plus + ECharts + Vite |
| 测试与集成 | JUnit 5 + Mockito + AssertJ（137 例）；GitHub Actions（后端单测 + 双前端构建） |

**关键设计点**：①业务状态机——帖子 5 种状态、报名 7 种状态，非法流转直接拦截；②并发一致性——所有状态转换采用"带预期旧状态的条件更新 + 影响行数校验"，名额自增采用"原子条件 SQL 防超卖"，用户级行锁防止并发绕过发帖上限；③信誉分与权限联动；④可解释推荐公式；⑤列表查询批量组装（IN 查询 + 内存拼接），杜绝 N+1。

## 五、可行性分析

**技术可行性**：所选技术栈（Spring Boot、MyBatis-Plus、Vue 3、Vant/Element Plus）均为业界成熟的方案，社区文档与案例丰富；状态机、条件更新、原子 SQL 等关键技术点在本项目场景下已验证可行，并有单元测试佐证。

**业务可行性**：需求来源于作者在校学习生活中的真实观察，场景明确、边界清晰；系统明确不涉及支付、即时聊天等高风险或强合规要求的模块，联系方式按报名状态授权可见，个人信息展示做了隐私控制，无政策合规风险。

**经济可行性**：全部采用开源技术与本地环境部署，无第三方付费服务依赖；开发工具（IDEA、VS Code、Navicat）均可免费或已有授权使用。

**时间可行性**：课题已完成需求分析、核心功能开发与一轮工程质量整改，具备可运行、可演示的系统；剩余时间用于完善细节、补充测试与实验记录，并撰写毕业论文与准备答辩，进度安排留有余量。
